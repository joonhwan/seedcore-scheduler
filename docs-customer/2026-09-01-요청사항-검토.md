## 1. 사용자 삭제 기능 — 조건부 가능 / 완전 삭제는 불가

### 현재 상태

사용자 관리 화면(`apps/web/src/pages/AdminUsersPage.tsx`)에는 활성·비활성 전환, 비밀번호 초기화, 잠금 해제가 있고 삭제는 없습니다. 서버에도 삭제 기능이 없습니다(`apps/api/src/users/users.controller.ts`).

### 완전 삭제가 불가능한 이유

데이터베이스에서 사용자 정보를 지우면 그 사람이 남긴 기록이 함께 무너집니다. 사용자 행은 아래 위치에서 참조되고 있으며, 외래키 정책이 대부분 `ON DELETE RESTRICT`(참조가 남아 있으면 삭제를 거부)입니다.

| 참조하는 곳 | 의미 | 삭제 시 결과 |
|---|---|---|
| `projects.created_by` | 프로젝트를 만든 사람 | 삭제 거부 |
| `project_members.user_id` / `added_by` | 프로젝트 참여 이력 | 삭제 거부 |
| `schedule_nodes.created_by` / `updated_by` | 일정을 만들고 고친 사람 | 삭제 거부 |
| `node_comments.author_id` | 댓글 작성자 | 삭제 거부 |
| `node_history.actor_id` | 일정 변경 이력의 주체 | 삭제 거부 |
| `audit_logs.actor_id` | 감사 기록 | 작성자만 `NULL` 로 바뀜 |

즉 프로젝트에 한 번이라도 참여했거나 일정을 건드린 사람은 데이터베이스 차원에서 삭제되지 않습니다. 억지로 지우려면 그 사람이 만든 일정과 변경 이력을 함께 지우거나 작성자를 익명으로 바꾸어야 하는데, 이는 "누가 언제 무엇을 고쳤는지 추적할 수 있어야 한다"는 이 시스템의 기본 원칙(`AGENTS.md` §4.7)을 정면으로 거스릅니다.

### 대신 제안하는 방식

1. **활동 기록이 없는 계정만 완전 삭제**: 만든 뒤 아무 활동이 없는 계정(프로젝트 참여·일정·댓글·이력이 모두 0건)에 한해 진짜 삭제 버튼을 제공합니다. 잘못 만든 계정을 정리하는 용도로는 충분합니다.
2. **활동 기록이 있는 계정은 "퇴사 처리"**: 비활성으로 바꾸는 동시에 기본 목록에서 감추고, "퇴사자 포함 보기"를 켰을 때만 나타나게 합니다. 화면에서 사라지므로 실사용 체감은 삭제와 같으면서 이력은 보존됩니다.

두 방식 모두 데이터베이스 스키마를 바꾸지 않고 구현할 수 있습니다. 다만 2번에서 "퇴사"를 단순 비활성과 구분하려면 사용자 테이블에 상태 컬럼을 추가하는 편이 깔끔하며, 그 경우 마이그레이션이 발생하므로 사전에 별도로 안내드리겠습니다.

## 2. 로그인 유지 — 원인 확인, 수정 가능 (최우선)

### 확인된 원인

서버는 세션을 두 겹으로 관리합니다(`apps/api/src/sessions/sessions.service.ts`).

- 슬라이딩 만료 30분: 요청이 올 때마다 만료 시각을 30분 뒤로 미룹니다.
- 절대 만료 12시간: 로그인한 지 12시간이 지나면 무조건 끊습니다.

문제는 **브라우저에 내려주는 세션 쿠키의 만료 시각이 로그인 시점 기준 30분으로 고정된 뒤 다시 갱신되지 않는다**는 점입니다. 로그인 응답에서만 쿠키를 설정하고(`apps/api/src/auth/auth.controller.ts:70`), 이후 요청을 처리하는 인증 가드는 데이터베이스의 만료 시각만 미룰 뿐 쿠키를 다시 발급하지 않습니다(`apps/api/src/auth/auth.guard.ts`).

그 결과 서버 세션은 살아 있는데도 브라우저가 30분 만에 쿠키를 스스로 버립니다. 계속 작업하고 있었는지 여부와 관계없이 **로그인 후 정확히 30분이 지나면 다음 요청에서 로그인 화면으로 이동**하게 됩니다. 사용자 대표께서 말씀하신 증상과 정확히 일치합니다.

### 수정 방향

1. 요청을 처리할 때마다 갱신된 만료 시각으로 세션 쿠키를 다시 내려보냅니다. 이것만으로 "쓰고 있는 동안에는 끊기지 않는다"가 성립합니다.
2. 그 위에 유지 시간 자체를 업무 형태에 맞게 늘립니다. 폐쇄망 단일 서버 환경이므로 슬라이딩 만료를 8시간, 절대 만료를 24시간 정도로 두어도 위험이 크지 않다고 봅니다.
3. 화면을 열어둔 채 오래 손대지 않는 경우까지 살리려면, 사용자가 편집 중일 때 주기적으로 세션을 연장하는 신호를 보내는 방식을 함께 넣겠습니다.
4. 편집하던 내용이 날아가는 문제를 줄이기 위해, 세션이 끊겼을 때 곧바로 로그인 화면으로 보내는 대신 화면 위에 다시 로그인하는 창을 띄우는 방식도 검토할 수 있습니다.

유지 시간은 보안 정책과 직결되므로 아래 11장 ①에서 확인을 요청드렸습니다.

## 3. MANAGER 지정 시 전체 선택 버튼 — 구현 가능 (소규모)

새 프로젝트 화면(`apps/web/src/pages/ProjectNewPage.tsx`)에는 활성 사용자 목록과 검색창, 개별 체크박스가 이미 있습니다. 여기에 "전체 선택"과 "전체 해제" 버튼을 추가하면 됩니다. 검색어가 입력된 상태라면 검색 결과에 한해 선택하도록 만드는 편이 실수를 줄입니다.

다만 전 인원을 MANAGER로 두면 그 프로젝트에서는 모두가 일정 생성·삭제와 멤버 관리 권한을 갖게 됩니다. 의도가 "전원을 참여시키되 권한은 일반 멤버로 준다"는 것이라면 화면 구성이 달라지므로 11장 ②에서 확인을 요청드렸습니다.

## 4. 프로젝트 목록 세로 스크롤 — 구현 가능 (소규모)

현재 프로젝트 목록은 한 페이지에 10건씩 끊어 보여주고 아래에 페이지 번호를 답니다(`apps/web/src/pages/ProjectsPage.tsx:132`의 `pageSize = 10`). 18건이면 두 페이지로 갈라집니다.

페이지 번호를 없애고 전체를 한 번에 세로로 이어 보여주도록 바꾸겠습니다. 서버는 이미 한 번에 최대 500건을 내려주고 있으므로(`apps/api/src/projects/projects.service.ts`) 화면 쪽만 고치면 되고, 150명·수십 개 프로젝트 규모에서는 성능 문제가 없습니다. 스크롤을 내려도 표 머리글은 위에 고정해 두겠습니다.

## 5. 최근 수정순 정렬과 수정 내역 로그창

이 항목은 성격이 다른 두 가지 요청이 함께 들어 있어 나누어 답변드립니다.

### 5-1. 최근 업데이트순 자동 정렬 — 일부는 이미 있음

서버는 프로젝트 목록을 수정일 내림차순으로 내려주고 있고, 화면의 "수정일" 열 머리글을 누르면 그 기준으로 다시 정렬할 수도 있습니다. 다만 화면의 **기본 정렬은 생성일 최신순**입니다. 목록에서 이름을 고치거나 보관 처리를 하면 그 행이 갑자기 다른 위치로 튀어 "보고 있던 항목이 사라진" 것처럼 보이는 문제가 있어 의도적으로 그렇게 두었습니다(`apps/web/src/lib/projectListSort.ts`의 주석 참고).

기본 정렬을 수정일 최신순으로 되돌리는 것은 어렵지 않습니다. 그러나 **7번을 먼저 고치지 않으면 의미가 없습니다.** 지금은 일정을 아무리 고쳐도 프로젝트 수정일이 바뀌지 않아 순서가 그대로이기 때문입니다. 7번을 고친 뒤 기본 정렬을 바꾸겠습니다.

### 5-2. 수정 내역 로그창 — 절반은 이미 있음

프로젝트 단위 이력 조회 화면이 이미 있습니다(`/projects/:id/history`). 누가·언제·어떤 일정을·어떻게 고쳤는지를 시간 역순으로 보여주고, 기간(지난 1주/1달/직접 지정)과 주제(전체·진척율 낮춤·삭제됨·기간 변경·댓글)로 걸러 볼 수 있으며, 삭제된 일정의 이력도 남습니다. 개별 일정을 열면 그 일정의 변경 이력과 댓글이 오른쪽 패널에 함께 나옵니다.

요청하신 것과 다른 점은 세 가지입니다.

| 요청 | 현재 | 필요한 작업 |
|---|---|---|
| 상시 팝업 창 | 별도 화면으로 이동 | 화면 위에 뜨는 창 형태로 다시 만들기 |
| 로그 버튼으로 어디서나 열기 | 프로젝트 안에서만 진입 | 상단 막대에 버튼 추가 |
| 전 프로젝트 통합 로그 | 프로젝트 하나씩만 조회 | 신규 개발 |

전 프로젝트 통합 로그는 새로 만들어야 합니다. 로그인·사용자 생성·권한 변경 같은 시스템 전반의 기록은 이미 감사 기록 테이블(`audit_logs`)에 차곡차곡 쌓이고 있으나 **읽어오는 기능이 없어 화면에서 볼 수 없는 상태**입니다. 조회 기능을 새로 붙이면 됩니다. 스키마 변경은 필요하지 않습니다.

## 6. 간트 차트 확대·축소 — 이미 있음 / 단위 조정 가능

확대·축소는 이미 동작합니다(`apps/web/src/components/Timeline.tsx`).

- 화면 상단 도구막대의 확대·축소 버튼
- 키보드 `+` 키로 확대, `-` 키로 축소
- "화면 맞춤" 버튼으로 전체 일정을 한 화면에 담기
- 일·주·월·분기 단위 전환

다만 한 번 누를 때 **1.3배(약 30%)씩** 움직여 요청하신 10% 단위보다 거칩니다. 배율을 10%로 바꾸고, 지금 몇 퍼센트인지 숫자로 표시하며, 슬라이더로 끌어 맞출 수 있게 하겠습니다. 배율이 잘게 나뉘면 버튼을 여러 번 눌러야 하므로 슬라이더를 함께 두는 편이 실제로는 더 편합니다.

혹시 말씀하신 "확대·축소"가 화면 배율이 아니라 **인쇄물처럼 전체를 한 장에 담는 축소**를 뜻한다면 접근이 달라지므로 11장 ③에서 확인을 요청드렸습니다.

## 7. 프로젝트 수정일이 갱신되지 않는 문제 — 결함, 수정 가능

### 확인된 원인

일정을 추가·수정·삭제하는 처리는 일정 테이블만 건드리고 프로젝트 행은 손대지 않습니다(`apps/api/src/nodes/nodes.service.ts`에 프로젝트를 갱신하는 코드가 없습니다). 프로젝트의 수정일은 프로젝트 이름이나 설명, 보관 상태를 바꿀 때만 움직입니다. 말씀하신 "26/08/21로 고정"은 그날 프로젝트 자체를 마지막으로 손댔다는 뜻입니다.

### 수정 방향

일정을 추가·수정·이동·삭제할 때 소속 프로젝트의 수정일을 함께 갱신하겠습니다. 이때 결정할 사항이 하나 있습니다. **댓글 작성도 "수정"으로 볼 것인지**입니다. 댓글까지 포함하면 활발한 프로젝트가 목록 위로 잘 올라오지만, "일정이 바뀐 날"이라는 뜻은 흐려집니다. 11장 ④에서 확인을 요청드렸습니다.

목록에 "최종 수정자"를 함께 보여드릴 수도 있습니다. 다만 이 경우 프로젝트 테이블에 컬럼을 추가해야 하므로 데이터베이스 변경이 발생합니다. 필요하다고 판단되면 별도로 안내드리고 진행하겠습니다.

## 8. 서버 재시작 시 접속자 확인 — 구현 가능 (기준 합의 필요)

세션 테이블에 접속 정보가 이미 남습니다: 누구인지(`user_id`), 언제 로그인했는지(`created_at`), 마지막으로 요청을 보낸 시각(`last_seen_at`), 접속 IP까지 들어 있습니다.

따라서 관리자 화면에 **현재 접속자 목록**을 만드는 것은 어렵지 않습니다. 이름·최근 활동 시각·접속 IP를 함께 보여드릴 수 있습니다.

한 가지 미리 말씀드릴 점이 있습니다. 이 시스템은 웹 브라우저로 접속하는 구조라 **"지금 화면을 보고 있는 사람"을 정확히 알 수는 없습니다.** 브라우저를 그냥 닫으면 서버에 아무 신호도 오지 않기 때문입니다. 그래서 실제로는 "최근 몇 분 안에 활동한 사람"으로 근사하게 판단합니다. 판단 기준(예: 최근 5분 이내 활동)을 정해 주시면 그대로 반영하겠습니다.

함께 만들면 유용할 기능도 제안드립니다.

- **재시작 예고 배너**: 관리자가 "○시 ○분에 재시작합니다"를 등록하면 접속 중인 모든 화면 위쪽에 안내 띠가 뜹니다. 전체 공지를 따로 돌리지 않아도 됩니다.
- **미저장 편집 경고**: 재시작 예고가 뜬 상태에서 편집 중인 내용이 있으면 화면에서 저장을 재촉합니다.

배너 문구를 저장하려면 설정 값을 담을 자리가 필요하므로 작은 테이블이 하나 추가될 수 있습니다. 그 경우 사전에 별도로 안내드리겠습니다.

## 9·10. 인원별 프로젝트 권한 관리 — 구현 가능

9번(사용자를 고르고 여러 프로젝트에 한 번에 권한 부여)과 10번(인원별 참여 프로젝트 조회·추가·삭제)은 같은 화면에서 함께 해결하는 것이 자연스러워 묶어 답변드립니다.

### 현재 상태

권한 관리는 프로젝트를 기준으로만 되어 있습니다. 서버 기능도 "이 프로젝트의 멤버를 조회·추가·변경·삭제한다"는 형태뿐이고(`apps/api/src/members/members.controller.ts`), **특정 사용자가 어떤 프로젝트에 속해 있는지 조회하는 기능은 없습니다.** 그래서 말씀하신 대로 프로젝트마다 들어가 한 사람씩 넣어야 합니다.

### 구현 방향

관리자 모드의 사용자 관리 화면에서 사람을 고르면 오른쪽에 그 사람의 프로젝트 참여 현황이 나오도록 만들겠습니다.

1. **조회**: 그 사람이 참여 중인 프로젝트 전체와 각각의 역할(MANAGER/MEMBER), 참여 시작일을 목록으로 보여줍니다.
2. **일괄 추가**: 전체 프로젝트 목록을 체크박스로 띄우고, 여러 개를 한꺼번에 골라 역할을 지정해 넣습니다.
3. **역할 변경·제외**: 목록에서 바로 역할을 바꾸거나 프로젝트에서 뺍니다.

데이터베이스 구조는 이미 이 조회를 감당하도록 되어 있습니다(`project_members` 테이블에 사용자 기준 색인이 있습니다). 스키마를 바꾸지 않고 조회·일괄 처리 기능과 화면만 새로 만들면 됩니다.

기존 규칙 두 가지는 그대로 지킵니다.

- 프로젝트의 마지막 MANAGER는 제외할 수 없습니다. 관리자가 없는 프로젝트가 생기는 것을 막기 위해서입니다.
- 모든 권한 변경은 감사 기록에 남습니다.

## 11. 확인이 필요한 사항 (회신 요청 문안)

아래 내용은 사용자 대표께 그대로 전달하실 수 있도록 정리한 것입니다.

> 보내주신 수정 요청사항을 검토했습니다. 10건 중 9건은 구현 가능하며, 그중 2건(2번 로그인 유지, 7번 수정일 갱신)은 새 기능이 아니라 시스템 결함으로 확인되어 먼저 처리하겠습니다. 6번 확대·축소는 이미 들어 있는 기능이므로 조작 단위만 요청하신 수준으로 조정하겠습니다.
>
> 다만 정확히 만들기 위해 아래 여섯 가지를 확인해 주시면 감사하겠습니다.
>
> **① 로그인 유지 시간** — 현재 설계는 마지막 조작으로부터 30분, 로그인 후 최대 12시간입니다(다만 결함 때문에 실제로는 로그인 30분 뒤 무조건 끊기고 있었습니다). 이를 어느 정도로 늘리기를 원하시는지요? 예를 들어 "근무 시간 내내 유지(마지막 조작으로부터 8시간, 로그인 후 최대 24시간)" 정도를 제안드립니다. 폐쇄망 환경이라 위험이 크지 않으나, 공용 PC에서 접속하는 경우가 있다면 유지 시간을 무한정 늘리기는 어렵습니다.
>
> **② 프로젝트 생성 시 전체 선택의 의미** — "전체 인원 선택"이 (가) 전원을 MANAGER로 지정한다는 뜻인지, (나) 전원을 프로젝트에 참여시키되 몇 명만 MANAGER로 두고 나머지는 일반 멤버로 둔다는 뜻인지 알려주시기 바랍니다. MANAGER는 일정 생성·삭제와 멤버 관리까지 할 수 있는 권한이라 전원에게 주기에는 부담이 있을 수 있습니다.
>
> **③ 간트 확대·축소의 의미** — 화면에서 보는 배율을 10% 단위로 조절한다는 뜻이 맞는지요? 만약 인쇄물이나 이미지로 내보낼 때 전체 일정을 한 장에 담는 축소를 말씀하신 것이라면 별도 기능이므로 알려주시기 바랍니다.
>
> **④ 프로젝트 "수정일"의 기준** — 일정을 추가·변경·삭제한 시각을 수정일로 삼는 것은 확정입니다. 여기에 댓글 작성도 포함할지 정해 주시기 바랍니다. 포함하면 활발한 프로젝트가 목록 위로 잘 올라오고, 제외하면 "일정이 실제로 바뀐 날"이라는 뜻이 분명해집니다.
>
> **⑤ 접속자 확인의 기준과 용도** — 브라우저를 그냥 닫는 경우 서버에 신호가 오지 않아 "지금 화면을 보고 있는 사람"을 정확히 알 수는 없습니다. "최근 5분 이내에 활동한 사람"과 같은 근사 기준을 쓰게 되는데, 몇 분을 기준으로 할지 알려주시기 바랍니다. 아울러 관리자가 재시작 예정 시각을 등록하면 접속 중인 모든 화면에 안내 띠가 뜨는 기능도 함께 넣을 수 있는데, 필요하신지 회신 부탁드립니다.
>
> **⑥ 사용자 삭제의 범위** — 이 시스템은 "누가 언제 무엇을 고쳤는지"를 추적할 수 있어야 한다는 요건 때문에, 일정을 만들거나 고친 적이 있는 계정을 데이터베이스에서 완전히 지우면 그 사람이 남긴 일정과 변경 이력까지 함께 무너집니다. 따라서 다음 두 가지로 나누어 처리하려 합니다.
>
> - 활동 기록이 전혀 없는 계정(잘못 만든 계정 등)은 완전 삭제를 허용합니다.
> - 활동 기록이 있는 계정은 "퇴사 처리"하여 사용자 목록에서 감춥니다. 화면상으로는 사라지므로 삭제와 다르지 않으나, 과거 이력에는 이름이 남습니다.
>
> 이 방식으로 진행해도 괜찮은지 확인 부탁드립니다.
>
> 추가로 한 가지 말씀드립니다. 5번의 "최근 수정순 정렬"은 7번(수정일이 갱신되지 않는 문제)을 고쳐야 실제로 동작하므로, 7번을 먼저 수정한 뒤 정렬 기본값을 바꾸겠습니다.

  - 사용자를 "퇴사" 상태로 구분하는 경우(사용자 테이블에 상태 컬럼 추가)
