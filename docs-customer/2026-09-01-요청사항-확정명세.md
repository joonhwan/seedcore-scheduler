## 1. ① 로그인 유지 — 확정 사양

### 회신 내용
로그인 후 12시간 유지, 만료 10분 전에 연장 팝업을 띄워 12시간을 다시 확보하는 방식(관공서 시스템 방식).

### 확정 사양

1. **세션 수명은 12시간 하나로 단순화합니다.** 지금은 "마지막 조작으로부터 30분"과 "로그인 후 12시간" 두 겹인데, 앞의 30분 규칙을 없애고 12시간만 남깁니다. 조작 여부와 무관하게 로그인 후 12시간이 기준선이 됩니다.
2. **1차 검토에서 확인한 쿠키 결함을 함께 고칩니다.** 브라우저 쿠키의 만료 시각도 12시간으로 맞춰 발급합니다. 이 수정이 없으면 아래 팝업이 뜨기도 전에 30분 만에 끊깁니다.
3. **만료 10분 전 연장 팝업**을 띄웁니다. 남은 시간을 초 단위로 세어 보여주고, 버튼은 두 개입니다.
   - "로그인 연장": 세션을 새로 발급해 다시 12시간을 확보합니다.
   - "지금 로그아웃": 즉시 종료합니다.
4. **팝업을 놓친 경우**에는 만료 시각에 자동 로그아웃되며, 다시 로그인하는 화면이 뜹니다. 이때 편집 중이던 내용이 있으면 그 사실을 함께 알려 저장을 놓치지 않게 합니다.
5. 화면 오른쪽 위에 **남은 시간**을 상시 표시해 언제 끊기는지 미리 알 수 있게 합니다.

### 연장 횟수 (㉮ 확정)
**연장 횟수에는 제한을 두지 않습니다(㉮ 회신).** 폐쇄망 단일 서버라는 전제에서 나온 결정입니다. 화면을 열어둔 채 연장을 계속 누르면 그만큼 계속 쓸 수 있습니다.

### 데이터베이스 변경
없습니다. 기존 세션 테이블을 그대로 사용합니다.

## 2. ② 사용자 그룹(부서) 관리 — 신규 기능, 요구 확대

### 회신 내용
운영기술센터 21명, 구매팀 3명, 경영관리 10명처럼 인원을 그룹으로 묶어 관리하고, 프로젝트를 만들 때 그룹을 골라 일괄 참여시키며, 그룹 밖 인원(임원 등)은 개별로 덧붙이는 방식.

### 판정: 구현 가능하나 신규 기능입니다

당초 "전체 선택 버튼 추가"로 보았던 것이, 조직 구조를 시스템에 담는 기능으로 확대되었습니다. 현재 시스템에는 부서나 그룹 개념이 전혀 없습니다. 사용자는 아이디·이름·역할(ADMIN/USER)만 가지며, 소속을 나타내는 자리가 없습니다.

다만 **이 기능은 9번·10번(인원별 프로젝트 권한 관리)과 맞물려 관리 부담을 크게 덜어줍니다.** 그룹이 생기면 "구매팀 전원을 이 프로젝트에 넣는다", "운영기술센터 소속이 참여 중인 프로젝트를 본다" 같은 일이 한 번에 됩니다. 투자할 가치가 있다고 판단합니다.

### 확정 사양

**가. 그룹 관리 화면 (관리자 모드 신규)**
- 그룹 생성·이름 변경·삭제
- 그룹에 인원 추가·제외 (여러 명 한꺼번에 선택)
- 그룹별 인원수와 소속자 목록 조회

**나. 프로젝트 생성 화면 개편**
- 그룹 목록에서 참여 그룹을 고릅니다(복수 선택 가능). 상위 그룹을 고르면 **하위 그룹 인원까지 함께** 들어옵니다.
- 그룹 밖 인원이나 다른 팀에서 한두 명만 넣을 때는 지금처럼 검색해 개별로 덧붙입니다.
- 그룹으로 들어온 사람과 개별로 넣은 사람이 겹쳐도 한 번만 들어갑니다.
- 참여자마다 역할(MANAGER/MEMBER)을 지정합니다. **그룹으로 들어온 인원의 기본 역할은 MEMBER**로 두고, MANAGER는 개별로 지정합니다.
- 최종 참여자 명단과 인원수를 한 화면에서 확인한 뒤 생성합니다. 위 예시대로라면 "총 7명"처럼 표시됩니다.

**다. 기존 프로젝트에도 그룹 단위 추가**
- 이미 만든 프로젝트의 멤버 관리 화면에서도 그룹을 골라 일괄 추가할 수 있게 합니다.

### 그룹과 프로젝트의 관계 — 명단 복사 방식으로 확정 (㉯ 회신)

프로젝트를 만드는 시점의 그룹 인원을 **참여자 명단으로 복사**합니다. 이후 그룹에 사람이 들어오거나 빠져도 이미 만들어진 프로젝트의 참여자는 그대로 유지됩니다.

- 신규 입사자는 관리자가 그룹에 넣고, 참여시킬 프로젝트를 골라 개별로 추가합니다(10번 기능으로 여러 프로젝트를 한 번에 체크할 수 있습니다).
- 그룹에서 사람을 빼도 진행 중인 프로젝트의 권한은 사라지지 않습니다. 권한이 사람 모르게 바뀌는 사고를 막기 위한 것입니다.

### 조직 계층 — 상위 그룹을 고르면 하위 인원까지 (㉰ 회신)

회신 주신 예시를 그대로 담으려면 그룹에 **상하 관계**가 필요합니다.

```
운영기술센터 (21명)
├─ 기구완성팀 (5명)
├─ 생산기술팀 (8명)
├─ 품질보증팀 (7명)
└─ 센터장 (1명, 팀에 속하지 않고 센터 직속)
```

이 구조라면 회신의 두 예시가 그대로 성립합니다.

| 예시 | 선택 | 결과 |
|---|---|---|
| 1 | 운영기술센터 체크 | 하위 세 팀과 센터장까지 **21명 전원** |
| 2 | 기구완성팀 체크 + 센터장 개별 + 품질보증팀원 1명 개별 | **7명** |

**소속은 1인 1소속입니다.** 사람은 자기가 실제로 속한 말단 팀 하나에만 등록하고, 상위 그룹 소속은 계층에서 저절로 따라옵니다. 기구완성팀원 5명을 운영기술센터에 또 넣을 필요가 없으므로, 같은 사람이 여러 곳에 중복 등록되어 명단이 어긋나는 일이 생기지 않습니다.

다만 데이터베이스 구조 자체는 한 사람이 여러 그룹에 속할 수 있는 형태로 두고, **화면에서 1인 1소속을 지키도록** 만들겠습니다(이미 다른 그룹에 있는 사람을 추가하면 "옮기시겠습니까?"라고 묻는 방식). 나중에 겸직이나 파견 인원이 생겨 예외가 필요해질 때 데이터 구조를 뜯어고치지 않아도 되기 때문입니다.

### 데이터베이스 변경 (신규 테이블 2개)

```
user_groups          그룹 자체
  id, name, parent_id(상위 그룹, 없으면 최상위), description, created_at, updated_at
  같은 상위 그룹 안에서 이름이 겹치지 않도록 제한

user_group_members   그룹 소속
  group_id, user_id, added_by, added_at
  기본키: (group_id, user_id)
```

`parent_id` 하나로 계층을 표현합니다. 계층을 쓰지 않고 평평한 그룹 목록으로만 운영하셔도 그대로 동작하므로, 조직 개편이 있어도 구조 변경 없이 따라갈 수 있습니다.

## 3. ③ 간트 확대·축소와 출력 — 절반은 이미 있습니다

### 회신 내용
화면을 일정 배율로 확대·축소하고, **그 화면 그대로를 출력물로 내보내는** 기능. 4개월 프로젝트라면 월 단위 전체 출력, 4주 단위 출력, 1주 단위 날짜별 출력이 모두 필요.

### 먼저 알려드릴 사항 — 단위별 출력은 이미 됩니다

현재 프로젝트 화면의 **내보내기 메뉴에 이미 다음 기능이 들어 있습니다.**

| 기능 | 지원 내용 |
|---|---|
| 간트 이미지(PNG) 내보내기 | **일·주·월·분기** 중 단위 선택, 표시할 트리 단계 선택(예: 2단계까지만), 밝은/어두운 테마 선택 |
| 엑셀(.xlsx) 간트 내보내기 | **일·주·월** 중 단위 선택, 개요(윤곽선) 포함 여부 선택 |

즉 "월 단위 전체 진행 상황"과 "주 단위", "일 단위" 출력물은 지금도 뽑을 수 있습니다. **아직 써 보지 않으셨다고 하셨으므로, 먼저 사용해 보신 뒤 부족한 점을 알려주시기로 했습니다(㉱ 보류).** 사용 위치는 사용설명서에서 안내드립니다.

### 현재 기능의 한계 — 여기가 실제로 부족한 부분

1. **기간을 잘라 뽑을 수 없습니다.** 지금은 프로젝트 전체 기간을 한 장에 담습니다. 4개월 프로젝트를 일 단위로 뽑으면 가로로 매우 긴 이미지 한 장이 나오고, 인쇄하면 글씨를 알아보기 어렵습니다. "3월 1일~3월 28일 구간만" 같은 지정이 불가능합니다.
2. **화면에서 확대한 배율이 출력에 반영되지 않습니다.** 화면 배율과 출력 배율이 따로 놀아, 화면에서 보기 좋게 맞춘 상태를 그대로 뽑을 수 없습니다.

### 확정 사양

**가. 화면 배율 (요청하신 10% 단위)**
- 확대·축소를 10% 단위로 바꾸고, 현재 배율을 숫자로 표시합니다.
- 잘게 나뉘면 버튼을 여러 번 눌러야 하므로 슬라이더를 함께 둡니다.
- 기존의 화면 맞춤 버튼과 키보드 단축키는 그대로 둡니다.

**나. 보고 있는 화면 그대로 내보내기**
- 내보내기 대화상자에 "지금 화면 그대로" 선택지를 추가해, 현재 배율과 펼침 상태를 그대로 출력물에 담습니다.

**다. 기간을 지정한 출력 (신규)**
- 출력 대상 기간을 직접 지정합니다(시작일~종료일).
- 자주 쓰는 범위는 버튼으로 제공합니다: 전체 기간 / 이번 달 / 이번 주 / 앞으로 4주.

**라. 여러 장으로 잘라 PDF 한 부로 내보내기 (신규, ㉲ 회신 반영)**
- "4개월을 4주씩 잘라 4장", "한 달을 1주씩 잘라 5장"처럼 기간을 자동 분할합니다.
- 결과물은 **인쇄용 PDF 한 부**입니다. 4주씩 넉 장이면 4쪽짜리 PDF 하나가 내려받아지므로, 회의 자료로 그대로 인쇄하실 수 있습니다. 파일이 여러 개로 흩어지지 않습니다.
- 각 쪽 머리에 그 쪽이 담은 기간(예: `2026-03-01 ~ 2026-03-28`)과 프로젝트 이름을 찍어, 인쇄물을 섞어 놓아도 순서를 알 수 있게 합니다.
- 가로로 긴 간트의 특성상 **가로 방향(A4 가로) 기본**으로 만들고, 용지 방향과 크기는 대화상자에서 고를 수 있게 합니다.

### 데이터베이스 변경
없습니다. 모두 화면 쪽 작업입니다.

### 기술 검토 — PDF 생성 방식
현재 간트 이미지 내보내기는 화면 밖에 간트를 그려 PNG로 찍는 방식입니다(`html-to-image`). 여기에 PDF 묶음 기능을 얹으려면 **PDF 생성 라이브러리 하나를 새로 들여와야 합니다.**

- 폐쇄망 환경이라 화면이 외부에서 무언가를 내려받는 방식은 쓸 수 없습니다. 라이브러리는 개발 단계에서 프로그램 안에 함께 묶어 배포하므로, 운영 서버가 인터넷에 연결될 필요는 없습니다.
- 기존 엑셀 내보내기(`exceljs`)와 같은 방식이므로 배포 구조가 달라지지 않습니다.
- 구간마다 이미지를 만들어 PDF 쪽으로 넣는 흐름이라, 이미 검증된 이미지 내보내기 코드를 그대로 재사용합니다.

## 4. ④ 프로젝트 수정일 — 확정

- 일정을 **추가·수정·이동·삭제**한 시각을 프로젝트 수정일로 반영합니다.
- **댓글 작성은 반영하지 않습니다.** (회신대로 확정)
- 프로젝트 이름·설명·보관 상태 변경은 지금처럼 계속 반영합니다.
- 이 수정이 끝나면 프로젝트 목록의 기본 정렬을 **수정일 최신순**으로 바꿉니다(5-1번 요청).

### 데이터베이스 변경
없습니다. 프로젝트 테이블의 기존 수정일 컬럼을 갱신하도록 처리만 추가합니다.

## 5. ⑤ 서버 재시작 예고와 접속자 확인 — 확정

### 회신 내용
재시작 5분 전부터 팝업 알림, 사용자가 확인 버튼을 눌러 닫음, 1분 주기로 남은 시간을 다시 표시.

### 확정 사양

**가. 관리자 쪽**
- 재시작 예정 시각과 안내 문구를 등록합니다. 등록한 예고는 취소할 수 있습니다.
- **현재 접속자 목록**을 함께 보여줍니다. 이름, 마지막 활동 시각, 접속 IP가 나옵니다.

**나. 사용자 쪽**
- 재시작 5분 전부터 화면 위에 팝업이 뜹니다. 남은 시간이 초 단위로 줄어드는 것이 보입니다.
- "확인" 버튼으로 닫습니다.
- 닫은 뒤에도 1분마다 다시 떠서 남은 시간을 알립니다(5분 전, 4분 전, … 1분 전).
- 편집 중인 내용이 있으면 팝업에 "저장하지 않은 변경이 있습니다"를 함께 띄웁니다.

**다. 접속자 판단 기준**
**"최근 5분 이내에 활동한 사람"을 접속 중으로 봅니다(㉳ 회신).** 브라우저를 그냥 닫은 사람은 최대 5분 동안 목록에 남습니다. 서버가 알 수 없는 정보라 근사치일 수밖에 없으므로, 재시작 직전에는 이 목록과 함께 재시작 예고 팝업을 띄우는 것이 실질적인 대비책입니다.

### 데이터베이스 변경 (신규 테이블 1개)

```
server_notices       재시작 예고 등 공지
  id, kind, message, scheduled_at, created_by, created_at, canceled_at
```

예고는 한 번에 하나만 유효하도록 다루되, 지난 예고 기록은 남겨 언제 재시작했는지 추적할 수 있게 합니다.

## 6. ⑥ 사용자 정리 — 확정 (두 방식 모두 구현)

### 가. 활동 기록이 없는 계정 완전 삭제
- 프로젝트 참여, 일정 생성·수정, 댓글, 변경 이력이 **모두 0건**인 계정에 한해 삭제 버튼이 나타납니다.
- 활동이 있는 계정에서는 버튼이 아예 보이지 않고, 그 이유를 함께 안내합니다("이 계정은 3개 프로젝트에 참여하고 일정 47건을 수정한 기록이 있어 삭제할 수 없습니다. 퇴사 처리를 이용하십시오").
- 삭제 전 확인 창을 거치며, 삭제 사실은 감사 기록에 남습니다.

### 나. 활동 기록이 있는 계정은 퇴사 처리
- 퇴사 처리하면 사용자 목록 기본 화면에서 사라집니다. "퇴사자 포함 보기"를 켜야 나타납니다.
- 로그인이 차단되고, 그 계정의 세션이 즉시 모두 끊깁니다.
- 프로젝트 참여자 선택 목록, 그룹 추가 대상 목록에서도 제외됩니다.
- 과거의 일정 이력과 댓글에는 이름이 그대로 남습니다.
- 되돌릴 수 있습니다(복직 처리).

### 데이터베이스 변경 (컬럼 1개 추가)

```
users 테이블에 retired_at (날짜, 비어 있을 수 있음) 추가
  - 값이 없으면 재직, 값이 있으면 그 시각에 퇴사 처리된 것
```

기존의 활성·비활성 구분은 그대로 둡니다. 비활성은 "일시적으로 접속을 막음", 퇴사는 "조직을 떠나 목록에서 감춤"으로 뜻이 다르기 때문입니다.

## 7. 데이터베이스 변경 총괄

`AGENTS.md` §7 규정에 따라 변경 내용을 미리 정리합니다.

| 변경 | 대상 | 내용 | 관련 항목 |
|---|---|---|---|
| 신규 테이블 | `user_groups` | 그룹 정보 + 상위 그룹(`parent_id`)으로 조직 계층 표현 | ② |
| 신규 테이블 | `user_group_members` | 그룹 소속 (운영은 1인 1소속) | ② |
| 신규 테이블 | `server_notices` | 재시작 예고 공지 | ⑤ |
| 컬럼 추가 | `users.retired_at` | 퇴사 처리 시각 | ⑥ |

- 모두 **기존 데이터를 손대지 않고 덧붙이는 변경**입니다. 기존 행이 지워지거나 형태가 바뀌지 않습니다.
- 새 컬럼은 비어 있는 상태로 추가되므로 기존 사용자는 모두 재직 상태로 유지됩니다.
- 반영 절차는 기존 마이그레이션 파이프라인을 그대로 따릅니다. 운영 서버는 재시작 시 마이그레이션이 적용되며, 적용 전 데이터베이스 백업을 먼저 수행하겠습니다.
- 다음 항목은 **데이터베이스 변경 없이** 처리됩니다: ① 로그인 유지, ③ 간트 배율·출력, ④ 수정일, 4번 목록 스크롤, 5-2번 통합 로그, 8번 접속자 목록, 9·10번 인원별 권한 관리.
- ①·④는 **이미 반영되어 운영 중**입니다(1단계 완료). 예상대로 스키마 변경 없이 처리되었습니다.

## 8. 2차 확인 결과 (2026-09-01 회신)

여섯 항목 중 다섯이 확정되었고, ㉱ 하나만 보류입니다.

| 확인 | 회신 | 반영 위치 |
|---|---|---|
| ㉮ 로그인 연장 횟수 | **제한 없음** | §1 — 1단계에서 이미 그렇게 구현되어 있어 바꿀 것이 없습니다 |
| ㉯ 그룹 인원 변경 시 기존 프로젝트 | **(나) 자동 반영 없음.** 대량 등록은 프로젝트 생성 시점에만 하고, 이후 신규 입사자는 개별로 그룹 배정·프로젝트 추가 | §2 — 명단 복사 방식으로 확정 |
| ㉰ 복수 그룹 소속 | **1인 1소속.** 그룹화의 목적은 프로젝트 생성 시 참여자를 개인별이 아니라 한 번에 고르기 위함 | §2 — 조직 계층으로 구현 |
| ㉱ 기존 내보내기 사용 경험 | **보류.** 아직 써 보지 않았으므로 사용 후 피드백 예정 | §3 — 배율·기간 작업은 그대로 진행 |
| ㉲ 여러 장 출력물 형태 | **(나) 인쇄용 PDF 한 부(여러 쪽)** | §3-라 — 압축 파일 방식은 폐기 |
| ㉳ 접속자 판단 기준 | **최근 5분 기준 그대로** | §5-다 |

### ㉰ 회신에서 새로 드러난 것 — 조직 계층

회신에 담아 주신 예시(운영기술센터 21명 = 기구완성팀 5 + 생산기술팀 8 + 품질보증팀 7 + 센터장 1)를 보면, 그룹이 평평한 목록이 아니라 **상하 관계**를 가져야 합니다. "운영기술센터를 고르면 21명 전원", "기구완성팀을 고르면 5명"이 동시에 성립해야 하기 때문입니다.

이것을 계층 없이 만들려면 같은 사람을 센터와 팀 양쪽에 중복 등록해야 하는데, 그러면 1인 1소속 방침과 어긋나고 인사 이동이 있을 때마다 두 곳을 손봐야 합니다. 그래서 그룹에 상위 그룹을 두는 방식으로 설계했습니다. 자세한 내용은 §2에 있습니다.

**이 변화가 데이터베이스에 미치는 영향은 컬럼 하나(`user_groups.parent_id`)뿐입니다.** 계층을 쓰지 않고 평평하게 운영하셔도 그대로 동작하므로, 조직 개편이 있어도 구조를 바꿀 필요가 없습니다.

| 단계 | 항목 | 상태 | 확인 대기 | 데이터베이스 변경 |

| 2단계 | 4번 목록 세로 스크롤, 6번 간트 배율 10% 단위 | 착수 가능 | — | 없음 |

**2차 회신으로 모든 단계가 착수 가능해졌습니다.** ㉱는 기존 내보내기를 써 보신 뒤의 개선 요청이라, 6단계의 기간 지정·PDF 작업 자체를 막지 않습니다. 개선 요청이 오면 그 단계에 합쳐 처리합니다.

작업량이 가장 큰 것은 3단계(그룹 관리 + 인원별 권한 관리)이고, 관리 업무 부담을 가장 크게 덜어주는 것도 이 단계입니다.

### 1단계 완료 내용 (2026-09-01)

- 로그인은 **12시간 유지**되며, 만료 10분 전에 연장 창이 뜹니다. 연장 횟수 제한은 없습니다(㉮ 회신대로입니다).
- 원인이었던 결함(만료를 미루면서 브라우저 쿠키를 다시 내려보내지 않던 문제)을 함께 고쳤습니다. 이 수정이 없으면 연장 창이 뜨기도 전에 30분 만에 끊깁니다.
- 프로젝트 목록의 **수정일이 일정 변경을 반영**합니다. 댓글 작성은 반영되지 않습니다(④ 회신대로).
- 목록 **기본 정렬이 최근 수정순**으로 바뀌었습니다.
- 사용설명서(문서·화면)에 위 내용을 반영했습니다.

> 2단계의 목록 세로 스크롤이 적용되기 전까지는, 목록에서 프로젝트를 수정하면 그 행이 한 페이지에 10건씩 나뉜 목록 안에서 위쪽으로 이동합니다. 세로 스크롤로 바꾸면 화면 안에서 자리만 옮기게 되어 자연스러워집니다.
