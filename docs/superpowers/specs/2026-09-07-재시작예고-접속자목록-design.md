## 1. 배경과 목적

폐쇄망 단일 서버라서 관리자가 서버를 직접 끄고 켠다. 지금은 그 사실을 사용자에게 알릴 방법이
없어서, 누군가 일정을 편집하는 도중에 서버가 내려가면 그 내용이 그대로 사라진다. 관리자 쪽에서도
지금 누가 쓰고 있는지 알 수 없어 재시작해도 되는 때인지 판단할 근거가 없다.

이번 작업은 두 가지를 채운다. 관리자가 재시작 예정 시각을 미리 등록하면 사용자 화면에 팝업으로
알리고, 관리자 화면에서 현재 접속 중인 사람을 보여준다.

**서버를 실제로 재시작하는 기능은 이 작업에 포함되지 않는다.** 관리자가 예고를 걸어 두고 손으로
서버를 내리는 흐름이며, 시스템은 예고와 안내만 맡는다. 그래서 예정 시각이 지나도 서버가 살아 있는
구간이 생기고, 그 구간의 동작을 §4.3 에서 따로 정한다.

---

## 2. 범위

포함하는 것은 셋이다.

1. **관리자 화면** — 재시작 예정 시각과 안내 문구를 등록하고 취소한다. 같은 화면에서 현재 접속자
   목록(이름, 마지막 활동 시각, 접속 IP)을 본다. 지난 예고 기록도 조회한다.
2. **사용자 화면** — 재시작 5분 전부터 팝업이 떠서 남은 시간을 초 단위로 센다. "확인"으로 닫아도
   1분마다 다시 뜬다.
3. **접속자 판정** — 최근 5분 이내에 활동한 사람을 접속 중으로 본다(㉳ 회신).

포함하지 않는 것은 다음과 같다.

- 서버를 실제로 종료하거나 재시작하는 기능.
- 재시작 예고 외의 공지(일반 알림, 점검 안내 등). 테이블에 `kind` 를 두어 나중에 늘릴 자리는
  만들되, 이번에는 `RESTART` 하나만 쓴다.
- 편집 중인지 감지해서 문구를 조건부로 띄우는 것. §4.4 에서 이유를 밝힌다.

## 3. 브레인스토밍에서 확정한 결정

착수 전 조사 문서가 결정을 요구한 두 지점과, 조사 과정에서 새로 드러난 충돌 하나를 사용자와
확인해 다음과 같이 정했다.

| 결정 사항 | 확정 내용 |
|---|---|
| 예정 시각이 지났는데 서버가 살아 있을 때 | 팝업 문구를 "곧 재시작됩니다"로 바꿔 계속 표시한다. 예고가 취소되거나 서버가 실제로 꺼질 때까지 유지된다 |
| "저장하지 않은 변경이 있습니다" 문구의 범위 | 편집 중인지 감지하지 않고 **항상 띄운다** |
| 관리자의 시각 입력 방식 | 빠른 버튼(5·10·30분 뒤)과 직접 입력을 함께 둔다 |
| 예고를 화면에 닿게 하는 방식 | 전용 엔드포인트를 두되, 그 라우트만 `lastSeenAt` 을 갱신하지 않는다 |

### 3.1 폴링과 접속자 판정의 충돌 (새로 드러난 것)

`AuthGuard` 는 인증된 모든 요청마다 `sessions.touch()` 를 불러 `lastSeenAt` 을 갱신한다
(`apps/api/src/auth/auth.guard.ts:60`). 예고를 받으려고 주기적으로 폴링을 걸면 **그 폴링 요청
자체가 활동으로 기록된다.** 그러면 브라우저만 켜 두고 자리를 비운 사람도 영원히 "접속 중"으로
남아, "최근 5분 이내에 활동한 사람"이라는 판정 기준이 무의미해진다.

접속자 목록과 예고 폴링은 한 기능의 양쪽이므로 함께 풀어야 한다. 그래서 폴링 라우트에 한해
`lastSeenAt` 을 건드리지 않기로 했다(§5.2).

## 4. 동작 사양

### 4.1 관리자 — 예고 등록과 취소

빠른 버튼(5분 뒤·10분 뒤·30분 뒤)을 누르면 그 시각이 채워진다. 내일 새벽처럼 미리 잡아 두는
경우에는 날짜와 시각을 직접 고른다. 안내 문구는 기본값을 채워 두어 그대로 등록해도 되게 한다.

**빠른 버튼의 기준 시각은 서버 시계다.** 관리자 화면도 `serverNow` 를 받아 두고 그것에 분을 더해
채운다. 관리자 PC 시계가 어긋나 있으면 "5분 뒤"가 실제로는 8분 뒤가 되어, 사용자 화면의
카운트다운과 관리자가 의도한 시각이 어긋난다.

**지난 시각은 등록할 수 없다.** 서버에서 `scheduledAt > now` 를 검사해 어긋나면 400 으로 돌려준다.
등록하자마자 §4.3 의 경과 상태로 들어가는 예고는 실수로 보아야 한다.

**유효한 예고는 한 번에 하나다.** 유효한 예고가 있는 동안 새로 등록하려 하면 API 가 409 로
거절하고, 화면은 등록 폼 대신 현황과 취소 버튼을 보여준다. 관리자가 모르는 사이에 앞선 예고를
덮어쓰는 일을 막기 위해서다. 시각을 바꾸려면 취소한 뒤 다시 등록하며, 두 동작이 각각 감사로그에
남는다.

### 4.2 사용자 — 팝업이 뜨는 규칙

예정 시각까지 5분 남았을 때부터 팝업이 뜬다. 남은 시간을 초 단위로 세어 보여주고 버튼은
"확인" 하나다. 닫으면 사라지지만 **1분 경계를 지날 때마다 다시 뜬다**(5분 전, 4분 전, … 1분 전).

이 재등장 규칙은 순수 함수 하나로 처리한다. 남은 시간을 0에서 자르지 않은 값으로 두고
`Math.ceil(남은ms / 60000)` 을 "분 표지"로 쓴다.

| 상태 | 분 표지 |
|---|---|
| 4분 40초 남음 | 5 |
| 3분 10초 남음 | 4 |
| 정각 | 0 |
| 70초 지남 | -1 |

"확인"을 누르면 그때의 분 표지를 예고 id 와 함께 기억하고, 표지가 달라지면 다시 띄운다. 예정
시각이 지난 뒤에도 표지가 음수로 계속 줄어들므로 **5분 전 구간과 경과 구간이 같은 규칙 하나로
처리된다.** 예고가 취소되거나 새로 등록되면 id 가 달라져 기억이 저절로 초기화된다.

### 4.3 예정 시각이 지난 뒤

카운트다운 대신 "곧 재시작됩니다. 작업 중인 내용을 저장해 주십시오"로 문구가 바뀌고, 1분마다
계속 다시 뜬다. 예고가 취소되거나 서버가 실제로 꺼질 때까지 유지된다.

재시작이 몇 분 늦어지는 일이 흔하기 때문이다. 카운트다운이 0이 되는 순간 팝업을 없애면 그 사이에
사용자가 편집을 다시 시작해 작업을 잃는다.

### 4.4 "저장하지 않은 변경이 있습니다" 문구

**편집 중인지 감지하지 않고 항상 띄운다.**

확정명세 §5-나는 "편집 중인 내용이 있으면" 이라는 조건부로 적혀 있으나, 지금 편집 상태를 아는
곳은 프로젝트 상세 화면의 일정 편집 모달과 댓글 입력 두 군데뿐이다. 프로젝트 생성·복제, 그룹
관리, 사용자 상세에도 입력 폼이 있지만 아무도 추적하지 않는다. 조건부로 만들면 추적하는 화면에서만
경고가 뜨고 나머지에서는 조용해져, 안내가 반쪽이 된다.

**고객에게 전달할 때 이 차이를 명시한다.** 조건이 빠지는 대신 놓치는 자리가 없어진다.

### 4.5 접속자 판정

`lastSeenAt >= now - 5분` **이면서** `expiresAt > now` 인 세션의 주인을 접속 중으로 본다. 뒤의
조건이 필요한 이유는 만료된 세션 행이 즉시 지워지지 않기 때문이다. 앞 조건만 보면 이미 끊긴
사람이 섞인다.

같은 사람이 창을 여러 개 열어 세션이 둘 이상이면 사람 단위로 묶어 가장 최근 활동 하나로
보여주고, IP 가 서로 다르면 함께 나열한다.

브라우저를 그냥 닫은 사람은 최대 5분 동안 목록에 남는다. 서버가 알 수 없는 정보라 근사치일
수밖에 없다.

**목록을 보고 있는 관리자 자신도 포함한다.** 빼면 인원수가 실제와 어긋나 헷갈린다. 마지막 활동
시각은 절대 시각과 상대 시간을 함께 보여준다(예: "14:32 (2분 전)"). 재시작 판단에 필요한 것은
"몇 분 전인가"이지만, 화면을 켜 둔 채 시간이 흐르면 상대 시간만으로는 언제 갱신된 값인지 알 수
없기 때문이다.

## 5. 서버 설계

### 5.1 데이터 모델

```prisma
model ServerNotice {
  id          String    @id @default(uuid())
  kind        String                          // 'RESTART' — Zod 로 제한, SQL 에 CHECK
  message     String
  scheduledAt DateTime  @map("scheduled_at")
  createdBy   String    @map("created_by")
  createdAt   DateTime  @default(now()) @map("created_at")
  canceledAt  DateTime? @map("canceled_at")

  creator     User      @relation("ServerNoticeCreatedBy", fields: [createdBy], references: [id])

  @@map("server_notices")
}
```

`User` 에 역관계 한 줄을 더한다.

```prisma
serverNotices ServerNotice[] @relation("ServerNoticeCreatedBy")
```

**`users` 테이블 자체는 건드리지 않는다.** 역관계는 Prisma 스키마에만 존재하고 SQL 에는 나오지
않으므로, 2차에서 겪은 "users 테이블 재생성" 경로를 밟지 않는다.

SQLite 는 enum 을 지원하지 않으므로 `kind` 는 `String` 으로 두고 Zod 로 제한하며, 마이그레이션
SQL 에 `CHECK (kind IN ('RESTART'))` 를 직접 쓴다(AGENTS.md §4.3).

인덱스는 두지 않는다. 예고 행은 많아야 수백 개이고 조회는 전체 훑기로 충분하다.

**유효한 예고의 정의**: `canceledAt IS NULL` 인 것 중 `createdAt` 이 가장 나중인 것. 예정 시각이
지나도 유효한 상태로 남는다(§4.3).

### 5.2 `@NoSessionTouch()`

`auth.guard.ts` 에 `@Public()`·`@AdminOnly()` 와 같은 방식으로 표시를 하나 더한다. 이 표시가 붙은
라우트에서는 `sessions.touch()` 대신 갱신 없는 조회를 쓴다. 인증과 만료 검사는 그대로 하고
`lastSeenAt` 만 손대지 않는다.

`SessionsService` 에 조회 전용 메서드를 더한다. `touch()` 에서 갱신을 뺀 형태이며, 만료된 세션과
비활성 사용자를 걸러내는 처리는 그대로 유지한다.

이 표시가 붙는 라우트는 지금으로서는 `GET /server-notices/active` 하나다.

### 5.3 엔드포인트

| 메서드·경로 | 권한 | 응답·비고 |
|---|---|---|
| `GET /server-notices/active` | 로그인 (`@NoSessionTouch`) | `{ notice: ServerNoticeView 또는 null, serverNow }` |
| `POST /server-notices` | ADMIN + `OriginGuard` | 유효한 예고가 이미 있으면 409 |
| `POST /server-notices/:id/cancel` | ADMIN + `OriginGuard` | 이미 취소된 것이면 409 |
| `GET /server-notices` | ADMIN | 지난 예고 기록. 최근 50건을 `createdAt` 내림차순으로 돌려주고 페이지네이션은 두지 않는다 |
| `GET /sessions/active` | ADMIN | `{ users: ActiveUserView[], serverNow }` |

모든 라우트에 Zod 검증을 붙이고, 상태를 바꾸는 라우트에는 `OriginGuard` 를 붙인다
(AGENTS.md §4.2·4.4).

`expectedUpdatedAt` 방식의 동시성 검사(AGENTS.md §4.5)는 쓰지 않는다. `ServerNotice` 에는
`updatedAt` 이 없고, 취소는 `canceledAt` 이 이미 채워져 있는지 보는 것으로 경합을 걸러낼 수 있다.

새 모듈은 `apps/api/src/server-notices/` 에 둔다. 접속자 조회는 이미 있는 `sessions/` 에
컨트롤러를 새로 만들어 붙인다.

### 5.4 감사로그

`AuditAction` 에 `SERVER_NOTICE_CREATE` 와 `SERVER_NOTICE_CANCEL` 을 더한다
(`packages/shared/src/index.ts`). 기존 이름들이 `대상_동작` 형태이므로 그것을 따른다.

관리자 모드에서 수행한 것이 아니라 ADMIN 전용 기능이므로 `ADMIN_OVERRIDE_EDIT` 로 기록하지
않는다. AGENTS.md §4.4 의 그 규칙은 관리자가 일반 데이터를 넘겨보며 고칠 때를 위한 것이다.

## 6. 화면 설계

### 6.1 `packages/shared` 에 더할 것

- `ServerNoticeKind` — 현재 `'RESTART'` 하나
- `CreateServerNoticeDto` — `kind`, `message`(1~500자), `scheduledAt`
- `ServerNoticeView`, `ActiveServerNoticeResponse`, `ActiveSessionsResponse`
- `SERVER_NOTICE_WARNING_MS` (5분), `ACTIVE_SESSION_WINDOW_MS` (5분)
- `AuditAction` 에 액션 둘 추가

**새 export 를 더하면 vite 사전 번들 캐시를 지워야 한다.** `pnpm dev` 로 띄우면 `scripts/dev.mjs`
가 매번 지우므로 걸리지 않는다.

### 6.2 시계 어긋남 처리 — 기존 방식을 잇는다

`sessionCountdown.ts` 에 목표 시각을 일반화한 함수를 둔다.

```ts
remainingMsFrom({ targetAt, serverNow, receivedAtLocalMs }, nowLocalMs): number
```

기존 `remainingMs(clock, now)` 가 이 함수를 부르게 바꾼다. 호출부는 그대로 두고 세션과 예고가
같은 계산을 공유한다.

브라우저 시계를 빼기의 한쪽으로 쓰지 않는 것이 이 모듈의 핵심이다. 서버가 준 두 시각의 차이로
응답 시점의 남은 시간을 구하고, 그 뒤로 흐른 시간만 브라우저 시계로 잰다. `scheduledAt` 만 내려주고
브라우저 시계로 빼면, 시계가 3분 빠른 PC 는 재시작 2분 뒤에야 팝업을 보게 된다.

`tickIntervalMs` 도 그대로 쓴다.

### 6.3 폴링

`apps/web/src/lib/serverNotice.ts` 에 `useActiveServerNotice()` 를 둔다. 로그인 상태에서만 돌고,
`refetchInterval` 은 예고가 없으면 60초, 잡혀 있으면 30초다.

남은 시간은 화면이 스스로 세므로 폴링은 예고의 **등록과 취소를 알아채는 용도**다. "5분 뒤" 버튼을
누른 직후에도 늦어야 30초 안에 팝업이 뜬다.

### 6.4 사용자 팝업

`ServerNoticeDialog.tsx` 를 `App.tsx` 최상단에 `SessionExpiryDialog` 와 나란히 둔다.

두 창이 함께 뜰 수 있으므로 재시작 쪽을 위에 놓는다(`z-[110]`, 세션 만료 창은 `z-[100]`).
재시작이 임박했다면 세션을 연장하는 것보다 저장이 급하기 때문이다.

### 6.5 관리자 화면

`/admin/server` 라우트를 더하고 헤더에 아이콘을 넣는다. **`App.tsx` 의 링크와 라우트 두 곳을 함께
고쳐야 한다**(기존 관리자 메뉴 셋이 그렇게 되어 있다).

`AdminServerPage.tsx` 는 세 부분이다.

1. **예고 카드** — 유효한 예고가 없으면 빠른 버튼과 직접 입력, 안내 문구를 받는다. 있으면 폼 대신
   현황(예정 시각, 남은 시간, 문구, 등록자)과 취소 버튼을 보여준다.
2. **접속자 목록** — 이름, 마지막 활동 시각, IP, 총 인원수. 30초마다 자동으로 갱신하고 수동
   새로고침 버튼도 둔다.
3. **지난 예고 기록** — 접어 둘 수 있는 목록.

## 7. 시험 계획

분기가 있는 순수 로직을 시험으로 먼저 짠다(`superpowers:test-driven-development`).
`sessionCountdown.test.ts` 가 본뜰 형태다.

| 대상 | 확인할 것 |
|---|---|
| `noticeCountdown.test.ts` (web) | 분 표지 계산, 재등장 판정, 예정 시각 경과 후의 음수 표지 |
| `sessionCountdown.test.ts` (web) | 일반화한 뒤에도 기존 시험이 그대로 통과하는지 |
| `server-notices.service.test.ts` (api) | 유효 예고 선택 규칙(취소된 것 제외·가장 나중 것), 중복 등록 409, 이미 취소된 것을 또 취소할 때 409 |
| 접속자 목록 판정 (api) | 5분 창 안팎의 경계, 만료된 세션 제외, 사람 단위 묶기 |

접속자 판정은 순수 함수로 떼어내 시험한다. 서비스에 DB 조회와 섞어 두면 시각 경계를 시험하기가
번거롭다.

시험은 `pnpm -F @sam/api test` 와 `pnpm -F @sam/web test` 로 돌린다. 코드를 고친 뒤에는
`pnpm -r typecheck` 로 컴파일 에러를 확인한다(AGENTS.md §4.1).

## 8. 데이터베이스 변경과 배포

**새 테이블 하나(`server_notices`)가 늘어난다. 기존 테이블은 바뀌지 않는다.**

마이그레이션 폴더가 하나 늘어나고, 두 배포 환경의 적용 상태가 다르다.

| 환경 | 적용될 마이그레이션 | 방식 |
|---|---|---|
| fly.io | 이번 것 **하나** | `master` 에 push 하면 컨테이너 기동 시 `prisma:migrate:deploy` 가 자동으로 돈다 |
| 고객 서버(exe) | 2차·3차 것과 함께 **둘**이 순서대로 | 배포판을 전달하고 관리자가 `sp-migrate.exe` 를 실행한다 |

**`master` 에 머지하기 전에 fly.io 볼륨 스냅샷을 뜬다**(AGENTS.md §7).

```bash
fly volumes list -a seedcore-scheduler
fly volumes snapshots create <volume id>
```

빌드 쪽은 손댈 것이 없다. `apps/api/scripts/build-exe.js` 가 `prisma/migrations` 전체를 복사해 두
exe 의 pkg 자산에 넣으므로, 새 폴더를 만들기만 하면 자동으로 실려 나간다. 줄바꿈 오염도
`.gitattributes` 가 막고 있다.

작업을 마친 뒤 DB 변경 내용과 파이프라인 반영 여부를 사용자에게 정리해 공유한다(AGENTS.md §7).

## 9. 작업 환경 주의사항

- `prisma migrate dev` 는 개발 서버를 끄고 돌린다. SQLite 는 단일 writer 라 `pnpm dev` 가 DB
  핸들을 쥐고 있으면 락이 걸린다.
- `packages/shared` 에 새 export 를 더하면 vite 사전 번들 캐시를 지워야 한다. 안 지우면 그 심볼이
  조용히 `undefined` 가 되어 **에러 없이 화면만 빈 채로** 뜬다.
- API 는 3000 이 뜰 때까지 시간이 걸린다. `curl http://localhost:3000/api/v1/health` 가 200 을 줄
  때까지 기다린다.
- 브라우저로 3000 을 직접 열지 않는다. exe 빌드가 남긴 `apps/api/public` 의 옛 화면이 뜬다.
