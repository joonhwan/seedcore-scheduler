## 1. 배경과 목적

고객사는 퇴사자와 잘못 만든 계정이 사용자 목록에 계속 쌓이는 것을 정리하고 싶어 한다. 회신에서
**두 방식을 모두 요청**했다. 활동 기록이 없는 계정은 흔적 없이 지우고, 활동이 있는 계정은 목록에서
감추되 과거 기록은 남기는 방식이다.

두 방식이 필요한 이유는 명확하다. 시험 삼아 만든 계정이나 오타로 잘못 만든 계정을 목록에 영구히
남겨 둘 이유가 없다. 반대로 실제로 일하던 사람의 계정을 지우면 그 사람이 만든 일정과 댓글의
작성자를 알 수 없게 되어 감사 추적이 끊긴다.

이 작업은 **2차(사용자 그룹·인원별 권한)와 하나의 배포로 묶기로 확정되어 있다**(확정명세 §9).
같은 화면(관리자 모드의 사용자 관리 영역)을 건드리고, 퇴사자가 그룹 추가 대상에서 빠져야 하므로
그룹 기능을 전제로 하며, 데이터베이스 변경을 한 번의 배포로 적용할 수 있기 때문이다.

---

## 2. 범위

### 이 설계가 다루는 것

- 활동 기록이 없는 계정의 완전 삭제 (판정·안내·확인·감사 기록)
- 퇴사 처리와 복직 (로그인 차단, 세션 즉시 종료, 목록에서 감추기)
- 사용자 관리 목록의 "퇴사자 포함" 보기
- 사용자 상세 화면의 "계정 정리" 섹션

### 이 설계가 다루지 않는 것

- **데이터베이스 스키마 변경.** `users.retired_at` 은 2차 마이그레이션
  (`20260903010359_user_groups_and_retired_at`)에 이미 들어가 있고 운영에도 적용되었다. 이번 작업에
  마이그레이션은 없다.
- **비활성(`is_active`) 기능 자체의 변경.** 일시적 접속 차단이라는 기존 뜻을 그대로 둔다.
- **프로젝트 멤버 목록·그룹 인원 목록에 퇴사 배지를 붙이는 일.** 이유는 §8 에 적었다.
- **퇴사자의 데이터 이관(다른 사람에게 담당을 넘기는 기능).** 요청에 없다.

## 3. 확정된 결정 사항

브레인스토밍에서 사용자에게 물어 확정받았다. 확정명세에 없는 내용이므로 이 문서가 유일한 기록이다.

| 결정 사항 | 확정된 답 |
| --- | --- |
| 삭제할 때 그 사람의 감사로그 | **행위자(`actor_id`)만 비운다.** 감사로그 행 자체는 남는다 |
| 퇴사와 비활성의 관계 | **퇴사 처리하면 `is_active` 도 함께 내린다.** 두 상태를 독립으로 두지 않는다 |
| 퇴사자의 기존 그룹 소속·프로젝트 참여 | **둘 다 그대로 둔다.** 화면 표시와 집계에서만 구분한다 |
| 퇴사 배지를 붙일 범위 | **사용자 관리 목록과 사용자 상세 두 곳만.** 다른 목록은 기존 "비활성" 표시로 갈음한다 |

### 결정의 근거

**감사로그를 활동으로 치지 않는 이유.** 계정을 만들어 한 번 로그인하기만 해도 `LOGIN_SUCCESS` 가
남는다. 이것을 활동으로 세면 지울 수 있는 계정이 사실상 없어져, "잘못 만든 계정을 정리한다"는 요청
취지를 절반만 채우게 된다. `audit_logs.actor_id` 는 비어 있을 수 있는 컬럼이라 행을 남긴 채 행위자만
끊을 수 있다. "2026-09-01 10:00 에 로그인이 있었다"는 사실은 남고 누구였는지만 사라진다. 삭제
사실 자체는 관리자를 행위자로 하는 `USER_DELETE` 로 따로 남으므로 추적이 끊기지 않는다.

**퇴사할 때 비활성을 함께 내리는 이유.** `is_active` 를 보고 사람을 걸러내는 자리가 서버에 열다섯
군데 있다. 로그인 거부, 세션 검증, 프로젝트 참여자 후보, 그룹 인원 추가, 멤버 일괄 추가가 모두
그 값 하나에 걸려 있다. 두 상태를 독립으로 두면 그 열다섯 군데의 조건을 모두 "비활성이거나 퇴사"로
고쳐야 하고, **한 군데를 빠뜨리면 퇴사자가 참여자 후보에 뜨는 사고**가 난다. 함께 내리면 기존 코드가
그대로 퇴사자를 막으므로 빠뜨림이 구조적으로 불가능하다. 대신 퇴사 직전의 활성 여부를 감사로그
payload 에 `wasActive` 로 남겨, 원래 비활성이던 사람이었는지 나중에 알 수 있게 한다.

**소속과 참여를 그대로 두는 이유.** 복직이 요구사항이므로(확정명세 §6-나) 소속을 지우면 되돌릴 수
없다. 또 2차가 이미 비활성 사용자를 그룹에 남기고 표시만 구분하는 방식을 택했으므로
(`groups.service.ts` 가 인원 목록에 `isActive` 를 함께 내려준다) 같은 방식이 일관된다.

## 4. 상태 모델

상태는 셋이며, 두 컬럼의 조합으로 표현한다.

| 상태 | `retired_at` | `is_active` | 뜻 |
| --- | --- | --- | --- |
| 재직·활성 | `NULL` | `true` | 정상 |
| 재직·비활성 | `NULL` | `false` | 일시적 접속 차단 (기존 기능) |
| 퇴사 | 시각 | `false` | 조직을 떠남 |

**`retired_at` 이 채워졌는데 `is_active = true` 인 조합은 만들지 않는다.** 퇴사 처리와 복직 두 경로가
항상 두 컬럼을 함께 바꾸며, 사용자 관리 목록의 활성·비활성 토글 버튼은 퇴사자 행에서 감춘다
(§7.1). 퇴사자의 상태를 바꾸는 길은 상세 화면의 복직 하나로 모은다.

### 상태 전이

```
재직·활성   ──[퇴사 처리]──>  퇴사       retired_at = now, is_active = false, 세션 전부 종료
재직·비활성 ──[퇴사 처리]──>  퇴사       (같음. wasActive = false 로 기록)
퇴사        ──[복직 처리]──>  재직·활성  retired_at = NULL, is_active = true
```

복직은 항상 활성으로 되돌린다. 퇴사 전에 비활성이던 사람이라면 관리자가 복직 후 다시 비활성으로
내리면 된다. 드문 경우를 위해 전이를 복잡하게 만들지 않는다.

## 5. 삭제 가능 판정

### 5.1 세는 것은 아홉 갈래다

확정명세 §6-가는 "프로젝트 참여, 일정 생성·수정, 댓글, 변경 이력이 모두 0건"이라고 적었다. 그러나
`users` 행을 실제로 지우려면 **`User` 를 참조하는 관계 열한 개가 모두 비어 있어야 한다.** 명세가
말하지 않은 두 갈래(감사로그, 남을 추가한 기록)를 여기서 확정한다.

| # | 관계 | 참조 컬럼 | 삭제할 때 |
| --- | --- | --- | --- |
| 1 | `createdProjects` | `projects.created_by` | 0건이어야 한다 |
| 2 | `projectMemberships` | `project_members.user_id` | 0건이어야 한다 |
| 3 | `membershipsAdded` | `project_members.added_by` | 0건이어야 한다 |
| 4 | `nodesCreated` | `schedule_nodes.created_by` | 0건이어야 한다 |
| 5 | `nodesUpdated` | `schedule_nodes.updated_by` | 0건이어야 한다 |
| 6 | `comments` | `node_comments.author_id` | 0건이어야 한다 |
| 7 | `history` | `node_history.actor_id` | 0건이어야 한다 |
| 8 | `groupMemberships` | `user_group_members.user_id` | 0건이어야 한다 |
| 9 | `groupMembersAdded` | `user_group_members.added_by` | 0건이어야 한다 |
| — | `sessions` | `sessions.user_id` | **함께 지워진다** (`onDelete: Cascade`) |
| — | `auditLogs` | `audit_logs.actor_id` | **행위자만 비운다** (§3 의 결정) |

3·9 번(남을 프로젝트나 그룹에 넣은 기록)은 필수 컬럼이라 비울 수 없다. 그래서 남을 관리한 적이 있는
계정은 활동이 없어 보여도 지울 수 없다. 관리자 계정이 대개 여기 걸린다.

### 5.2 화면에는 둘로 나누어 보여준다

아홉 갈래를 그대로 나열하면 관리자가 무엇을 해야 할지 알 수 없다. 성격에 따라 나눈다.

| 구분 | 포함되는 것 | 관리자가 할 수 있는 일 |
| --- | --- | --- |
| **정리하면 없어지는 것** | 2 (프로젝트 참여), 8 (그룹 소속) | 상세 화면의 위 섹션에서 빼면 0건이 되어 삭제할 수 있게 된다 |
| **지울 수 없는 것** | 1, 3, 4, 5, 6, 7, 9 | 영구히 삭제할 수 없다. 퇴사 처리를 쓴다 |

이 구분 덕분에 확정명세의 안내 문구("…기록이 있어 삭제할 수 없습니다. 퇴사 처리를 이용하십시오")가
한 걸음 더 나아가, **관리자가 무엇을 하면 지울 수 있는지**까지 알려 준다.

### 5.3 판정은 서버가 두 번 한다

화면이 집계를 보고 삭제 버튼을 띄우지만, **`DELETE` 요청을 받은 서버가 집계를 다시 세어 확인한 뒤**
지운다. 화면이 집계를 읽은 뒤 삭제를 누르기까지 사이에 그 사람이 프로젝트에 추가될 수 있기
때문이다. 다시 센 결과 활동이 있으면 `USER_HAS_ACTIVITY` 로 거부한다.

## 6. 서버 API

모두 `/api/v1/admin/users` 아래에 두며, 기존 `UsersController` 에 붙인다. 컨트롤러에 이미
`@UseGuards(OriginGuard)` 와 `@AdminOnly()` 가 클래스 단위로 붙어 있어 새 라우트가 그대로 상속받는다.

| 메서드 | 경로 | 하는 일 | 응답 |
| --- | --- | --- | --- |
| `GET` | `/:id/activity` | 아홉 갈래 집계와 삭제 가능 여부 | `UserActivitySummary` |
| `POST` | `/:id/retire` | 퇴사 처리 + 세션 종료 | `UserListItem` |
| `POST` | `/:id/unretire` | 복직 | `UserListItem` |
| `DELETE` | `/:id` | 완전 삭제 | `204 No Content` |

**집계 조회와 삭제는 재직 여부와 무관하게 동작한다.** 퇴사자도 활동이 0건이면 지울 수 있어야 하기
때문이다(§7.2 의 퇴사자 화면에도 삭제 버튼이 있다).

### 6.1 집계 응답 (`UserActivitySummary`)

```ts
{
  canDelete: boolean;          // 아홉 갈래가 모두 0 인가
  clearable: {                 // 정리하면 없어지는 것
    projectMemberships: number;
    groupMemberships: number;
  };
  permanent: {                 // 지울 수 없는 것
    createdProjects: number;
    nodesCreated: number;
    nodesUpdated: number;
    comments: number;
    history: number;
    membershipsAdded: number;
    groupMembersAdded: number;
  };
}
```

화면이 문구를 만들 수 있도록 **합계가 아니라 항목별 건수를 그대로 내린다.** 합계만 내리면 "일정 47건을
수정하고 댓글 5건을 남긴" 같은 안내를 만들 수 없다.

### 6.2 목록 조회의 확장

기존 `GET /admin/users` 의 `status`(`active` / `inactive` / `all`)를 그대로 두고
**`includeRetired` 파라미터를 따로 받는다.** 재직 여부와 활성 여부는 독립한 축이기 때문이다.

- 기본값(파라미터 없음): `retired_at IS NULL` 인 사람만 — 확정명세 §6-나의 "목록 기본 화면에서 사라진다"
- `includeRetired=1`: 퇴사자까지 전부

쿼리 파라미터는 항상 문자열로 들어오므로 **`'1'` 일 때만 참으로 본다.** 기존 `status` 를 다루는 방식과
같게 컨트롤러에서 해석하고, 서비스에는 `boolean` 으로 넘긴다.

`UserListItem` 에 `retiredAt: string | null` 을 더한다.

### 6.3 거부 규칙

| 상황 | 오류 코드 | 적용되는 곳 |
| --- | --- | --- |
| 자기 자신을 퇴사·삭제 | `SELF_ACTION_FORBIDDEN` | retire, delete |
| 활성 ADMIN 이 자기 혼자인데 퇴사 | `LAST_ACTIVE_ADMIN` (기존 재사용) | retire |
| 이미 퇴사한 사람을 다시 퇴사 | `ALREADY_RETIRED` | retire |
| 재직 중인 사람을 복직 | `NOT_RETIRED` | unretire |
| 활동이 한 건이라도 있는데 삭제 | `USER_HAS_ACTIVITY` | delete |
| 없는 사용자 | `USER_NOT_FOUND` (기존) | 전부 |

**퇴사에는 `LAST_ACTIVE_ADMIN` 을 적용하지만 삭제에는 적용하지 않는다.** 활성 ADMIN 이 자기 혼자인
상황에서 그 계정은 남을 관리한 기록(`membershipsAdded` 등)이 반드시 있으므로 `USER_HAS_ACTIVITY` 에
먼저 걸린다. 규칙을 중복해서 두지 않는다.

### 6.4 삭제의 실행 순서

한 트랜잭션 안에서 처리한다.

1. 아홉 갈래를 다시 센다. 하나라도 0이 아니면 `USER_HAS_ACTIVITY` 로 중단한다
2. `audit_logs` 에서 그 사람이 행위자인 행의 `actor_id` 를 `NULL` 로 바꾼다
3. `users` 행을 지운다 (`sessions` 는 Cascade 로 함께 사라진다)
4. 트랜잭션이 커밋된 뒤에 `USER_DELETE` 감사로그를 남긴다 — 행위자는 **삭제를 실행한 관리자**이고,
   payload 에 지운 계정의 `username` 과 `displayName` 을 담는다

4 번을 트랜잭션 밖에 두는 이유는 2·3 이 실패했을 때 감사로그만 남는 것을 막기 위함이다. 순서를
이렇게 두면 삭제가 실제로 끝난 경우에만 기록된다.

### 6.5 감사 액션 세 개를 더한다

| 액션 | 언제 | payload |
| --- | --- | --- |
| `USER_RETIRE` | 퇴사 처리 | `{ wasActive, sessionsKilled }` |
| `USER_UNRETIRE` | 복직 | 없음 |
| `USER_DELETE` | 완전 삭제 | `{ username, displayName }` |

## 7. 화면 설계

### 7.1 사용자 관리 목록 (`AdminUsersPage`)

- 상태 드롭다운 옆에 **"퇴사자 포함" 체크상자**를 둔다. 켜면 `includeRetired=1` 로 조회한다
- 퇴사자 행에 **"퇴사" 배지**를 붙인다. 기존 "비활성" 배지와 색으로 구별한다
- **퇴사자 행에서는 활성·비활성 토글 버튼을 감춘다.** 퇴사자를 활성으로 되돌리면 §4 가 금지한
  조합이 만들어진다. 상태를 바꾸려면 상세 화면의 복직을 쓰게 한다
- 이름 클릭으로 상세로 가는 기존 동작은 그대로 둔다

### 7.2 사용자 상세 (`AdminUserDetailPage`)

## 8. 다른 화면에 미치는 영향

**서버 코드를 고칠 곳이 없다.** 퇴사자는 항상 `is_active = false` 이므로, 비활성을 걸러내는 기존
코드가 그대로 퇴사자를 막는다. §3 에서 두 상태를 함께 내리기로 한 결정이 여기서 값을 한다.

| 자리 | 파일 | 퇴사자가 막히는 이유 |
| --- | --- | --- |
| 로그인 | `auth.service.ts:123` | `!user.isActive` 로 거부 |
| 세션 검증 | `sessions.service.ts:70` | `!session.user.isActive` 로 무효 |
| 프로젝트 참여자 후보 | `projects.service.ts:162, 180, 420` | `where: { isActive: true }` |
| 멤버 추가·일괄 추가 | `members.service.ts:78, 154` | 같음 |
| 그룹 인원 추가 | `groups.service.ts:271~278` | 비활성을 따로 세어 안내 |
| 사용자 기준 권한 | `user-projects.service.ts:95` | `USER_INACTIVE` 로 거부 |

### 퇴사 배지를 두 곳에만 붙이는 이유

이미 참여 중인 사람이 나오는 목록(프로젝트 멤버 관리, 그룹 인원)에는 퇴사자가 계속 보인다. 여기에는
퇴사 배지를 붙이지 않고 **기존 "비활성" 표시로 갈음한다.**

- 퇴사자는 반드시 비활성이므로 경고 역할은 이미 하고 있다
- 배지를 붙이려면 2차에서 소속 정보를 더했던 것처럼 `ProjectMemberItem` 등 API 응답 타입 여러 개를
  다시 고쳐야 하는데, 얻는 것이 그만큼 크지 않다
- 필요해지면 나중에 필드 하나를 더하는 작은 작업으로 붙일 수 있다

## 9. 검증 계획

### 9.1 서버 규칙 (Prisma 대역으로 단위 시험)

`users.service.test.ts` 를 새로 만들고 다음을 고정한다.

- 거부 규칙 여섯 (§6.3 의 표)
- 집계가 아홉 갈래를 정확히 세는가. 특히 `membershipsAdded` 와 `groupMembersAdded` 처럼 **남을 추가한
  기록**을 빠뜨리지 않는가
- 퇴사 처리가 `retired_at` 과 `is_active` 를 **함께** 바꾸고 세션을 끊는가
- 복직이 둘을 함께 되돌리는가
- 삭제가 감사로그의 `actor_id` 를 `NULL` 로 바꾼 뒤 행을 지우는가
- 삭제 직전에 집계를 다시 세는가 (§5.3)

### 9.2 목록 조회

- `includeRetired` 가 없으면 퇴사자가 나오지 않는가
- `includeRetired=1` 이면 나오는가
- `status=inactive` 와 조합했을 때 두 축이 각각 걸리는가

### 9.3 전체 검사

`pnpm -r typecheck` 와 `pnpm -r test` 를 돌린다.

### 9.4 화면 확인 (직접 조작)

**이번에는 시험용 계정을 만들어 실제로 지워 볼 수 있다.** 2차의 화면 확인에서는 "새 사용자를 만들지
말 것"이 방침이었는데(지울 방법이 없었다), 이 작업이 바로 그 방법을 만든다.

1. 시험 계정을 만들고 아무 활동 없이 삭제 → 목록에서 사라지는가
2. 그 계정으로 로그인만 한 뒤 삭제 → **감사로그가 있어도 지워지는가** (§3 의 결정이 실제로 동작하는가)
3. 지운 뒤 `audit_logs` 의 그 행이 남아 있고 `actor_id` 만 비었는가
4. 시험 계정을 프로젝트에 넣은 뒤 → 삭제 버튼이 사라지고 "정리하면 삭제할 수 있다" 안내가 뜨는가
5. 프로젝트에서 빼면 → 삭제 버튼이 다시 나타나는가
6. 일정을 하나 만들게 한 뒤 → "지울 수 없다" 안내로 바뀌는가
7. 퇴사 처리 → 목록에서 사라지고, "퇴사자 포함" 을 켜면 배지와 함께 나타나는가
8. 퇴사자로 로그인 시도 → 막히는가. 접속 중이던 세션이 끊겼는가
9. 퇴사자가 프로젝트 참여자 후보와 그룹 인원 후보에서 빠졌는가
10. 퇴사자의 그룹 소속과 참여 프로젝트가 그대로 남아 있는가
11. 복직 → 활성으로 돌아오고 후보 목록에 다시 나타나는가
12. 자기 자신을 퇴사·삭제하려 하면 거부되는가

### 9.5 배포판 예행 연습

**이번 작업에는 마이그레이션이 없으므로 2차 계획의 Task 13 과 같은 예행 연습을 다시 할 필요는 없다.**
