## 1. 배경

그룹 기능을 만들고 나니 두 가지가 부족했다.

**하나는 소속을 볼 수 없다는 것이다.** 그룹을 만들어 놓았는데 사용자 목록 어디에도 "이 사람이 어느 그룹인지" 가 나오지 않는다. 사용자 상세 화면(`/admin/users/:id`)만 소속 경로를 보여 주는데, 목록에서 한 명씩 상세로 들어가야 알 수 있으니 그룹을 만든 효과가 반감된다. 특히 프로젝트 멤버 관리 화면에서 "이 사람이 어느 팀 사람인지" 는 관리자가 가장 자주 알고 싶어 하는 것이다.

**다른 하나는 그룹을 일부만 고를 수 없다는 것이다.** 지금은 상위 그룹을 체크하면 자손 인원이 전부 따라오고, 하위 하나를 빼는 방법이 없다. 화면상 하위 그룹의 체크박스가 켜지지도 않아, 상위를 체크했을 때 무엇이 담기는지 눈으로 확인할 수도 없다.

## 2. 확정된 결정 사항

브레인스토밍에서 사용자에게 확인받았다.

| 결정 사항                                | 확정된 답                                                                              |
| ---------------------------------------- | -------------------------------------------------------------------------------------- |
| 프로젝트 현재 멤버 목록의 그룹 조회 경로 | **멤버 목록 API 가 소속을 함께 내려준다.** 그룹 조회 API 는 ADMIN 전용으로 그대로 둔다 |
| 목록의 표시 형식                         | **말단 그룹 이름만 배지로 보이고, 마우스오버에 경로 전진을 담는다**                    |
| 반쯤 체크된 상위 그룹의 직속 인원        | **포함한다.** 상위를 체크하면 상위 자신도 선택되므로 자연히 그렇게 된다                |

## 3. 왜 멤버 API 가 소속을 내려주는가

화면마다 사용자 목록의 출처와 접근 가능한 사람이 다르다. 코드를 훑어 정리한 결과가 다음과 같다.

| 화면                        | 사용자 목록의 출처          | 접근 가능한 사람    | 그룹 조회에 결정이 필요한가 |
| --------------------------- | --------------------------- | ------------------- | --------------------------- |
| 사용자 관리 목록            | `GET /admin/users`          | ADMIN               | 아니오                      |
| 프로젝트 **현재 멤버** 목록 | `GET /projects/:id/members` | 프로젝트 멤버 전원  | **예**                      |
| 프로젝트 **추가 후보** 목록 | `GET /admin/users`          | 사실상 ADMIN        | 아니오                      |
| 명단 편집기(생성·복제)      | `GET /admin/users`          | ADMIN + 관리자 모드 | 아니오                      |
| 사용자 상세                 | 이미 소속 경로를 보여준다   | ADMIN + 관리자 모드 | 이미 됨                     |

**결정이 필요한 곳은 "프로젝트 현재 멤버 목록" 하나뿐이다.** 나머지는 모두 `GET /admin/users` 를 쓰는데 그것이 이미 `@AdminOnly()` 이므로, 같은 ADMIN 전용인 `GET /admin/groups` 를 함께 불러도 접근 권한이 새로 필요하지 않다.

그 하나를 위해 **그룹 조회를 로그인 사용자 전체에게 여는 것은 과하다고 보았다.** 그룹 조회는 조직 전체의 계층과 소속을 한 번에 돌려주므로, 프로젝트 멤버 화면이 필요한 것(그 프로젝트 멤버들의 소속)보다 훨씬 많은 정보를 준다. 필요한 것만 정확히 내려주는 편이 권한 경계를 좁게 유지한다.

### 함께 발견한 기존 결함 (이 설계의 범위 밖)

`ProjectMembersPage` 의 멤버 추가 영역은 `canManage`(MANAGER 또는 ADMIN + 관리자 모드)일 때 열리는데, 후보 검색이 `@AdminOnly()` 인 `GET /admin/users` 를 부른다. **즉 일반 MANAGER 는 지금도 후보 목록을 받지 못해 그 자리에 "권한이 없습니다." 가 뜬다.** 이 브랜치가 만든 것이 아니라 원래 있던 결함이며, 이 설계에서는 다루지 않는다. 별건으로 다룰 때 이 문서의 §3 표를 참고하면 된다.

## 4. 요청 1 — 사용자 목록의 소속 그룹 표시

### 4.1 공유 순수 함수

`packages/shared/src/user-groups.ts` 에 하나를 더한다.

```typescript
/**
 * 한 사용자의 소속 그룹 경로를 최상위부터 돌려준다. 소속이 없으면 빈 배열.
 *
 * 운영은 1인 1소속이지만 데이터베이스는 여러 소속을 허용한다. 그런 데이터가 들어오면
 * **말단 이름의 가나다순으로 첫 번째 하나만** 쓴다. 화면이 조용히 하나만 고르는 것보다
 * 여기에 규칙을 적어 두는 편이 낫다.
 */
export function groupPathOfUser<T extends GroupNode & { name: string }>(
  groups: T[],
  memberships: GroupMembership[],
  userId: string,
): string[];
```

내부에서는 그 사용자의 소속 그룹 id 들을 모아 각각 `groupPathNames` 로 경로를 만들고, 말단 이름 기준으로 정렬해 첫 번째를 돌려준다. `groupPathNames` 를 재사용하므로 경로를 만드는 규칙이 한 곳에만 있다.

**서버와 화면이 이 함수를 함께 쓴다.** 서버가 내려준 경로와 화면이 계산한 경로가 같은 코드에서 나와야 두 화면의 배지가 어긋나지 않는다.

### 4.2 서버

`ProjectMemberItem` 에 필드 둘을 더한다.

```typescript
export const ProjectMemberItem = z.object({
  userId: z.string(),
  username: z.string(),
  displayName: z.string(),
  role: ProjectRole,
  addedAt: z.string(),
  /** 말단 소속 그룹 이름. 소속이 없으면 null. 목록의 배지에 쓴다. */
  groupName: z.string().nullable(),
  /** 최상위부터의 경로. 마우스오버 표시에 쓴다. 소속이 없으면 빈 배열. */
  groupPath: z.array(z.string()),
});
```

`MembersService.list()` 가 질의 둘을 더해 채운다.

- `userGroupMember.findMany({ where: { userId: { in: 멤버들의 id } } })` — 소속
- `userGroup.findMany()` — 경로를 만들기 위한 전체 그룹

그룹은 수십 개, 멤버는 프로젝트당 수십 명 규모라 질의 둘을 더하는 부담이 없다. 경로는 `groupPathOfUser` 로 만들고, `groupName` 은 그 경로의 마지막 원소다.

**`ProjectMemberItem` 을 돌려주는 메서드가 셋이므로 모두 채워야 한다.** `list()`·`add()`·`updateRole()` 이다. 한 곳만 채우면 추가나 역할 변경 직후의 화면과 새로고침 뒤의 화면이 달라진다. (`addBulk()` 는 `BulkAddMembersResult` 를 돌려주므로 해당하지 않는다.)

세 곳이 같은 계산을 하게 되므로 `MembersService` 안에 private 도우미 하나를 두어 재사용한다. `add()` 와 `updateRole()` 은 한 사람만 다루므로 그 사람의 소속만 읽으면 된다.

### 4.3 공용 배지 컴포넌트

```
apps/web/src/components/UserGroupBadge.tsx    props: { path: string[] }
```

경로가 비어 있으면 아무것도 그리지 않는다. 있으면 **말단 이름만** 배지로 보이고 `title` 에 `path.join(' › ')` 를 담는다. 배지 모양은 `AdminUsersPage` 의 기존 배지(ADMIN·비활성 등)와 같은 Tailwind 구성을 쓴다.

### 4.4 붙는 자리 다섯

| 자리                                        | 소속을 어디서 얻는가                       |
| ------------------------------------------- | ------------------------------------------ |
| `ProjectMembersPage` 의 현재 멤버 행        | 새로 더한 `ProjectMemberItem.groupPath`    |
| `ProjectMembersPage` 의 멤버 추가 후보 목록 | `useGroupTree(canUseGroups)` + `groupPathOfUser` |
| `AdminUsersPage` 의 사용자 행               | `useGroupTree()` + `groupPathOfUser`       |
| `MemberDraftEditor` 의 후보 검색 목록       | `useGroupTree()` + `groupPathOfUser`       |
| `MemberDraftEditor` 의 명단 목록            | 같음                                       |

`ProjectMembersPage` 의 후보 목록은 처음 이 절을 쓸 때 빠뜨렸다가 최종 검토에서 되찾은 자리다. 같은 화면의 위쪽 멤버 행에는 배지가 뜨는데 바로 아래 후보 목록에만 뜨지 않으면 한 화면 안에서 표시 규칙이 어긋나므로, 3 장 표가 그 자리를 세었던 대로 함께 붙인다. 그룹 조회가 ADMIN 전용이라 이 자리만 `canUseGroups` 로 조회를 막는다.

`ProjectNewPage` 와 `ProjectClonePage` 는 명단 편집기를 쓰므로 자동으로 함께 적용된다.

`AdminUsersPage` 는 관리자 모드를 요구하지 않는데 `GET /admin/groups` 는 `@AdminOnly()` 뿐이므로 호출에 문제가 없다. `MemberDraftEditor` 가 쓰이는 두 화면은 ADMIN + 관리자 모드를 요구하므로 역시 문제가 없다.

**`useGroupTree()` 가 실패하거나 아직 도착하지 않은 경우에는 배지를 그리지 않는다.** 그룹은 곁다리 정보이므로, 그것을 못 받았다고 사용자 목록 자체가 오류로 보이면 안 된다.

## 5. 요청 2 — 그룹 선택의 반쯤 체크 상태

### 5.1 상태를 담는 방식

`GroupPickerDialog` 의 `picked` 는 **명시적으로 체크된 그룹 id 의 집합**이고, 화면에 보이는 세 상태는 거기서 계산한다.

| 조작                      | 결과                                           |
| ------------------------- | ---------------------------------------------- |
| 체크                      | 자기 자신과 **모든 자손**을 `picked` 에 넣는다 |
| 해제                      | 자기 자신과 **모든 자손**을 `picked` 에서 뺀다 |
| **반쯤 체크된 것을 클릭** | 체크와 같다. 자기 자신과 모든 자손을 넣는다    |

자손을 모으는 데는 이미 있는 `collectDescendantGroupIds` 를 쓴다.

### 5.2 표시 상태 판정 (공유 순수 함수)

```typescript
export type GroupCheckState = 'checked' | 'indeterminate' | 'unchecked';

/**
 * 트리 체크박스의 세 상태를 판정한다.
 *
 *  - picked 에 있고 모든 자손도 picked 에 있으면 checked
 *  - picked 에 있으나 빠진 자손이 있으면 indeterminate
 *  - picked 에 없으나 자손 중 하나라도 있으면 indeterminate
 *  - 아무것도 없으면 unchecked
 */
export function groupCheckState(
  groups: GroupNode[],
  picked: ReadonlySet<string>,
  groupId: string,
): GroupCheckState;
```

### 5.3 담기는 인원이 달라진다

**체크된 그룹들의 직속 인원 합집합**을 담는다.

```typescript
/**
 * 주어진 그룹들에 **직접** 속한 사용자 id 를 중복 없이 돌려준다. 자손을 따라가지 않는다.
 *
 * expandGroupMembers 와 달리 자손을 자동으로 포함하지 않는 이유는, 화면이 상위를 체크할 때
 * 자손도 명시적으로 체크하기 때문이다. 이중으로 셀 필요가 없고, 무엇보다 **하위를 일부러
 * 풀었을 때 그 뜻이 그대로 반영되어야** 한다.
 */
export function directMembersOf(
  memberships: GroupMembership[],
  groupIds: readonly string[],
): string[];
```

반환 순서는 `expandGroupMembers` 와 같이 `memberships` 에 들어 있던 순서를 따른다. 화면 표시 순서를 안정적으로 두기 위함이다.

**반쯤 체크된 상위 그룹의 직속 인원은 포함된다.** 운영기술센터를 체크한 뒤 기구완성팀만 풀면 센터장은 들어오고 기구완성팀원은 들어오지 않는다. 상위를 체크할 때 상위 자신도 `picked` 에 들어가므로 별도 처리 없이 그렇게 된다.

### 5.4 기존 약속과 어긋나지 않는지 확인한 것

- **선행 설계 §5 의 약속("미리보기 숫자와 실제로 담기는 인원이 같은 함수에서 나온다")은 유지된다.** 쓰는 함수가 `expandGroupMembers` 에서 `directMembersOf` 로 바뀔 뿐, 미리보기와 `onPick` 이 같은 것을 쓴다.
- **서버는 영향을 받지 않는다.** 서버는 그룹 id 를 받지 않는다(선행 설계 §8.3 이 "서버가 그룹 id 를 받아 인원을 펼침" 대안을 이미 버렸다). `expandGroupMembers` 는 그룹 목록의 누계 인원수(`GroupsService.tree`)와 집계 조회(`projectCoverage`)에서 계속 쓰이며, **그 두 곳에서는 자손 포함이 옳다.**
- **확정명세 §2-나("상위 그룹을 고르면 하위 그룹 인원까지 함께 들어옵니다")도 그대로다.** 상위를 체크하면 하위가 자동으로 체크되므로 결과가 같고, 이제 일부만 고르는 것이 추가로 가능해진다.

### 5.5 비활성 사용자 처리는 그대로 둔다

지금 `GroupPickerDialog` 는 활성 사용자와의 교집합을 내서 미리보기 숫자와 `onPick` 값을 같게 맞추고, 걸러진 인원이 있으면 "비활성 사용자 N명은 제외됩니다" 를 알린다. **그 구조를 그대로 유지하고 `expandGroupMembers` 자리에만 `directMembersOf` 를 넣는다.**

### 5.6 구현상 주의할 점

**HTML 체크박스의 `indeterminate` 는 JSX 어트리뷰트가 없고 DOM 프로퍼티로만 있다.** `ref` 로 설정해야 한다.

```tsx
<input
  type="checkbox"
  checked={state === 'checked'}
  // indeterminate 는 어트리뷰트가 아니라 DOM 프로퍼티라 ref 로만 설정할 수 있다.
  ref={(el) => {
    if (el) el.indeterminate = state === 'indeterminate';
  }}
  onChange={() => onToggle(group.id)}
/>
```

`onToggle` 은 현재 상태를 다시 판정해 처리한다. `unchecked` 와 `indeterminate` 는 모두 "넣기", `checked` 만 "빼기" 다.

## 6. 검증 계획

이 저장소의 기존 방식을 따른다. 순수 로직은 `vitest` 로 검사하고, 서비스는 Prisma 를 좁은 대역으로 바꿔치기한다. **웹에는 React 컴포넌트 시험 환경이 없으므로**(`apps/web/vitest.config.ts` 가 `environment: 'node'`) 화면은 타입 검사·번들 빌드·직접 조작으로 확인한다.

### 6.1 순수 로직 (테스트를 먼저 쓴다)

| 함수              | 검사할 분기                                                                                                             |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `groupPathOfUser` | 소속 없음(빈 배열), 말단 팀 소속(경로 전체), 최상위 직속(한 원소), 두 그룹에 걸친 데이터(가나다순 첫 번째), 없는 사용자 |
| `groupCheckState` | 네 가지 상태 각각, 잎 그룹(자손 없음), 자손이 여럿일 때 하나만 빠진 경우, 순환 데이터에서도 멈추는지                    |
| `directMembersOf` | 자손을 따라가지 않는지, 여러 그룹의 합집합에서 중복 제거, 빈 목록, 없는 그룹 id                                         |

**`directMembersOf` 가 자손을 따라가지 않는다는 것을 명시적으로 검사해야 한다.** `expandGroupMembers` 와 헷갈려 자손을 포함하게 고치면 §5.3 의 요구가 조용히 깨진다.

### 6.2 서버 규칙 (Prisma 대역)

- `MembersService.list()` 가 소속이 있는 멤버에게 경로를, 없는 멤버에게 `null`·빈 배열을 채우는지
- `add` 와 `addBulk` 의 반환값에도 같은 값이 채워지는지
- 소속이 여러 개인 데이터에서 가나다순 첫 번째를 고르는지

### 6.3 전체 검사

`pnpm -r typecheck`, `pnpm -r test`, `pnpm -F @sam/web build` 를 돌린다. 마지막 것을 반드시 포함하는 이유는, 이 저장소에서 `packages/shared` 에 새 export 를 추가하면 타입 검사와 시험은 통과하는데 번들링에서만 깨지는 일이 있기 때문이다.
