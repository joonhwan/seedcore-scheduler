# 프로젝트 중요도(우선순위)와 목록 인플레이스 편집 — 설계

- 작성일: 2026-09-14
- 상태: 승인됨 (2026-09-14)
- 범위: `packages/shared`, `apps/api`(스키마 변경 포함), `apps/web`

---

## 1. 배경

### 1.1 요청

고객이 프로젝트 목록 화면에 대해 이렇게 문의했다.

> 자꾸 순서가 바뀌는게 불편함. 나에게 있어서 중요도(미리 지정?) 있는 걸 위로 가게...
> 혹은 수동으로 순서를 위아래 드래그해서 변경하는 방식으로 조회할 수 있는가.

이어진 확인에서 중요도의 성격이 정해졌다. **개인의 화면 설정이 아니라 조직이 공유하는
프로젝트의 속성이다.** 팀장이나 관리자가 그때그때 조정하며, 여러 프로젝트에 걸쳐 있는
멤버가 **지금 무엇을 먼저 진행해야 하는지 인지하도록 만드는 소통 수단**이다.

### 1.2 "순서가 바뀐다"의 정체

목록의 기본 정렬은 최근 수정순이고, 그 "수정"에는 일정 변경이 들어간다
(`projectLastModifiedAt()`, `packages/shared`). 그래서 **남이 자기 프로젝트의 일정을
하나만 고쳐도 내가 보던 프로젝트가 한 칸씩 밀려 내려간다.**

이 정렬은 2026-09 고객 요청 5번에 따라 넣은 것이다. 다만 그 원문은
"가장 최근에 업데이트된 순서로 자동 정렬해서 보여준다던가, **혹은** … 로그창"이라는
**두 방안의 제시**였고, 우리가 앞의 것을 골랐다. 따라서 이번 문의는 이전 요청과
충돌하는 것이 아니라 같은 목적을 다른 방식으로 이루자는 요청이다.

### 1.3 이미 끝난 선행 작업

정렬 선택을 브라우저에 기억하는 기능은 커밋 `6c41854` 로 완결되었다. 사용자가 고른
정렬 기준이 `localStorage` 에 남아 다시 들어와도 유지된다. **이번 작업의 중요도 컬럼은
그 구조에 정렬 가능한 컬럼 하나를 더하는 형태로 얹힌다.**

## 2. 확정된 요구사항

1. 중요도는 **프로젝트의 속성**이며 모든 멤버에게 같은 값으로 보인다.
2. 값은 **부호 있는 정수**로 저장한다. 지정하지 않은 상태가 `0`, 최저가 `-3`, 최고가 `+3`.
   추후 단계를 넓힐 수 있어야 한다.
3. 중요도는 **목록의 컬럼 하나**이며, 컬럼 머리를 눌러 정렬할 수 있다.
4. **MANAGER 가 명칭·설명·중요도를 편집할 수 있다.** 보관·복제·삭제는 관리자 전용으로 남는다.
5. 편집은 **목록 화면을 벗어나지 않고 그 자리에서** 한다.
6. **ADMIN 은 "모든 프로젝트의 MANAGER"로 단순화한다.**
7. 누가 언제 명칭·설명·중요도를 바꿨는지 **기록만 남긴다.** 이력 조회 화면은 별도 작업으로 미룬다.

## 3. 데이터 모델

### 3.1 스키마 변경

`projects` 테이블에 컬럼 하나를 추가한다.

```prisma
model Project {
  // ... 기존 필드 그대로
  priority    Int      @default(0)
}
```

기존 행은 모두 `0`(보통)이 된다.

### 3.2 `CHECK` 제약을 걸지 않는 이유

`AGENTS.md` §4.3 은 SQLite 에 enum 이 없으므로 `CHECK` 로 값을 제한하라고 안내한다.
**이 컬럼에는 걸지 않는다.**

SQLite 는 제약을 바꾸려면 테이블을 통째로 다시 만들어야 하는데, **단계를 넓힐 계획이
이미 요구사항에 들어 있다.** 범위를 바꿀 때마다 무거운 마이그레이션을 치르게 된다.
값이 들어오는 경로는 API 하나뿐이고 Zod 가 막으므로, 범위 판단은 애플리케이션
계층에만 둔다.

### 3.3 인덱스

**추가하지 않는다.** 프로젝트는 최대 수십 건이고 정렬은 브라우저에서 이뤄진다.

## 4. 공유 스키마 (`packages/shared`)

**범위와 라벨을 이 패키지 한 곳에 둔다.** 나중에 단계를 넓힐 때 고칠 곳이 하나여야 하기
때문이다.

```ts
export const PROJECT_PRIORITY_MIN = -3;
export const PROJECT_PRIORITY_MAX = 3;

/** 저장값 → 화면에 보일 말. 숫자만으로는 높은 쪽인지 낮은 쪽인지 즉시 읽히지 않는다. */
export function projectPriorityLabel(value: number): string;

/** 드롭다운에 채울 선택지. 큰 값부터 늘어선다. */
export const PROJECT_PRIORITY_OPTIONS: readonly { value: number; label: string }[];
```

| 값 | 라벨 |
|---|---|
| +3 | 최우선 |
| +2 | 높음 |
| +1 | 다소 높음 |
| 0 | 보통 |
| -1 | 다소 낮음 |
| -2 | 낮음 |
| -3 | 최하 |

`projectPriorityLabel()` 은 **범위를 벗어난 값도 견뎌야 한다.** 나중에 범위를 넓혔다가
되돌리는 경우, 또는 DB 를 직접 고친 경우에 화면이 깨지면 안 된다. 표에 없는 값은
부호를 붙인 숫자를 그대로 돌려준다.

### 4.1 DTO 변경

```ts
export const UpdateProjectDto = z
  .object({
    name: z.string().min(1).max(128).optional(),
    description: z.string().max(2000).nullable().optional(),
    status: ProjectStatus.optional(),
    priority: z.number().int().min(PROJECT_PRIORITY_MIN).max(PROJECT_PRIORITY_MAX).optional(),
    expectedUpdatedAt: z.string(),
  })
  .refine(/* 네 필드 중 하나는 있어야 한다 */);
```

`ProjectListItem` 에 `priority: z.number().int()` 를 추가한다. **여기에는 범위 제한을 걸지
않는다.** 응답 스키마가 DB 의 현재 값을 거부하면 목록 전체가 뜨지 않기 때문이다.

> **주의**: `shared` 에 새 이름을 추가하므로, `pnpm dev` 가 아닌 방법으로 개발 서버를
> 띄운다면 `apps/web/node_modules/.vite` 를 지워야 한다 (`AGENTS.md` §5).

## 5. 권한

### 5.1 판단 규칙

**"그 프로젝트의 MANAGER 이거나, 관리자 모드의 ADMIN"** 한 갈래로 통일한다. ADMIN 을
모든 프로젝트의 MANAGER 로 보는 단순화가 이것을 가능하게 한다.

관리자 모드를 **켠 상태**의 ADMIN 만 해당한다는 점이 중요하다. `AGENTS.md` §4.4 가
"ADMIN 은 관리자 모드가 활성화된 상태에서만 모든 프로젝트에 대한 CRUD 및 가시성을
확보한다"고 정한 규칙을 그대로 따른다.

**이 규칙은 이미 코드에 있다.** 상세 화면(`ProjectDetailPage.tsx:228`)의

```ts
const canManageProject = myRole === 'MANAGER' || (isAdmin && adminMode);
```

가 정확히 같은 조건이다. 새 개념을 들이는 것이 아니라 **이미 쓰이는 판단을 프로젝트
속성 편집까지 넓히는 것이다.** 목록 화면에도 같은 이름으로 둔다.

### 5.2 필드마다 갈리는 권한

**이번 설계에서 가장 주의할 부분이다.** 한 API 안에서 필드에 따라 판단이 달라진다.

| 필드 | 고칠 수 있는 사람 |
|---|---|
| `name`, `description`, `priority` | 그 프로젝트의 MANAGER, 또는 관리자 모드의 ADMIN |
| `status`(보관·복원) | 관리자 모드의 ADMIN 만 |

MANAGER 가 `status` 를 함께 보내면 **요청 전체를 거부한다.** 일부만 반영하면 무엇이
적용되고 무엇이 무시됐는지 화면이 알 수 없다.

이 규칙은 `ProjectsService.update()` 한 곳에 함수로 모은다. 컨트롤러에 흩어 놓으면
필드가 늘 때마다 빠뜨리기 쉽다.

## 6. API

### 6.1 경로 이동

```
변경 전: PATCH /api/v1/admin/projects/:id   @AdminOnly()
변경 후: PATCH /api/v1/projects/:id         (가드는 §5 규칙)
```

MANAGER 가 쓰는 엔드포인트에 `admin` 이 남아 있으면 읽는 사람이 오해한다. 폐쇄망
단일 서버이고 호출자가 웹 클라이언트뿐이라 함께 고치면 끝난다.

**`OriginGuard` 는 그대로 유지된다.** 이 컨트롤러는 클래스 레벨에
`@UseGuards(OriginGuard)` 가 붙어 있어(`projects.controller.ts:33`) 라우트를 옮겨도
계속 적용된다 (`AGENTS.md` §4.4, 상태 변경 라우트 필수).

### 6.2 동시성

`expectedUpdatedAt` 검사는 지금 그대로 둔다. 인플레이스 편집이므로 목록이 들고 있는
`updatedAt` 을 그대로 보낸다.

**중요도를 바꾸면 `projects.updated_at` 이 갱신된다.** 이는 의도한 동작이며, 다음 두 가지
결과를 낳는다.

1. 기본 정렬(최근 수정순)로 보고 있으면 그 프로젝트가 위로 올라온다. 중요도 컬럼으로
   정렬 중이면 순서가 흔들리지 않는다.
2. 같은 프로젝트를 동시에 편집하던 다른 사람은 409 를 받는다. 프로젝트 하나를 둘이
   동시에 고치는 일이 드물고, 409 를 받으면 새로고침 후 다시 하면 된다.

> 일정 변경이 `projects.updated_at` 을 건드리지 않는 규칙(`AGENTS.md` §4.5)은 그대로다.
> 이번에 추가되는 것은 프로젝트 행 자체의 변경이므로 그 규칙에 어긋나지 않는다.

## 7. 감사로그

기존 `PROJECT_UPDATE` 액션을 그대로 쓰고 **payload 를 넓힌다.**

```jsonc
{
  "name":        { "before": "옛 이름", "after": "새 이름" },
  "description": { "before": null,      "after": "새 설명" },
  "priority":    { "before": 0,         "after": 2 }
}
```

바뀐 필드만 담는다.

### 7.1 이전 값을 남기는 이유

요청은 "누가 언제 무엇을 바꿨는지"였고 이전 값은 언급되지 않았다. 그래도 남긴다.
**기록하는 그 순간에만 알 수 있는 정보이고, 지금 담지 않으면 나중에 이력 화면을 만들 때
"보통에서 높음으로 올렸다"를 복원할 방법이 없기 때문이다.** 비용은 감사로그 한 줄에
필드 몇 개가 붙는 정도다.

### 7.2 관리자 모드 기록

`ctx.adminMode === true` 이면 `ADMIN_OVERRIDE_EDIT` 를 별도로 남기는 기존 동작을 유지한다
(`AGENTS.md` §4.4).

### 7.3 이번 범위 밖

**감사로그를 조회하는 API 도 화면도 만들지 않는다.** 현재 `/projects/:id/history` 는
`node_history` 를 읽어 일정 변경만 보여주며, `audit_logs` 를 볼 수단은 존재하지 않는다.
따라서 이번에 남기는 기록은 **당분간 DB 를 직접 열어야 볼 수 있다.** 이력 화면은 별도
작업으로 진행하기로 합의했다.

## 8. 웹 화면

### 8.1 중요도 컬럼

`DEFAULT_COLUMN_WIDTHS`(`lib/projectListColumns.ts`)에 `priority` 를 넣는다. 폭은 라벨 중
가장 긴 "다소 높음"이 잘리지 않을 만큼으로 잡는다.

**색은 양수에만 준다.** 일곱 값 모두에 색을 주면 목록이 알록달록해져 오히려 무엇이
중요한지 안 보인다. `0` 과 음수는 차분하게 둔다. 기존 `DelayStatusBadge` 의 표현 방식을
참고해 결을 맞춘다.

### 8.2 인플레이스 편집

이름은 이미 `ProjectNameCell` + `useProjectNameEdit` 으로 구현되어 있고, 상세 화면과 훅을
공유한다. **이 구조를 설명과 중요도로 넓힌다.**

- **이름**: 연필 버튼을 그릴 조건을 `canRename`(ADMIN 전용)에서 §5 규칙으로 바꾼다.
- **중요도**: 드롭다운으로 고른다. 값이 일곱 개뿐이라 고르는 즉시 저장하는 편이 자연스럽다.
- **설명**: 아래 8.3 참고.

권한 판단은 지금처럼 셀이 아니라 **호출부가 한다.** 셀 컴포넌트는 받은 대로 그린다.

**상세 화면의 이름 편집기도 함께 바꾼다.** `ProjectDetailPage.tsx:1035` 가
`canRename={isAdmin && adminMode}` 로 넘기고 있어, 그대로 두면 **MANAGER 가 목록에서는
이름을 고칠 수 있는데 상세 화면에서는 못 고치는 어긋남**이 생긴다. 바로 옆에 이미
`canManageProject` 가 있으므로 그것을 넘기면 된다.

### 8.3 설명 편집에서 정해야 할 것

**설명은 최대 2000자인데 목록 셀은 한 줄만 보인다.** 한 줄짜리 입력창에 2000자를 넣게
하면 쓰기 어렵다. 두 방법이 있다.

- **(가) 편집 중에만 셀이 여러 줄 입력창으로 늘어난다.** 화면을 벗어나지 않는다는 요구에
  가장 충실하다. 그동안 그 행의 높이가 커진다.
- **(나) 작은 팝오버를 띄운다.** 행 높이가 흔들리지 않지만 새 컴포넌트가 필요하다.

**(가)로 정했다.** 요구의 핵심이 "목록 화면을 벗어나지 않는 것"이고, 행 높이가 잠시
변하는 것은 편집 중임을 드러내는 신호로도 읽힌다.

### 8.4 정렬

`PROJECT_SORT_FIELDS`(`lib/projectListSort.ts`)에 `priority` 를 추가한다. 이미 만든 정렬
기억 기능이 자동으로 적용되어, 중요도순으로 맞춰 두면 다시 들어와도 유지된다.

**중요도 컬럼만 첫 클릭이 내림차순이다.** 다른 컬럼은 오름차순부터 시작하지만, 중요도로
정렬하는 의도는 거의 언제나 "중요한 것을 위에서 보겠다"이다. 규칙의 일관성보다 이쪽이
덜 헷갈린다. `nextSortSelection()` 에 필드별 시작 방향을 둔다.

동률일 때의 2차 순서는 기존 정렬 동작을 그대로 따른다.

## 9. 테스트

프로젝트 규칙(`AGENTS.md` §4.1, TDD)에 따라 각 단위마다 먼저 실패하는 테스트를 쓴다.

**`packages/shared`**
- 라벨 표가 일곱 값을 모두 덮는다
- 범위를 벗어난 값도 견딘다
- DTO 가 범위 밖 값과 정수가 아닌 값을 거부한다
- DTO 가 `priority` 만 담긴 요청을 받아들인다

**`apps/api`**
- MANAGER 가 명칭·설명·중요도를 고칠 수 있다
- MANAGER 가 `status` 를 보내면 거부된다
- 멤버가 아닌 USER 는 고칠 수 없다
- 관리자 모드가 꺼진 ADMIN 은 남의 프로젝트를 고칠 수 없다
- 감사로그 payload 에 이전 값과 새 값이 함께 남는다
- 바뀌지 않은 필드는 payload 에 없다

**`apps/web`**
- 중요도가 정렬 가능한 컬럼 목록에 있다
- 중요도 컬럼의 첫 클릭이 내림차순이다
- 다른 컬럼의 첫 클릭은 여전히 오름차순이다

화면 연결은 자동 테스트로 덮이지 않으므로 개발 서버를 띄워 직접 확인한다.

## 10. 마이그레이션과 배포

**DB 스키마가 바뀌므로 `AGENTS.md` §7 의 절차를 따른다.**

1. `pnpm dev` 를 끄고 `pnpm -F @sam/api prisma:migrate:dev` 를 돌린다. SQLite 는 단일
   Writer 라 개발 서버가 DB 를 쥐고 있으면 락이 걸린다.
2. 마이그레이션 후 `pnpm -F @sam/api prisma:generate` 로 클라이언트를 갱신한다. 빠뜨리면
   새 필드를 모른다는 TS 에러가 무더기로 난다.
3. **`master` 에 머지하기 전에 fly.io 볼륨 스냅샷을 뜬다.** `master` push 는
   `deploy.yml` 을 돌리고, 컨테이너 기동 스크립트가 `prisma:migrate:deploy` 를 먼저
   부르므로 **머지되는 순간 fly.io 의 DB 에 적용된다.**

```bash
fly volumes list -a seedcore-scheduler
fly volumes snapshots create <volume id>
```

되돌릴 때는 `priority` 컬럼을 떨어뜨리면 되고, 다른 데이터는 건드리지 않는다.

## 11. 이번 범위에서 제외한 것

- **수동 드래그로 순서 바꾸기.** 중요도 컬럼이 같은 목적을 이루므로 실제로 써 본 뒤에
  판단한다. 만들게 된다면 드래그는 곧 중요도를 조정하는 수단이 된다.
- **개인별 순서·고정.** 중요도가 조직 공통 값으로 정해지면서 성격이 다른 기능이 되었다.
- **이력 조회 화면.** §7.3 참고.
- **중요도 변경 알림.** 값이 바뀐 것을 능동적으로 알리지 않는다. 목록에서 보고 알아차린다.
- **상세 화면의 중요도 표시.** 요청은 목록 화면에 대한 것이었다. 상세 화면에서도 보고
  고치고 싶다는 요구가 나오면 그때 넓힌다. 이번에 상세 화면에서 바꾸는 것은 **이름 편집의
  권한 조건 하나뿐**이며(§8.2), 그것도 고치지 않으면 목록과 어긋나기 때문이다.
- **설명 편집을 훅으로 빼기.** 쓰는 곳이 목록 하나뿐이라 아직 이르다. 상세 화면에도 같은
  편집이 생기면 `useProjectNameEdit` 처럼 빼낸다.

## 12. 검토에서 정해진 것

1. **설명 편집 방식**: §8.3 의 (가), 편집 중에만 셀이 여러 줄로 늘어나는 방식으로 정했다.
2. **중요도 라벨 문구**: §4 의 표대로 간다. **고객이 실제로 써 본 뒤 바꾸자고 할 가능성이
   있는 항목이므로**, 문구를 `packages/shared` 한 곳에만 두어 고칠 때 그 파일만 손대면
   되도록 한다.
