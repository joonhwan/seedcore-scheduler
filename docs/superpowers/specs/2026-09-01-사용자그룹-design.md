## 1. 배경과 목적

고객사는 운영기술센터 21명, 구매팀 3명, 경영관리 10명처럼 **조직 단위로 인원을 관리**하고 있으나,
지금 시스템에는 부서나 그룹이라는 개념이 전혀 없다. 사용자는 아이디·이름·역할(ADMIN/USER)만 가지며
소속을 나타내는 자리가 없다.

그래서 프로젝트를 만들 때마다 참여자를 한 명씩 골라야 하고, 반대로 "이 사람이 어떤 프로젝트에
들어 있는지" 확인하려면 프로젝트를 하나씩 열어 봐야 한다. 권한 관리가 프로젝트를 기준으로만
되어 있고 사용자를 기준으로 조회하는 축이 아예 없기 때문이다.

이 설계는 두 가지를 함께 해결한다.

1. **조직 계층을 담는 그룹 기능**을 신설하고, 그룹을 골라 프로젝트 참여자를 한 번에 채운다.
2. **사용자를 기준으로 한 권한 관리 축**을 만들어, 한 사람의 참여 프로젝트를 조회하고 여러
   프로젝트에 한 번에 넣는다.

## 2. 범위

### 이 설계가 다루는 것

- 그룹의 생성·수정·삭제와 계층 구조 (`user_groups`)
- 그룹 소속 인원의 추가·제외 (`user_group_members`)
- 그룹을 골라 프로젝트 참여자 명단을 채우는 기능
- 사용자 기준 프로젝트 권한 조회·일괄 추가·역할 변경·제외
- 프로젝트 생성 화면 개편과 참여자 명단 편집기의 공용 컴포넌트화
- 검색 결과 전체 선택·해제 버튼 (요청 3번)

### 이 설계가 다루지 않는 것

- **그룹을 권한 주체로 삼는 자동 반영.** 그룹 인원이 바뀌어도 이미 만들어진 프로젝트의 참여자는
  변하지 않는다. 근거는 §8에 따로 정리했다.
- **퇴사 처리와 계정 완전 삭제(확정명세 ⑥).** 3차 작업이며 같은 배포에 묶이지만 설계 문서는
  따로 쓴다. 다만 마이그레이션은 한 번에 묶는다(§11).
- 겸직·파견처럼 한 사람이 여러 그룹에 속하는 운영. 데이터 구조는 이를 허용하되 화면에서 1인
  1소속을 지킨다.

## 3. 확정된 결정 사항

브레인스토밍 과정에서 사용자에게 확인받은 결정이다. 확정명세에는 없는 내용이므로 이 문서가
유일한 기록이다.

| 결정 사항 | 확정된 답 |
|---|---|
| 그룹 관리 화면의 위치 | `/admin/groups` 별도 메뉴를 신설한다. 사용자 관리 화면에 얹지 않는다 |
| 인원별 권한 관리(9·10) 화면 형태 | `/admin/users/:id` 사용자 상세 페이지를 새로 만든다. 3차의 퇴사·삭제도 여기 들어간다 |
| 인원이 있는 그룹의 삭제 | 소속 인원이나 하위 그룹이 하나라도 있으면 거부하고 이유를 보여준다 |
| 요청 3번 "전체 선택 버튼" | 그룹 선택과 별개로 "검색 결과 전체 선택·해제" 버튼도 함께 만든다 |
| 그룹과 프로젝트의 연결 수준 | 권한 계산은 건드리지 않고, **집계 조회로 빠뜨림을 안내**한다 (§8) |
| 사용자 목록의 이름 클릭 동작 | 상세 페이지로 이동하도록 바꾸고, 표시 이름 편집은 상세 페이지로 옮긴다 |
| 그룹 계층 깊이 | 최대 5단계로 제한한다 (회사·본부·센터·팀·파트) |

## 4. 데이터 모델

```prisma
model UserGroup {
  id          String   @id
  name        String
  parentId    String?  @map("parent_id")
  description String?
  createdAt   DateTime @default(now()) @map("created_at")
  updatedAt   DateTime @updatedAt @map("updated_at")

  parent   UserGroup?        @relation("GroupTree", fields: [parentId], references: [id])
  children UserGroup[]       @relation("GroupTree")
  members  UserGroupMember[]

  @@unique([parentId, name])
  @@map("user_groups")
}

model UserGroupMember {
  groupId   String   @map("group_id")
  userId    String   @map("user_id")
  addedById String   @map("added_by")
  addedAt   DateTime @default(now()) @map("added_at")

  group   UserGroup @relation(fields: [groupId], references: [id], onDelete: Cascade)
  user    User      @relation("GroupMemberUser", fields: [userId], references: [id])
  addedBy User      @relation("GroupMemberAddedBy", fields: [addedById], references: [id])

  @@id([groupId, userId])
  @@index([userId])
  @@map("user_group_members")
}
```

`User` 모델에는 역참조 두 줄을 더한다.

```prisma
  groupMemberships   UserGroupMember[] @relation("GroupMemberUser")
  groupMembersAdded  UserGroupMember[] @relation("GroupMemberAddedBy")
```

### 설계 판단

- **`@@unique([parentId, name])` 은 최상위 그룹끼리는 걸리지 않는다.** SQL 표준상 `NULL` 끼리는
  같다고 보지 않으므로, `parentId` 가 `NULL` 인 최상위 그룹의 이름 중복은 데이터베이스가 막아
  주지 않는다. **애플리케이션에서 따로 검사해야 하며, 이 검사가 유일한 방어선이다.**
- **`onDelete` 정책이 양쪽에서 다르다.** 그룹 쪽은 `Cascade`, 사용자 쪽은 기존 관례대로
  `RESTRICT` 이다. 다만 인원이나 하위 그룹이 남아 있으면 서버가 삭제 자체를 거부하므로
  `Cascade` 는 실제로 발동하지 않는 안전망이다.
- **계층 깊이를 5단계로 제한하고 순환을 막는다.** 상위 그룹을 지정할 때 자기 자신이나 자기
  자손을 고르면 그래프가 순환하여 펼침 함수가 무한히 돈다. 조직도는 회사·본부·센터·팀·파트면
  충분하다고 보아 5로 잡았다. 일정 트리의 10단계 제한(AGENTS.md §4.6)과는 별개의 값이다.
- **`user_group_members` 는 한 사람이 여러 그룹에 속할 수 있는 형태로 둔다.** 운영은 1인 1소속을
  화면에서 지키지만, 나중에 겸직이나 파견 인원이 생겼을 때 데이터 구조를 뜯어고치지 않아도
  되게 한다. 확정명세 §2의 ㉰ 회신 반영 대목이 이 방침을 명시하고 있다.

## 5. 공유 순수 함수 (`packages/shared`)

**서버의 일괄 추가와 화면의 미리보기가 반드시 같은 함수를 써야** 화면에 "총 7명"이라고 보여 준
숫자와 실제로 들어가는 인원이 어긋나지 않는다. 분기가 많으므로 테스트를 먼저 쓴다.

| 함수 | 역할 |
|---|---|
| `expandGroupMembers(groups, memberships, selectedGroupIds)` | 고른 그룹들의 자손까지 포함한 사용자 id 집합을 돌려준다 |
| `groupDepthOf(groups, groupId)` | 최상위부터 센 깊이를 돌려준다 (최상위가 1) |
| `canReparentGroup(groups, groupId, newParentId)` | 순환과 깊이 초과를 판정한다 |
| `mergeMemberDrafts(current, incoming)` | 명단에 인원을 합류시킨다. 기본 역할은 MEMBER 이고, 이미 있는 사람의 역할은 보존한다 |

`packages/shared` 에 새 export 를 더하므로 vite 사전 번들 캐시 함정에 걸리기 쉽다. `pnpm dev` 로
띄우면 `scripts/dev.mjs` 가 매번 지워 주므로 안전하다 (AGENTS.md §5).

## 6. 서버 API

### 6.1 그룹 (`/api/v1/admin/groups`, ADMIN 전용)

| 메서드 | 경로 | 역할 |
|---|---|---|
| `GET` | `/admin/groups` | 전체 그룹을 계층 정보와 인원수까지 담아 한 번에 반환 |
| `POST` | `/admin/groups` | 그룹 생성 |
| `PATCH` | `/admin/groups/:id` | 이름·설명·상위 그룹 변경 (순환·깊이 검사 포함) |
| `DELETE` | `/admin/groups/:id` | 인원·하위 그룹이 없을 때만 삭제 |
| `GET` | `/admin/groups/:id/members` | 소속 인원 목록 |
| `POST` | `/admin/groups/:id/members` | 여러 명을 한꺼번에 추가. 다른 그룹 소속자는 `move` 옵션으로 옮김 |
| `DELETE` | `/admin/groups/:id/members/:userId` | 소속 해제 |
| `GET` | `/admin/groups/:id/projects` | **그룹 인원의 프로젝트 참여 현황 집계** (§8) |

### 6.2 사용자 기준 권한 (`/api/v1/admin/users/:userId/projects`, ADMIN 전용)

| 메서드 | 경로 | 역할 |
|---|---|---|
| `GET` | `…/projects` | 참여 중인 프로젝트와 역할·참여일 |
| `POST` | `…/projects` | 여러 프로젝트에 한 번에 참여시킴 |
| `PATCH` | `…/projects/:projectId` | 역할 변경 |
| `DELETE` | `…/projects/:projectId` | 참여 해제 |

### 6.3 프로젝트 쪽 확장

- **`CreateProjectDto` 에 `memberUserIds` 를 더한다.** 지금은 `managerUserIds` 만 받으므로
  (`packages/shared/src/index.ts:189`) **생성 시점에 MEMBER 를 넣는 방법이 없다.** `CloneProjectDto`
  가 이미 두 배열을 함께 받고 있으므로 새 형태를 발명하지 말고 그 형태에 맞춘다. 기본값이 빈
  배열이라 기존 호출은 그대로 동작한다.
- **`POST /projects/:projectId/members/bulk` 를 신설한다.** 개별 추가 API 를 여러 번 부르면 중간에
  하나가 실패했을 때 절반만 들어간 상태로 남으므로, 트랜잭션 하나로 처리하고 이미 멤버인 사람은
  건너뛰어 결과를 요약해 돌려준다.

### 6.4 지켜야 할 기존 규칙

- 새 라우트에는 모두 `@UseGuards(OriginGuard)` 를 붙인다 (AGENTS.md §4.4).
- 검증은 `packages/shared` 의 Zod 스키마와 `ZodValidationPipe` 로만 한다. `class-validator` 는
  쓰지 않는다 (AGENTS.md §4.2).
- `members.service.ts` 에 모여 있는 규칙을 사용자 기준 API 에도 똑같이 적용한다. 마지막 MANAGER
  제거 거부(`LAST_MANAGER`), 관리자 모드가 아니면 자기 역할 변경 금지(`CANNOT_CHANGE_SELF_ROLE`),
  관리자 모드일 때 `ADMIN_OVERRIDE_EDIT` 를 함께 남기는 패턴이다.
- `AuditAction` (`packages/shared/src/index.ts:150`) 에 다섯 가지를 더한다. `GROUP_CREATE`,
  `GROUP_UPDATE`, `GROUP_DELETE`, `GROUP_MEMBER_ADD`, `GROUP_MEMBER_REMOVE` 이다. 일괄 추가는
  사람마다 기존 `MEMBER_ADD` 를 남겨 프로젝트 이력에서 추적되게 한다.

### 6.5 새로 쓰는 오류 코드

기존 `LAST_MANAGER`·`NOT_A_MEMBER` 처럼 `{ error: '...' }` 형태로 돌려주며, 화면은 코드에 대응하는
한국어 문장을 보여준다.

| 코드 | 상태 | 뜻 |
|---|---|---|
| `GROUP_NOT_EMPTY` | 409 | 소속 인원이나 하위 그룹이 남아 있어 삭제할 수 없다. 남은 인원수와 하위 그룹 수를 함께 담는다 |
| `GROUP_NAME_DUPLICATE` | 409 | 같은 상위 그룹 아래에 같은 이름이 이미 있다 (최상위끼리도 포함) |
| `GROUP_CYCLE` | 400 | 자기 자신이나 자기 자손을 상위 그룹으로 지정했다 |
| `GROUP_DEPTH_EXCEEDED` | 400 | 계층이 5단계를 넘는다 |
| `GROUP_MEMBER_ALREADY_ASSIGNED` | 409 | `move` 를 주지 않았는데 다른 그룹에 이미 속한 사람이 섞여 있다. 해당 사용자와 현재 소속을 함께 담아 화면이 확인 창을 띄울 수 있게 한다 |

## 7. 화면 설계

세 화면 모두 새로운 시각적 양식을 만들지 않고, 기존 `AdminUsersPage` 와 `ProjectClonePage` 의
Tailwind 구성(테두리 있는 `section`·`fieldset`, `divide-y` 목록, 작은 배지)을 그대로 따른다.
관리자 모드 판정도 기존 페이지가 쓰는 `me.data.globalRole === 'ADMIN' && adminMode` 조건을 쓴다.

라우트는 `apps/web/src/App.tsx` 의 라우트 목록과 헤더의 관리자 메뉴 링크 **두 곳을 함께** 고쳐야
한다.

### 7.1 `/admin/groups` 그룹 관리

좌우 두 칸으로 나눈다. 왼쪽은 그룹 계층 트리이고, 오른쪽은 왼쪽에서 고른 그룹의 상세 정보와 소속
인원 목록이다.

```
┌─ 그룹 관리 ───────────────────────────── [+ 최상위 그룹] ─┐
│ ┌── 계층 트리 ──────────┐ ┌── 기구완성팀 ──────────────┐ │
│ │ ▾ 운영기술센터  21명   │ │ 이름   [기구완성팀      ]  │ │
│ │   · 기구완성팀   5명   │ │ 설명   [               ]  │ │
│ │   · 생산기술팀   8명   │ │ 상위   [운영기술센터  ▾]  │ │
│ │   · 품질보증팀   7명   │ │        [저장] [그룹 삭제]  │ │
│ │ ▸ 구매팀         3명   │ │ ── 소속 인원 5명 ────────  │ │
│ │ ▸ 경영관리      10명   │ │ 홍길동 @hong        [제외] │ │
│ └───────────────────────┘ │           [+ 인원 추가]    │ │
│                            │ ── 참여 중인 프로젝트 ──── │ │
│                            │ 2026 라인 증설  5명 중 3명 │ │
│                            └────────────────────────────┘ │
└────────────────────────────────────────────────────────────┘
```

- **인원수는 자손을 포함한 누계로 보여준다.** 확정명세 §2 의 예시가 "운영기술센터 (21명)"이므로
  사용자가 기대하는 숫자는 누계이다. 직속 인원과 누계가 다른 그룹만 `21명 (직속 1)` 처럼 괄호를
  덧붙여 오해를 막는다.
- **상위 그룹 변경은 드래그가 아니라 셀렉트 박스로 한다.** 그룹이 많아야 수십 개인 규모에서 드래그
  앤드 드롭은 구현 비용에 비해 얻는 것이 적다. 셀렉트의 선택지에서 자기 자신과 자기 자손을 애초에
  빼 두면 순환은 화면 단계에서 막히고, 서버 검사는 안전망으로 남는다.
- **삭제 버튼은 인원이나 하위 그룹이 있으면 비활성으로 두되, 최종 판정은 서버에 맡긴다.** 화면이
  목록을 읽은 뒤 다른 관리자가 인원을 넣었을 수 있으므로, 서버가 거부하면 그 이유를 그대로
  보여준다.

**인원 추가 대화상자**는 검색창과 체크박스 목록으로 여러 명을 한 번에 고른다. 이미 다른 그룹에
속한 사람은 행에 현재 소속을 함께 적어 둔다. 확인을 누를 때 그런 사람이 섞여 있으면 확인 창을 한
번 더 띄우고, 승인한 경우에만 서버에 `move: true` 를 보낸다.

> 선택하신 8명 중 3명은 이미 다른 그룹에 속해 있습니다.
> 홍길동(구매팀), 김철수(경영관리), 이영희(품질보증팀)
> 기존 소속에서 빼고 기구완성팀으로 옮기시겠습니까?

### 7.2 `/admin/users/:id` 사용자 상세

```
← 사용자 관리
홍길동 @hong  [ADMIN] [비활성]
마지막 로그인 2026-09-01 14:20 · 생성 2026-03-11

┌─ 계정 ──────────────────────────────────────────┐
│ 표시 이름 [홍길동        ] [저장]                │
│ [비밀번호 리셋] [비활성화] [잠금 해제]           │
└──────────────────────────────────────────────────┘
┌─ 소속 그룹 ─────────────────────────────────────┐
│ 운영기술센터 › 기구완성팀          [소속 변경]   │
└──────────────────────────────────────────────────┘
┌─ 참여 프로젝트 3건 ──────── [+ 프로젝트 일괄 추가] ┐
│ 2026 라인 증설   [MANAGER ▾]  2026-04-02  [제외] │
│ 설비 예방보전     [MEMBER  ▾]  2026-05-11  [제외] │
└──────────────────────────────────────────────────┘
```

- **사용자 목록의 이름 클릭은 이 상세 페이지로 이동하도록 바꾸고, 표시 이름 인라인 편집은 상세
  페이지로 옮긴다.** 목록 행에는 이미 버튼이 세 개 붙어 있는데 3차의 퇴사 처리와 계정 삭제까지
  더하면 행이 감당하지 못한다. 상세 페이지가 사용자 한 명에 관한 모든 조작이 모이는 자리가 된다.
  비밀번호 리셋·활성 토글·잠금 해제는 빠른 처리를 위해 목록에도 그대로 남긴다.
- **소속 그룹은 경로 전체를 보여준다.** 1인 1소속이므로 표시할 것은 하나이며, 상위 계층까지 적어야
  "기구완성팀"이 어느 센터 소속인지 알 수 있다. 소속이 없으면 "소속 없음"으로 적고 지정 버튼을 둔다.
  `[소속 변경]` 은 그룹을 고르는 대화상자를 열고, 확인하면 `POST /admin/groups/:id/members` 를
  `move: true` 로 부른다. 즉 §7.1 의 옮기기와 같은 경로를 쓰며 별도 API 를 만들지 않는다.
- **역할 변경은 셀렉트 박스를 바꾸는 즉시 확인 창을 거쳐 서버로 보낸다.** 기존
  `ProjectMembersPage` 가 그 방식이므로 맞춘다.
- **일괄 추가 대화상자**는 프로젝트 목록을 검색과 체크박스로 고르고, 역할을 하나 골라(기본값은
  MEMBER) 한꺼번에 넣는다. 이미 참여 중인 프로젝트는 체크할 수 없게 막고 "참여 중"이라고 적어 둔다.
- 마지막 MANAGER 를 빼려는 경우에는 서버가 거부하며, 화면은 그 이유를 그대로 보여준다.

### 7.3 공용 명단 편집기와 프로젝트 생성 화면

`ProjectClonePage` 안에 있는 참여자 명단 편집기(`MemberDraft` 인터페이스, 22행 부근)를
`apps/web/src/components/MemberDraftEditor.tsx` 로 떼어낸다. 이 컴포넌트가 담는 것은 명단
목록(사람마다 MANAGER·MEMBER·제외를 고르는 라디오), 인원수 요약, 그리고 명단을 채우는 두 가지
입력이다.

```
┌─ 참여자 명단 ────────────────────────────────────┐
│ 총 7명 (MANAGER 1 · MEMBER 6)                     │
│ [그룹으로 담기]                                    │
│ ┌ 검색해서 담기 ────────────────────────────────┐ │
│ │ [검색어            ]  ☑ 결과 전체 선택         │ │
│ │ ☑ 홍길동 @hong    ☐ 김철수 @kim               │ │
│ │                        [선택한 2명 담기]       │ │
│ └────────────────────────────────────────────────┘ │
│ ── 명단 ──────────────────────────────────────────│
│ 홍길동 @hong      ○MANAGER ●MEMBER ○제외          │
└────────────────────────────────────────────────────┘
```

- **`[그룹으로 담기]` 는 대화상자를 연다.** 그 안에서 그룹을 체크박스로 여러 개 고르면 하단에
  "선택한 그룹 인원 21명"이 미리 보이고, `명단에 담기` 를 눌러야 실제로 합류한다. 상위 그룹을
  고르면 자손 인원까지 함께 들어온다. **단발성 동작으로 두는 이유**는, 그룹 체크를 명단과 계속
  묶어 두면 체크를 해제할 때 개별로 MANAGER 로 바꿔 둔 사람까지 사라져 혼란스럽기 때문이다.
  명단을 한 번 복사하고 그 뒤로는 독립적으로 편집하는 방식이 ㉯ 회신의 성격과도 맞는다.
- **그룹으로 들어온 사람의 기본 역할은 MEMBER** 이고, 이미 명단에 있는 사람은 다시 들어오지
  않으며 기존 역할을 유지한다 (`mergeMemberDrafts`).
- **요청 3번의 전체 선택 버튼**은 검색 결과 목록의 머리에 붙는 `결과 전체 선택` 체크박스로
  구현한다. 검색어를 바꾸면 선택이 그 결과 범위에 한정되므로, 실수로 전 인원을 담는 일이 줄어든다.

이 컴포넌트를 쓰는 자리는 셋이다.

| 화면 | 적용 |
|---|---|
| `ProjectNewPage` | 새로 도입한다. 지금은 MANAGER 체크박스 목록뿐이다 |
| `ProjectClonePage` | 기존 코드를 이 컴포넌트로 교체한다. 비활성 사용자 경고 표시는 이 화면 전용 속성으로 남긴다 |
| `ProjectMembersPage` | 멤버 추가 영역에 `[그룹으로 담기]` 만 가져다 붙이고 결과를 `POST /projects/:projectId/members/bulk` 로 보낸다 (확정명세 §2-다) |

## 8. 그룹과 프로젝트의 관계

### 8.1 원칙: 명단 복사이며 자동 반영은 없다

프로젝트를 만드는 시점의 그룹 인원을 **참여자 명단으로 복사**한다. 이후 그룹에 사람이 들어오거나
빠져도 이미 만들어진 프로젝트의 참여자는 그대로 유지된다. 확정명세의 ㉯ 회신이 확정한 사양이다.

`project_members` 는 사용자 아이디만 담고 그룹을 참조하지 않으므로, **그룹을 지워도 프로젝트
권한은 한 건도 변하지 않는다.** 이것은 결함이 아니라 이 설계가 주는 가장 큰 이득이다. 그룹이
권한 주체였다면 조직 개편으로 "운영기술센터"를 없애는 순간 21명이 참여 중이던 모든 프로젝트에서
조용히 빠져나가는데, 폐쇄망이라 통지 수단이 없어 당사자는 다음 날 화면이 비어 있는 것을 보고서야
알게 된다.

### 8.2 대신 넣는 것: 집계 조회로 빠뜨림을 안내한다

자동 반영이 없을 때 남는 실질적 불편은 "관리자가 손으로 챙겨야 하는데 어디를 챙겨야 하는지 알
방법이 없다"는 점이다. 권한 계산을 건드리지 않고 이것만 해결한다.

`GET /api/v1/admin/groups/:id/projects` 는 그 그룹(자손 포함) 인원이 참여 중인 프로젝트를 집계해,
프로젝트마다 참여 인원수·그룹 인원수·빠진 사람 명단을 돌려준다. `project_members` 에
`@@index([userId])` 가 이미 있으므로 150명 규모에서는 즉시 응답한다.

붙는 자리는 셋이다.

| 자리 | 동작 |
|---|---|
| 그룹에 사람을 넣은 직후 | "기구완성팀 인원이 참여 중인 프로젝트가 2건 있습니다. 홍길동을 함께 넣으시겠습니까?" 체크 목록을 띄우고, 승인하면 `POST /projects/:id/members/bulk` 를 쓴다 |
| 그룹에서 사람을 뺄 때 | "이 사람은 기구완성팀이 참여 중인 프로젝트 2건에 들어 있습니다. 함께 빼시겠습니까?" 체크 목록을 띄운다. 체크를 풀면 프로젝트 권한은 유지된다 |
| 그룹 관리 화면 상세 패널 | "참여 중인 프로젝트" 목록을 상시 보여준다. "5명 중 3명"처럼 어긋난 곳이 눈에 띈다 |

**한계를 명시해 둔다.** 이 집계는 "이 프로젝트를 기구완성팀으로 채웠다"는 사실을 기록하는 것이
아니라, 현재 겹치는 인원을 보고 역으로 추론하는 것이다. 따라서 그룹과 무관하게 개별로 들어간
사람이 우연히 많은 프로젝트도 목록에 뜰 수 있다. 참여 비율을 함께 표시하고 비율이 높은 순으로
정렬해 이를 완화한다.

### 8.3 검토했다가 버린 대안

같은 고민을 되풀이하지 않도록 근거와 함께 남긴다.

- **그룹을 권한 주체로 승격** (`project_groups` 연결 테이블을 두어 그룹 인원 변경이 프로젝트에
  자동 반영되게 함): ㉯ 회신이 "자동 반영 없음"으로 확정했으므로 요구사항과 정면으로 어긋난다.
  비용도 크다. 멤버 여부를 조회하는 자리가 열두 곳(`project-access.ts:21`, `nodes.service.ts` 네
  곳, `comments.service.ts` 두 곳, `members.service.ts` 다섯 곳)이고 프로젝트 목록의 가시성
  필터(`projects.service.ts:50`)까지 모두 합집합 판정으로 바뀐다. 여기에 더해 역할을 어디에
  저장할지가 모호해지고(그룹 역할과 개인별 예외의 이중 구조), 마지막 MANAGER 보호 규칙이 그룹
  인원 관리 경로로 새어 나가며, `project_members.addedAt` 이 담고 있던 참여 이력이 흐려진다.
- **출처 기록 전용 테이블** (`project_groups` 를 두되 권한 계산에는 쓰지 않고 "무엇으로 채웠는지"만
  남김): §8.2 의 집계가 추론이 아니라 확정 기록이 된다는 이점이 있으나, 테이블이 셋으로 늘어
  §11 에서 실측으로 검증해 둔 마이그레이션 결과를 다시 확인해야 한다. 얻는 것에 비해 비용이
  크다고 보아 채택하지 않았다.
- **서버가 그룹 id 를 받아 인원을 펼침** (화면은 그룹 id 만 전송): 생성 전에 최종 명단과 "총 7명"을
  확인할 수 없어 확정명세 §2-나와 어긋난다.

## 9. 검증 계획

이 저장소의 기존 시험 방식을 따른다. 순수 로직은 별도 모듈로 떼어내 `vitest` 로 검사하고
(`clone-tree.ts` 와 `clone-tree.test.ts` 가 본보기), 서비스는 Prisma 를 대역으로 바꿔치기해 규칙만
검사한다(`auth.service.test.ts` 방식). 실제 데이터베이스를 띄우는 통합 시험은 이 저장소에 없으므로
새로 도입하지 않는다.

### 9.1 순수 로직 (테스트를 먼저 쓴다)

| 함수 | 검사할 분기 |
|---|---|
| `expandGroupMembers` | 상위 그룹 선택 시 자손 인원 포함, 형제 그룹 선택 시 중복 제거, 빈 그룹, 확정명세 §2 의 21명·7명 예시 두 가지 |
| `groupDepthOf` / `canReparentGroup` | 자기 자신을 상위로 지정, 자기 자손을 상위로 지정, 깊이 5단계 초과, 최상위로 올리기 |
| `mergeMemberDrafts` | 그룹으로 담을 때 기본 역할 MEMBER, 이미 명단에 있는 사람의 역할 보존, 중복 제거 |

### 9.2 서버 규칙 (Prisma 대역)

거부해야 하는 경우를 중심으로 검사한다. 통과 경로보다 거부 경로가 사고를 막는 자리이다.

- 그룹 삭제: 소속 인원이 있을 때 거부, 하위 그룹이 있을 때 거부, 둘 다 없을 때만 허용
- 그룹 생성·이름 변경: **최상위 그룹끼리의 이름 중복**을 애플리케이션이 막는지 (§4 참고)
- 상위 그룹 변경: 순환과 깊이 초과를 거부
- 인원 추가: `move` 를 주지 않았는데 다른 그룹 소속자가 섞여 있으면 거부
- 사용자 기준 권한 API: 마지막 MANAGER 제거 거부, 관리자 모드가 아닐 때 자기 역할 변경 거부,
  관리자 모드일 때 `ADMIN_OVERRIDE_EDIT` 감사로그를 함께 남기는지
- 일괄 추가: 트랜잭션 하나로 처리되어 중간 실패 시 절반만 들어가지 않는지, 이미 멤버인 사람을
  건너뛰고 결과를 요약해 돌려주는지

### 9.3 마이그레이션

`prisma migrate dev` 로 폴더를 만든 뒤, **생성된 SQL 이 §11 에서 실측으로 검증해 둔 다섯 문장과
같은지 대조한다.** 다르면 그 자리에서 멈추고 재검증한다. 이어서 `migration-runner.test.ts` 의
checksum 고정 시험이 기존 여섯 개만 대조하므로 새 폴더를 막지 않는지 확인하고, `.gitattributes`
규칙대로 새 SQL 파일의 줄바꿈이 LF 인지 확인한다.

`prisma migrate dev` 는 개발 서버를 끄고 돌린다. SQLite 는 단일 writer 라 `pnpm dev` 가 DB 핸들을
쥐고 있으면 락이 걸린다.

### 9.4 전체 검사

`pnpm -r typecheck` 와 `pnpm -r test` 를 돌린다.

### 9.5 화면 확인 (직접 조작)

시드 데이터로 확정명세 §2 의 조직도(운영기술센터 아래 세 팀과 센터장)를 그대로 만들어 두고, 회신의
두 예시를 화면에서 재현한다.

| 예시 | 선택 | 기대 결과 |
|---|---|---|
| 1 | 운영기술센터 체크 | 하위 세 팀과 센터장까지 21명 전원 |
| 2 | 기구완성팀 체크 + 센터장 개별 + 품질보증팀원 1명 개별 | 7명 |

여기에 더해 §8.2 의 집계 안내가 실제로 뜨는지 확인한다. 그룹에 사람을 넣은 직후에 "함께
넣으시겠습니까" 대화상자가 올라오고, 승인하면 해당 프로젝트에 실제로 들어가야 한다.

### 9.6 배포판 예행 연습 (구현 계획의 마지막 단계)

**마지막 스키마 변경은 2026-07-14 커밋 `b96c0a2` 이고 그 뒤로 237개 커밋 동안 스키마가 그대로였다.**
즉 `sp-migrate.exe` 경로는 코드와 테스트로는 갖춰져 있으나 고객 현장에서 실제로 돌아본 적이 없을
가능성이 높다. 다음을 순서대로 확인한다.

1. `pnpm build:exe` 로 실제 배포판을 빌드한다
2. 고객 데이터베이스 사본을 놓고 `sp-server.exe` 를 실행해 **종료 코드 3으로 멈추고 안내가 뜨는지**
   확인한다 (`apps/api/src/prisma/boot-decision.ts:77`)
3. `sp-migrate.exe` 를 실행해 `backups/pre-migrate/` 에 스냅샷이 생기고 다섯 문장이 모두 적용되는지
   확인한다
4. `sp-server.exe` 를 다시 실행해 정상 기동하는지 확인하고, 기존 아홉 개 테이블의 행 수가 그대로인지
   대조한다

## 10. 구현 순서

확정명세 §9 와 이관 문서의 제안을 따른다.

1. Prisma 스키마와 마이그레이션 (2차의 테이블 둘과 3차의 `users.retired_at` 을 한 번에 묶는다)

9. 배포판 예행 연습 (§9.6)

## 11. 데이터베이스 변경 (AGENTS.md §7)

| 변경 | 대상 | 내용 |
|---|---|---|
| 신규 테이블 | `user_groups` | 그룹 정보와 상위 그룹(`parent_id`)으로 표현하는 조직 계층 |
| 신규 테이블 | `user_group_members` | 그룹 소속. 기본키는 `(group_id, user_id)` |
| 컬럼 추가 | `users.retired_at` | 퇴사 처리 시각 (3차 작업이나 마이그레이션은 함께 묶는다) |

**이 변경은 이미 실측으로 검증되었으므로 다시 검증할 필요가 없다.** `prisma migrate diff
--from-schema-datasource` 로 실제 개발 DB 와 새 스키마의 차이를 뽑은 뒤, 그 SQL 을 데이터가 든 DB
사본에 직접 적용해 확인했다.

- 생성된 SQL 은 `ALTER TABLE ADD COLUMN` 하나, `CREATE TABLE` 둘, `CREATE INDEX` 둘로 **모두 다섯
  문장이며 기존 테이블을 재생성하지 않는다.** SQLite 에서 Prisma 가 종종 택하는 테이블 재생성
  경로(`RedefineTables`)가 발동하지 않은 이유는 `retired_at` 이 `NULL` 을 허용하고 기본값이 없기
  때문이다.
- 적용 전후로 users 7, projects 1, project_members 3, schedule_nodes 8, node_comments 2,
  node_history 111, audit_logs 192, sessions 4, autocomplete_terms 34 가 **모두 그대로**였다.
- `PRAGMA integrity_check` 는 `ok`, `PRAGMA foreign_key_check` 는 위반 0건이었다.
- 배포판이 쓰는 문장 분리기(`splitSqlStatements`)에 넣어도 정확히 다섯 문장으로 갈라져 모두
  성공했다.

**주의: `retired_at` 에 기본값을 주거나 `NOT NULL` 로 바꾸면 위 결론이 무너진다.** 그 경우 Prisma 가
`users` 테이블을 통째로 재생성하는 경로를 택하므로 검증을 다시 해야 한다.

§8 에서 결정한 집계 조회는 새 테이블을 쓰지 않으므로 이 결론에 영향을 주지 않는다.

### 반영 절차

`sp-server.exe` 는 데이터가 든 DB 에서 미적용 마이그레이션을 발견하면 **DB 를 건드리지 않고 종료
코드 3으로 멈춘다.** 관리자가 `sp-migrate.exe` 를 따로 실행해야 하며, 그 도구가 `VACUUM INTO` 로
`backups/pre-migrate/` 에 스냅샷을 뜬 뒤 적용한다. 고객용 절차는 확정명세 §7 에 표로 정리되어
있고, 배포판 `README.txt` 4장(원본은 `apps/api/scripts/README-exe.txt`)에 더 자세히 적혀 있다.

빌드 쪽은 손댈 것이 없다. `apps/api/scripts/build-exe.js` 가 `prisma/migrations` 전체를 복사해
`sp-server.exe` 와 `sp-migrate.exe` 양쪽 pkg 자산에 넣고, 폴더가 비어 있으면 빌드를 중단하는
검사(`assertMigrationsEmbedded`)까지 있다. **새 마이그레이션 폴더를 만들기만 하면 자동으로 실려
나간다.**
