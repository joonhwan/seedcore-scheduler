# 사용자·그룹 일괄 등록 (텍스트 파일) — 설계

- 작성일: 2026-09-09
- 대상 화면: 관리자 모드 "사용자 관리" (`apps/web/src/pages/AdminUsersPage.tsx`)
- 배경 문서: `docs-customer/2026-09-01-요청사항-확정명세.md` §2 (사용자 그룹, 조직 계층)
- 데이터베이스 변경: **없음** (AGENTS.md §7 해당 없음)

---

## 1. 목적과 범위

조직도를 담은 텍스트 파일 한 장으로 **그룹 계층과 사용자 계정을 한 번에 만든다.** 지금은
`UserCreateDialog` 가 계정을 한 명씩 만들고 소속을 지정하므로, 개통 시점에 수십 명을 넣으려면
같은 작업을 그 수만큼 되풀이해야 한다.

범위에 넣지 않는 것을 먼저 밝힌다.

- **기존 계정의 수정과 삭제는 다루지 않는다.** 이 기능은 새로 만드는 일만 한다. 파일을 잘못 올려
  멀쩡한 사람의 소속이 조용히 바뀌는 사고를 원천적으로 막기 위함이다.
- **프로젝트 참여는 다루지 않는다.** 확정명세 §2 의 "명단 복사 방식"대로, 프로젝트 참여자는
  프로젝트를 만드는 시점에 그룹을 골라 채운다.
- **ADMIN 계정은 만들지 않는다.** 기존 생성 경로와 같이 `globalRole` 은 `USER` 로 고정한다.

## 2. 파일 형식

들여쓰기로 조직 계층을 나타내고, 사용자 줄만 `- ` 로 시작한다.

```
# 운영기술센터 (2026년 조직도)
운영기술센터
  기구완성팀
    - gigu01, 김민준-기구완성팀
    - gigu02, 이서연-기구완성팀
  생산기술팀
    - saeng01, 박도윤-생산기술팀
  - center01, 정하준-센터장
구매팀
  - gumae01, 한지호-구매팀
```

### 2.1 해석 규칙

| 항목 | 규칙 |
|---|---|
| 건너뛰는 줄 | 빈 줄, 공백만 있는 줄, `#` 로 시작하는 줄 |
| 들여쓰기 환산 | 탭 하나를 공백 4칸으로 본다 |
| 계층 판정 | 앞선 줄보다 깊으면 그 줄의 하위, 같으면 형제, 얕으면 맞는 단계까지 나온다 |
| 그룹 줄 | `- ` 로 시작하지 않는 줄. 앞뒤 공백을 뗀 나머지 전체가 그룹 이름이다 |
| 사용자 줄 | `- 아이디, 이름`. **첫 쉼표만 구분자로 본다** (이름에 쉼표가 들어가도 잘리지 않는다) |
| 소속 없는 사용자 | 들여쓰기 없는 사용자 줄. 확정명세 §2 의 "그룹 밖 인원(임원 등)"이 이 자리다 |
| 계층 제한 | 최대 8단계 (`MAX_GROUP_DEPTH`, `packages/shared/src/user-groups.ts`) |

들여쓰기 폭을 2칸이나 4칸으로 고정하지 않고 **직전 줄과의 상대적 깊이**로 판정하는 이유는, 손으로
쓴 파일에서 폭이 어긋나는 일이 흔하기 때문이다. 폭을 고정하면 3칸으로 쓴 파일이 통째로 거부되지만,
상대 판정이면 파일 안에서 일관되기만 하면 통과한다. 대신 어느 단계와도 맞지 않는 어중간한 들여쓰기는
`BAD_INDENT` 로 잡아, 사람이 의도한 계층과 다르게 해석되는 일을 막는다.

### 2.2 아이디 제약

`Username` 스키마(`packages/shared/src/index.ts`)가 영숫자와 `.`, `_`, `-` 만 3~64자로 허용한다.
**한글 아이디는 쓸 수 없다.** 부서명을 아이디에 넣으려면 영문 약칭을 쓴다.

## 3. 화면 동작

사용자 관리 화면 머리의 "+ 사용자 추가" 옆에 **"일괄 등록"** 버튼을 둔다. 대화상자의 구성은 일정
CSV 가져오기(`ProjectDetailPage.tsx`)와 같게 맞춘다.

1. `.txt` 파일을 고르거나 텍스트를 직접 붙여넣는다. 형식 설명과 예시 몇 줄을 접이식으로 함께 둔다.
2. "확인"을 누르면 서버에 미리보기(`dryRun: true`)를 요청한다.
3. 미리보기에 아래를 보여준다.
   - 새로 만들 그룹 수와 이미 있는 그룹 수
   - 새로 만들 사용자 수와 이미 있는 아이디 목록
   - 고쳐야 하는 줄을 **줄 번호와 함께 모두** 나열
4. 초기 비밀번호를 한 번 입력한다. `validatePassword` 로 화면에서 먼저 거른다.
5. 이미 있는 아이디가 **하나라도 있을 때만** "이미 있는 아이디는 건너뛰고 나머지만 만들기"
   체크상자가 나타난다.
6. 형식 오류가 하나라도 남아 있으면 등록 버튼이 눌리지 않는다. 중복은 오류가 아니라 위 체크상자로
   처리한다.
7. 등록 요청은 미리보기가 준 `previewToken` 을 함께 보낸다.
8. 등록이 끝나면 몇 명을 만들고 몇 명을 건너뛰었는지 요약을 보여주고 사용자 목록을 다시 읽는다.
9. **`409 BULK_IMPORT_STALE` 을 받으면** "미리보기 이후에 다른 관리자가 사용자나 그룹을
   만들었습니다. 다시 확인해 주십시오"라고 안내하고 미리보기를 자동으로 다시 부른다. 대화상자는
   닫지 않고 입력한 텍스트와 비밀번호를 그대로 둔다. 관리자가 처음부터 다시 할 일은 없다.

## 4. 서버 설계

### 4.1 엔드포인트

`POST /api/v1/admin/users/bulk-import` 하나이며 `@AdminOnly()` 와 `@UseGuards(OriginGuard)` 를 단다
(AGENTS.md §4.4).

미리보기와 실제 적용을 **한 엔드포인트의 `dryRun` 플래그**로 나눈 이유는, 둘이 같은 계산을 지나야
하기 때문이다. 따로 만들면 "미리보기에서는 31명이라 했는데 등록하니 30명"이 생길 여지가 남는다.

### 4.2 DTO 와 응답

```ts
export const BulkImportUsersDto = z.object({
  text: z.string().min(1),
  initialPassword: z.string().min(PASSWORD_MIN_LENGTH),
  dryRun: z.boolean().default(true),
  skipExisting: z.boolean().default(false),
  /**
   * 미리보기가 내려준 값을 그대로 되돌려준다. dryRun 이 거짓일 때만 필수다.
   * 서버가 트랜잭션 안에서 다시 계산해 다르면 409 로 거부한다 (§4.4).
   */
  previewToken: z.string().min(1).optional(),
});

export const BulkImportIssueCode = z.enum([
  'EMPTY_FILE', 'BAD_INDENT', 'BAD_USER_LINE', 'INVALID_USERNAME',
  'DUPLICATE_USERNAME_IN_FILE', 'DUPLICATE_GROUP_IN_FILE',
  'NAME_TOO_LONG', 'GROUP_DEPTH_EXCEEDED',
]);   // 각 코드의 뜻은 §4.8

export const BulkImportIssue = z.object({
  line: z.number().int(),      // 1부터 세는 원본 줄 번호
  code: BulkImportIssueCode,
  message: z.string(),
});

export const BulkImportResult = z.object({
  /** 실제로 반영했는가. dryRun 이면 항상 false. */
  applied: z.boolean(),
  /** 아래 두 목록을 정렬해 해시한 값. 적용 요청이 이것을 되돌려준다 (§4.4). */
  previewToken: z.string(),
  groupsToCreate: z.array(z.array(z.string())),   // 최상위부터의 경로
  groupsExisting: z.array(z.array(z.string())),
  usersToCreate: z.array(z.object({
    line: z.number().int(),
    username: z.string(),
    displayName: z.string(),
    groupPath: z.array(z.string()),               // 빈 배열이면 소속 없음
  })),
  usersExisting: z.array(z.object({ line: z.number().int(), username: z.string() })),
  issues: z.array(BulkImportIssue),
  createdUserCount: z.number().int(),
  createdGroupCount: z.number().int(),
  skippedUserCount: z.number().int(),
});
```

미리보기와 적용이 **같은 응답 형태**를 쓴다. 화면은 `applied` 로 둘을 구분한다.

### 4.3 처리 순서

1. `packages/shared/src/user-import.ts` 의 순수 파서가 텍스트를 그룹 경로 목록과 사용자 목록으로
   바꾸고, 형식 오류를 줄 번호와 함께 모은다. **첫 오류에서 멈추지 않는다.**
2. 형식 오류가 남아 있으면 여기서 갈린다. `dryRun` 이 참이면 오류 목록을 담아 돌려주고, 거짓이면
   `400 BULK_IMPORT_INVALID` 로 거부한다. 화면은 미리보기를 거치므로 정상 흐름에서는 뒤쪽에 닿지
   않고, API 를 직접 부르는 경로를 막는 안전장치다.
3. `dryRun` 이 참이면 데이터베이스와 대조해 집계와 `previewToken` 을 만들어 돌려주고 끝낸다.
   여기서는 아무것도 쓰지 않으므로 트랜잭션이 필요 없다.
4. **비밀번호 해싱을 트랜잭션 밖에서 먼저 끝낸다.** bcrypt 는 한 번에 40밀리초 남짓 걸려 34명이면
   1.5초가량인데, 트랜잭션 안에 두면 SQLite 의 단일 Writer 를 그 시간만큼 붙들어 다른 사람의 저장이
   모두 밀린다. 공통 비밀번호라도 salt 는 계정마다 달라야 하므로 해시 자체는 사람 수만큼 계산한다.
5. `prisma.$transaction` 을 연다. **데이터베이스 대조를 이 안에서, 삽입 바로 앞에서 한다** (§4.4).
   1. 이미 있는 아이디와 이미 있는 그룹 경로를 가려낸다.
   2. 중복이 있는데 `skipExisting` 이 거짓이면 `400 BULK_IMPORT_DUPLICATE` 로 거부한다.
   3. `previewToken` 을 다시 계산해 요청이 가져온 값과 다르면 `409 BULK_IMPORT_STALE` 로 거부한다.
   4. 그룹을 위 단계부터 만들고, 사용자를 만들고, 소속을 넣는다.
   하나라도 실패하면 전부 되돌아간다.
6. Prisma 의 `P2002`(유일 제약 위반)를 잡아 `409 BULK_IMPORT_STALE` 로 바꾼다. 앞의 검사를 모두
   지나고도 남는 경합의 최후 방어선이며, 날것의 Prisma 오류가 화면에 뜨는 것을 막는다.
7. 감사로그를 남긴다 (§4.7).

### 4.4 미리보기와 적용 사이의 경합

미리보기를 본 뒤 등록을 누르기까지 사람이 화면을 읽는 시간이 흐른다. 그 사이에 다른 관리자가
사용자나 그룹을 만들 수 있다. 개통 시점에 관리자 여러 명이 부서를 나눠 넣는 상황이 이 기능의
전형적인 사용처라, 겹칠 여지가 작지 않다.

**창은 두 군데에 열린다.**

| 창 | 처리 |
|---|---|
| 요청 하나 안 (대조 → 삽입) | 대조를 트랜잭션 안, 삽입 바로 앞으로 옮겨 없앤다. 해싱은 밖에 두어 락 시간을 짧게 유지한다 |
| 미리보기 → 적용 | `previewToken` 으로 잡는다 (아래) |

**`previewToken` 은 "새로 만들 아이디 목록과 새로 만들 그룹 경로 목록"을 정렬해 해시한 값이다.**
미리보기가 내려주고 적용 요청이 그대로 되돌려주며, 서버가 트랜잭션 안에서 다시 계산해 대조한다.
다르면 아무것도 만들지 않고 `409 BULK_IMPORT_STALE` 로 거부한다. 화면은 "미리보기 이후에 다른
관리자가 사용자나 그룹을 만들었습니다"라고 안내하고 미리보기를 다시 부른다. **파일을 고치라고
말하면 안 된다** — 바뀐 것은 파일이 아니라 데이터베이스다.

이것은 AGENTS.md §4.5 의 `expectedUpdatedAt` 을 시각 하나가 아니라 집합에 적용한 것이다. 새 개념이
아니라 이 프로젝트가 이미 쓰는 낙관적 동시성 검사를 그대로 옮겼다.

토큰이 막아 주는 것을 사례로 적어 둔다.

| 사이에 벌어진 일 | 토큰이 없으면 | 토큰이 있으면 |
|---|---|---|
| 중복이 생겼고 `skipExisting` 이 거짓 | 400 으로 거부 (이미 안전) | 같음 |
| 중복이 생겼고 `skipExisting` 이 참 | **조용히 한 명을 덜 만든다** | 409 로 거부하고 다시 확인시킨다 |
| 같은 이름의 그룹이 생김 | 재사용하며 개수가 어긋난다 | 409 로 거부하고 다시 확인시킨다 |
| 관리자 둘이 같은 파일을 동시에 적용 | 뒤쪽이 유일 제약에 걸려 통째로 실패 | 뒤쪽이 대조에서 잡혀 409, 걸러지지 않으면 `P2002` 도 409 로 |

가운데 두 줄이 토큰을 두는 이유다. 개수가 어긋난 채로 끝나면 관리자는 나중에야 알아챈다.

### 4.5 이미 있는 것을 만났을 때

- **이미 있는 그룹은 그대로 쓴다.** 이름으로 대조하며, 앞뒤 공백을 뗀 뒤 정확히 같은 이름끼리
  같은 그룹으로 본다. 설명이나 상위 그룹을 파일 내용으로 덮어쓰지 않는다.
- **이미 있는 아이디는 `skipExisting` 이 참일 때만 건너뛴다.** 건너뛴 사람의 이름과 소속은 손대지
  않는다. §1 에서 밝힌 대로 이 기능은 새로 만드는 일만 하기 때문이다.

### 4.6 만들어지는 계정

기존 `UsersService.create()` 와 같다. `globalRole` 은 `USER`, `passwordMustChange` 는 참,
`isActive` 는 참, `retiredAt` 은 비어 있다.

### 4.7 감사로그

개별 `USER_CREATE` 와 `GROUP_CREATE` 를 **그대로 남기되** payload 에 일괄 등록임을 표시하고,
요약 한 줄을 새 액션 `USER_BULK_IMPORT` 로 남긴다.

개별 기록을 생략하고 요약만 남기면 "이 계정을 누가 언제 만들었나"를 계정 단위로 되짚을 수 없다.
반대로 요약이 없으면 34줄이 흩어져 "일괄 등록 한 번"이라는 사실이 기록에서 사라진다. 둘 다 남긴다.

`AuditAction` 은 문자열이고 마이그레이션에 `CHECK` 제약이 걸려 있지 않으므로, 새 액션 이름을
`packages/shared/src/index.ts` 의 목록에 더하는 것으로 끝난다. **데이터베이스 변경은 없다.**

### 4.8 오류 코드

| 코드 | 상황 |
|---|---|
| `EMPTY_FILE` | 내용이 될 줄이 하나도 없음 |
| `BAD_INDENT` | 들여쓰기가 어느 단계와도 맞지 않음 |
| `BAD_USER_LINE` | `- 아이디, 이름` 형태가 아님 |
| `INVALID_USERNAME` | 아이디에 허용되지 않는 문자가 있거나 길이를 벗어남 |
| `DUPLICATE_USERNAME_IN_FILE` | 같은 아이디가 파일 안에서 두 번 나옴 |
| `DUPLICATE_GROUP_IN_FILE` | 같은 부모 아래 같은 그룹 이름이 두 번 나옴 |
| `NAME_TOO_LONG` | 그룹 이름 64자, 사용자 이름 128자를 넘음 |
| `GROUP_DEPTH_EXCEEDED` | 계층이 8단계를 넘음 |

위는 **파일 내용의 오류**이며 줄 번호와 함께 `issues` 에 담겨 미리보기에 나온다. 아래는 **요청
자체를 거부하는 오류**로, HTTP 상태 코드와 `error` 필드로 돌아간다.

| 코드 | 상태 | 상황 |
|---|---|---|
| `BULK_IMPORT_INVALID` | 400 | 적용 요청인데 파일 내용에 오류가 남아 있음 |
| `BULK_IMPORT_DUPLICATE` | 400 | 이미 있는 아이디가 있는데 `skipExisting` 이 거짓 |
| `BULK_IMPORT_STALE` | 409 | 미리보기 이후 데이터베이스가 바뀜, 또는 `P2002` (§4.4) |

## 5. 시험

- `packages/shared/src/user-import.test.ts` (신규) — 파서 단위 시험. 구성은 옆에 있는
  `user-groups.test.ts` 를 따른다. 정상 트리, 탭과 공백이 섞인 트리, 어긋난 들여쓰기, 중복 아이디,
  소속 없는 사용자, 8단계 초과, 이름 안의 쉼표를 다룬다.
- `apps/api/src/users/users.service.test.ts` — 서버 시험을 덧붙인다. 34명 정상 등록, 기존 그룹
  재사용, `skipExisting` 동작, 그리고 **중간에 실패했을 때 아무것도 남지 않는지**를 확인한다.
- 경합 시험도 같은 자리에 둔다 (§4.4).
  - 미리보기를 받은 뒤 **다른 경로로 사용자를 하나 만들고** 적용하면 `409 BULK_IMPORT_STALE` 이
    나오고 아무것도 만들어지지 않는다. `skipExisting` 이 참일 때도 마찬가지다 — 조용히 한 명을 덜
    만들면 안 된다는 것이 이 시험의 요지다.
  - 미리보기를 받은 뒤 **같은 이름의 그룹을 만들고** 적용해도 `409` 가 나온다.
  - 낡은 `previewToken` 으로 적용하면 `409` 가 나온다.
  - 적용 요청에 `previewToken` 이 없으면 거부한다.

## 7. 샘플 파일

확정명세 §2 의 조직 구성을 그대로 담는다. 합계 34명이다.

```
운영기술센터 (21)
  ├─ 기구완성팀 (5)
  ├─ 생산기술팀 (8)
```

한글 아이디를 쓸 수 없으므로(§2.2) 부서마다 영문 약칭을 정했다.

| 부서 | 약칭 | 인원 | 아이디 |
|---|---|---|---|
| 기구완성팀 | `gigu` | 5 | `gigu01`~`gigu05` |
| 생산기술팀 | `saeng` | 8 | `saeng01`~`saeng08` |
