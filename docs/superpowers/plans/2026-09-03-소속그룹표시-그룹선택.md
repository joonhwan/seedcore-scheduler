# 소속 그룹 표시와 그룹 선택 반쯤 체크 상태 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 사용자 목록을 보여주는 화면들에 각 사용자의 소속 그룹을 배지로 표시하고, 그룹 선택 대화상자에 반쯤 체크된 상태를 도입해 그룹을 일부만 고를 수 있게 한다.

**Architecture:** 소속 조회 경로가 화면마다 다르다. 프로젝트 현재 멤버 목록은 일반 MANAGER 도 보므로 **멤버 목록 API 가 소속을 함께 내려주고**, 나머지 화면은 이미 ADMIN 전용 API 를 쓰므로 `useGroupTree()` 를 함께 부른다. 그룹 선택은 `picked` 를 명시적으로 체크된 그룹 집합으로 두고 세 상태를 계산하며, 담기는 인원이 자손 자동 포함(`expandGroupMembers`)에서 **체크된 그룹의 직속 인원 합집합(`directMembersOf`)** 으로 바뀐다. 서버는 그룹 id 를 받지 않으므로 이 변경에 영향받지 않는다.

**Tech Stack:** Node.js 22.13+, NestJS 10, Prisma 5.22, SQLite, React 18, Vite 5, TanStack Query, Tailwind, Zod, vitest

**Spec:** `docs/superpowers/specs/2026-09-03-소속그룹표시-그룹선택-design.md`

```typescript
/**
 * 한 사용자의 소속 그룹 경로를 최상위부터 돌려준다. 소속이 없으면 빈 배열.
 *
 * 운영은 1인 1소속이지만 데이터베이스는 여러 소속을 허용한다(구조를 뜯어고치지 않고 겸직을
 * 열 수 있게 하려는 것이다). 그런 데이터가 들어오면 **말단 이름의 가나다순으로 첫 번째
 * 하나만** 쓴다. 화면이 조용히 하나만 고르는 것보다 여기에 규칙을 적어 두는 편이 낫다.
 *
 * 서버(MembersService)와 화면(사용자 관리·명단 편집기)이 이 함수를 함께 쓴다. 같은 함수여야
 * 서버가 내려준 경로와 화면이 계산한 경로가 어긋나지 않는다.
 */
export function groupPathOfUser<T extends GroupNode & { name: string }>(
  groups: T[],
  memberships: GroupMembership[],
  userId: string,
): string[] {
  const known = new Set(groups.map((g) => g.id));
  const paths = memberships
    .filter((m) => m.userId === userId && known.has(m.groupId))
    .map((m) => groupPathNames(groups, m.groupId))
    .filter((p) => p.length > 0);
  if (paths.length === 0) return [];
  // 말단 이름 기준 가나다순. 하나뿐인 정상적인 경우에는 정렬이 아무 일도 하지 않는다.
  paths.sort((a, b) => a[a.length - 1]!.localeCompare(b[b.length - 1]!, 'ko'));
  return paths[0]!;
}

/** 트리 체크박스의 세 상태. */
export type GroupCheckState = 'checked' | 'indeterminate' | 'unchecked';

/**
 * 트리 체크박스의 세 상태를 판정한다.
 *
 *  - picked 에 있고 모든 자손도 picked 에 있으면 checked
 *  - picked 에 있으나 빠진 자손이 있으면 indeterminate
 *  - picked 에 없으나 자손 중 하나라도 있으면 indeterminate
 *  - 아무것도 없으면 unchecked
 *
 * collectDescendantGroupIds 가 방문 기록으로 순환을 막으므로 이 함수도 순환 데이터에서 멈춘다.
 */
export function groupCheckState(
  groups: GroupNode[],
  picked: ReadonlySet<string>,
  groupId: string,
): GroupCheckState {
  if (!groups.some((g) => g.id === groupId)) return 'unchecked';

  // 자기 자신을 포함해 돌려주므로 자손만 따로 걸러 낸다.
  const descendants = [...collectDescendantGroupIds(groups, [groupId])].filter(
    (id) => id !== groupId,
  );
  const self = picked.has(groupId);
  const pickedDescendants = descendants.filter((id) => picked.has(id)).length;

  if (self) {
    return pickedDescendants === descendants.length ? 'checked' : 'indeterminate';
  }
  return pickedDescendants > 0 ? 'indeterminate' : 'unchecked';
}

/**
 * 주어진 그룹들에 **직접** 속한 사용자 id 를 중복 없이 돌려준다. 자손을 따라가지 않는다.
 *
 * expandGroupMembers 와 달리 자손을 자동으로 포함하지 않는 이유는, 화면이 상위를 체크할 때
 * 자손도 명시적으로 체크하기 때문이다. 이중으로 셀 필요가 없고, 무엇보다 **하위를 일부러
 * 풀었을 때 그 뜻이 그대로 반영되어야** 한다.
 *
 * 반환 순서는 expandGroupMembers 와 같이 memberships 에 들어 있던 순서를 따른다. 화면 표시
 * 순서를 안정적으로 두기 위함이다.
 */
export function directMembersOf(
  memberships: GroupMembership[],
  groupIds: readonly string[],
): string[] {
  if (groupIds.length === 0) return [];
  const targets = new Set(groupIds);
  const out: string[] = [];
  const seen = new Set<string>();
  for (const m of memberships) {
    if (!targets.has(m.groupId)) continue;
    if (seen.has(m.userId)) continue;
    seen.add(m.userId);
    out.push(m.userId);
  }
  return out;
}
```

```typescript
  /**
   * 주어진 사용자들의 소속 경로를 한꺼번에 읽어 맵으로 돌려준다.
   *
   * 화면(사용자 관리·명단 편집기)이 쓰는 것과 **같은 groupPathOfUser 함수**로 만든다.
   * 그래야 서버가 내려준 경로와 화면이 계산한 경로가 어긋나지 않는다.
   *
   * 그룹은 수십 개, 멤버는 프로젝트당 수십 명 규모라 질의 둘을 더하는 부담이 없다.
   */
  private async groupPathMap(
    userIds: string[],
  ): Promise<Map<string, string[]>> {
    const out = new Map<string, string[]>();
    if (userIds.length === 0) return out;

    const [groups, memberRows] = await Promise.all([
      this.prisma.userGroup.findMany({
        select: { id: true, parentId: true, name: true },
      }),
      this.prisma.userGroupMember.findMany({
        where: { userId: { in: userIds } },
        select: { groupId: true, userId: true },
      }),
    ]);
    const memberships = memberRows.map((m) => ({
      groupId: m.groupId,
      userId: m.userId,
    }));
    for (const userId of userIds) {
      out.set(userId, groupPathOfUser(groups, memberships, userId));
    }
    return out;
  }
```

- **`updateRole()`**: 같은 방식으로 채운다. **이 메서드에는 조기 반환(같은 역할일 때)이 있으므로 그 경로에서도 채워야 한다.** 빠뜨리면 같은 역할로 요청했을 때만 배지가 사라진다.

```typescript
/**
 * useGroupTree() 로 받은 그룹·소속에서 사용자별 소속 경로 맵을 만든다.
 *
 * 세 화면(사용자 관리 목록, 명단 편집기의 후보 목록과 명단 목록)이 같은 일을 하므로 여기로

 *
 * tree 가 undefined 인 경우(아직 도착하지 않았거나 조회가 실패한 경우)에는 모두 빈 배열을
 * 돌려준다. **그룹은 곁다리 정보이므로 그것을 못 받았다고 사용자 목록 자체가 오류로 보이면
 * 안 된다.**
 */
import { groupPathOfUser, type UserGroupTree } from '@sam/shared';

export function groupPathMapOf(
  tree: UserGroupTree | undefined,
  userIds: string[],
): Map<string, string[]> {
  const out = new Map<string, string[]>();
  for (const userId of userIds) {
    out.set(userId, tree ? groupPathOfUser(tree.groups, tree.memberships, userId) : []);
  }
  return out;
}
```

- [ ] **Step 4: 토글을 자손까지 다루도록 바꾼다**

`toggle` 함수를 아래로 바꾼다.

```typescript
/**
 * 체크와 반쯤 체크는 모두 "넣기" 다. 자기 자신과 모든 자손을 picked 에 넣는다.
 * 완전히 체크된 것만 "빼기" 이며 자기 자신과 모든 자손을 뺀다.
 */
function toggle(groupId: string) {
  if (!tree.data) return;
  const nodes = tree.data.groups.map((g) => ({ id: g.id, parentId: g.parentId }));
  // 자기 자신을 포함해 돌려준다.
  const family = collectDescendantGroupIds(nodes, [groupId]);
  const state = groupCheckState(nodes, picked, groupId);

  setPicked((prev) => {
    const next = new Set(prev);
    if (state === 'checked') {
      for (const id of family) next.delete(id);
    } else {
      for (const id of family) next.add(id);
    }
    return next;
  });
}
```

### 계획을 쓰면서 정한 것

1. **`groupPathMapOf` 를 `apps/web/src/lib/` 에 둔다.** 설계 문서는 `groupPathOfUser` 만 언급했는데, 세 화면이 `UserGroupTree` 에서 맵을 만드는 일을 반복하므로 웹 전용 얇은 감싸기를 하나 둔다. `undefined` 를 받으면 빈 배열을 돌려주는 규칙(그룹 조회 실패에 견디기)도 여기 한 곳에 담긴다.
2. **Task 5 의 확인 항목을 설계 문서의 11개에서 20개로 늘렸다.** 회귀 확인(그룹 관리 화면의 누계 인원수, 집계 패널)을 더했는데, 이번 작업이 `expandGroupMembers` 를 쓰는 자리를 잘못 건드리면 그 두 곳이 조용히 깨지기 때문이다.
3. **Task 2 Step 2 를 "빌드해서 깨지는 곳을 찾는" 단계로 두었다.** `ProjectMemberItem` 에 필수 필드를 더하면 타입 검사가 고쳐야 할 자리를 정확히 알려 준다. 손으로 목록을 적는 것보다 확실하다.

### 확인한 타입 일관성

- `groupPathOfUser` 는 `groupPathNames` 와 같은 제네릭 제약(`T extends GroupNode & { name: string }`)을 쓴다. `UserGroupItem` 과 Prisma 의 `select: { id, parentId, name }` 결과가 모두 이를 만족한다.
- `groupCheckState` 는 `ReadonlySet<string>` 을 받는다. `GroupPickerDialog` 의 `picked` 는 `Set<string>` 이므로 그대로 넘어간다.
- `directMembersOf` 는 `readonly string[]` 을 받는다. `[...picked]` 가 `string[]` 이므로 그대로 넘어간다.
- `ProjectMemberItem.groupName` 은 `string | null`, `groupPath` 는 `string[]` 이다. `UserGroupBadge` 는 `path: string[]` 만 받으므로 `groupName` 은 화면에서 쓰지 않아도 된다. **그래도 API 계약에 두는 이유는, 목록을 다루는 다른 소비자가 경로 전체를 파싱하지 않고 말단 이름만 쓰고 싶을 때가 있기 때문이다.** 지금 쓰이지 않는 필드가 하나 생기는 것은 알고 두는 것이다.
