### 2차 — 사용자 그룹과 인원별 권한 관리 (테이블 2개 추가) ★ 다음 작업

요청 ②(그룹), 3번(전체 선택), 9·10번(인원별 프로젝트 권한)이 한 덩어리다. 확정명세 §2 가 사양의 원본이다.

**서버에 없는 것 — 여기가 작업의 중심이다**
- "이 사용자가 속한 프로젝트 목록"을 읽는 기능이 없다. `apps/api/src/members/` 는 프로젝트 기준
  API 뿐이다(`projects/:projectId/members`). 사용자 기준 조회·일괄 추가 기능을 새로 만든다.
  `project_members` 테이블에는 `@@index([userId])` 가 이미 있어 조회는 문제없다.
- 그룹 CRUD 와 그룹 소속 관리 API 전부.

**확정된 설계 제약 (2차 회신 ㉯·㉰)**
- 그룹 인원이 바뀌어도 **기존 프로젝트 참여자는 그대로 둔다**(명단 복사). 자동 반영 없음.
- **1인 1소속**이되 그룹에 상하 관계가 있다. `user_groups.parent_id` 로 표현하고, 상위 그룹을 고르면
  하위 그룹 인원까지 딸려온다(운영기술센터를 고르면 산하 세 팀 + 센터장 21명). 사람은 말단 팀
  하나에만 등록한다.
- DB 는 다대다 구조로 두고 1인 1소속은 화면에서 지킨다 — 겸직이 생겨도 스키마를 안 고치려는 것이다.
- 프로젝트 생성 시 그룹 선택과 개별 선택이 겹쳐도 한 번만 들어가야 한다(중복 제거).
- 그룹으로 들어온 인원의 기본 역할은 MEMBER. MANAGER 는 개별 지정.

**지켜야 할 기존 규칙**
- 마지막 MANAGER 는 제거할 수 없다(`members.service.ts` 의 `LAST_MANAGER` 검사).
- 모든 권한 변경은 감사 기록을 남긴다. 관리자 모드에서 한 변경은 `ADMIN_OVERRIDE_EDIT` 도 함께 남긴다.
- 새 API 는 `@UseGuards(OriginGuard)` 와 Zod 스키마 검증을 붙인다(AGENTS.md §4.2, §4.4).

**작업 순서 제안**
1. Prisma 스키마 + 마이그레이션(그룹 두 테이블). SQLite 라 enum 이 없다 — 필요하면 CHECK 제약.
2. 그룹 CRUD API + 소속 관리 API.
3. 사용자 기준 프로젝트 조회·일괄 추가 API (요청 9·10).
4. 관리자 그룹 관리 화면.
5. 사용자 관리 화면에 "이 사람의 프로젝트" 패널(조회·일괄 추가·역할 변경·제외).
6. 프로젝트 생성 화면 개편(그룹 선택 + 개별 추가 + 최종 명단 확인).

### 3차 — 사용자 삭제와 퇴사 처리 (컬럼 1개 추가)

  선택 목록과 **그룹 추가 대상 목록에서 제외**. 되돌릴 수 있어야 한다(복직).

## 5. 작업 환경 주의사항

- **개발 서버는 `pnpm dev` 하나로 띄운다.** `scripts/dev.mjs` 가 shared 빌드 → vite 사전 번들 캐시 삭제 →
  web·api 기동을 순서대로 처리한다. 캐시 삭제를 건너뛰면 shared 의 새 export 가 `undefined` 가 되어
  **에러 없이 빈 화면**이 뜨는데(AGENTS.md §5), 스크립트가 매번 지우므로 그 함정에 걸리지 않는다.
  다른 방법으로 띄울 때만 손으로 챙기면 된다.
- **개발 중에는 브라우저로 5173 만 연다. 3000 을 직접 열면 옛 화면이 뜬다.**
  5173 은 `/api` 를 3000 으로 프록시하므로 3000 은 떠 있어야 하지만, 브라우저로 열 곳은 아니다.
  API 서버는 정적 화면 경로를 후보 순서대로 찾는데(`app.module.ts` 의 `resolveStaticRoot`),
  `apps/api/public` 이 `apps/web/dist` 보다 먼저 걸린다. 그 폴더는 `pnpm build:exe` 가
  `apps/web/dist` 를 복사해 만드는 산출물이고 git 무시 대상이라, **몇 달 전 exe 를 빌드한 흔적이
  남아 있으면 3000 에서 그 시절 화면이 그대로 뜬다.** 실제로 2026-09-01 에 이것 때문에
  "고친 기능이 반영되지 않는다"고 30분을 뒤졌다(코드·DB·API 는 모두 정상이었다).
  3000 에서 최신 화면을 보고 싶으면 `apps/api/public` 을 지운다 — 그러면 후보 순서상
  `apps/web/dist` 가 잡혀 `pnpm -F @sam/web build` 결과가 3000 에도 반영된다(서버 재시작 필요).
- **exe 검증은 개발 서버를 끄고 한다.** `sp-server.exe` 도 3000 을 쓰므로 `pnpm dev` 가 떠 있으면
  `EADDRINUSE` 로 죽는다. exe 는 실행한 폴더의 `data/sam.db` 를 쓰므로 개발 DB
  (`apps/api/prisma/data/app.db`)와 데이터가 별개다.
- Prisma Client 는 생성해 두었다. 1단계는 스키마 변경이 없었다. 3~5단계에서 마이그레이션이 생기면
  **작업 후 사용자에게 DB 변경 내용을 상세히 공유해야 한다**(AGENTS.md §7).
- `prisma migrate` 는 개발 서버를 끄고 돌린다(SQLite 단일 writer).
- 셸에서 `cd` 를 독립적으로 쓰지 않는다. 절대 경로를 쓴다(AGENTS.md §4.1).
- 커밋 메시지를 heredoc 으로 넘길 때 PowerShell 문법(`@'...'@`)을 Bash 도구에 쓰면 제목에 `@` 가
  섞인다. 파일에 써서 `git commit -F` 로 넘기는 편이 안전하다.

## 6. 권해 두는 스킬

- `superpowers:brainstorming` — **2차 착수 전에 쓴다.** 사용자 그룹은 요구가 회신 과정에서 확대된 신규
  기능이고 화면이 여러 개 얽힌다(그룹 관리, 프로젝트 생성 개편, 인원별 권한 관리). 코드를 짜기 전에
  화면 흐름을 한 번 발라내는 편이 좋다.
- `superpowers:writing-plans` — 2차·3차는 서버 API 와 화면 여러 개를 걸치는 다단계 작업이다. 착수 전에
  계획을 글로 정리해 두면 중간에 길을 잃지 않는다.
- `superpowers:test-driven-development` — 3차의 "삭제 가능 여부 판정"처럼 분기가 많은 순수 로직은
  테스트를 먼저 쓰는 편이 빠르다. 1차에서도 `sessionCountdown.ts` 를 그렇게 떼어 두었다.
- `sam-troubleshooting` (프로젝트 스킬) — `database is locked`, 옛 빌드 실행, 빈 화면 같은 이 저장소
  고유의 함정을 다룬다. 개발 서버가 이상하게 굴면 먼저 본다.
- `mirero-tools:easy-korean-doc` — 사용자 대표에게 보낼 문서를 새로 쓰거나 고칠 때.
- `superpowers:verification-before-completion` — "됐다"고 보고하기 전에 실제로 돌려 본 증거를 남기는
  습관용. 1단계에서는 임시 DB에 서버를 띄워 쿠키 만료 시각까지 눈으로 확인했다.
