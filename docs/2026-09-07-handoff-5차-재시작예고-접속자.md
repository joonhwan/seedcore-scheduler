## 2. 이번 차수의 범위

확정명세 §5 그대로입니다. 요약하면 셋입니다.

**가. 관리자 화면** — 재시작 예정 시각과 안내 문구를 등록하고, 등록한 예고를 취소합니다.
같은 화면에 **현재 접속자 목록**(이름, 마지막 활동 시각, 접속 IP)을 함께 보여줍니다.

**나. 사용자 화면** — 재시작 5분 전부터 팝업이 뜨고 남은 시간이 초 단위로 줄어듭니다. "확인" 으로
닫아도 **1분마다 다시 뜹니다**(5분 전, 4분 전, … 1분 전). 편집 중인 내용이 있으면 "저장하지 않은
변경이 있습니다" 를 함께 띄웁니다.

**다. 접속자 판단 기준** — **최근 5분 이내에 활동한 사람**을 접속 중으로 봅니다(㉳ 회신). 브라우저를
그냥 닫은 사람은 최대 5분 동안 목록에 남습니다. 서버가 알 수 없는 정보라 근사치일 수밖에 없습니다.

**데이터베이스 변경은 테이블 하나입니다.**

```
server_notices       재시작 예고 등 공지
  id, kind, message, scheduled_at, created_by, created_at, canceled_at
```

예고는 한 번에 하나만 유효하도록 다루되, 지난 예고 기록은 남겨 언제 재시작했는지 추적할 수 있게
합니다.

## 3. 코드 조사 결과 — 다시 찾지 않아도 되는 것

이번 세션이 미리 훑어 둔 것입니다. **이 작업에 필요한 재료가 대부분 이미 있습니다.**

### 3.1 접속자 목록의 재료는 이미 다 있다

`Session` 모델(`apps/api/prisma/schema.prisma:160`)이 필요한 것을 모두 갖고 있습니다.

```prisma
model Session {
  sid        String   @id
  userId     String   @map("user_id")
  createdAt  DateTime @default(now()) @map("created_at")
  lastSeenAt DateTime @default(now()) @map("last_seen_at")   // ← 접속 판단 기준
  expiresAt  DateTime @map("expires_at")
  ip         String?                                          // ← 화면에 보여줄 IP
  userAgent  String?  @map("user_agent")
  ...
  @@index([userId])
  @@index([expiresAt])
}
```

- **`lastSeenAt` 은 이미 매 요청마다 갱신되고 있습니다.** `AuthGuard` 가 만료는 건드리지 않고
  `lastSeenAt` 만 올립니다(`sessions.service.ts:48` 주석이 "관리자 화면의 접속자 목록이 쓸 근거를
  남기기 위해서다" 라고 밝혀 두었습니다). **즉 이 기능을 위해 심어 둔 것이며 그대로 쓰면 됩니다.**
- `ip` 와 `userAgent` 도 이미 채워지고 있습니다.
- **인덱스가 `[userId]` 와 `[expiresAt]` 뿐이라 `lastSeenAt` 기준 조회에는 색인이 없습니다.**
  다만 150명 규모에서 세션 행은 많아야 수백 개이므로 전체 훑기로 충분합니다. 색인을 더하면
  마이그레이션이 늘어나니 굳이 넣지 마십시오.
- 접속 중 판단은 `lastSeenAt >= now - 5분` **이면서** `expiresAt > now` 여야 합니다. 만료된 세션 행은
  즉시 지워지지 않으므로 앞 조건만 보면 이미 끊긴 사람이 섞입니다.

### 3.2 카운트다운 팝업은 본뜰 것이 이미 있다

**세션 만료 연장 창이 구조적으로 같은 물건입니다.** 1차에서 만들어 검증까지 끝난 코드이므로
그대로 본뜨십시오.

| 파일 | 역할 |
|---|---|
| `apps/web/src/lib/sessionCountdown.ts` | 순수 함수 셋: `remainingMs`, `formatRemaining`, `tickIntervalMs` |
| `apps/web/src/lib/sessionCountdown.test.ts` | 위 함수들의 시험 |
| `apps/web/src/lib/session.ts` | `useSessionRemaining` 훅 — 남은 시간을 화면이 스스로 센다 |
| `apps/web/src/components/SessionExpiryDialog.tsx` | 만료 10분 전에 뜨는 대화상자 |
| `apps/web/src/components/SessionCountdownBadge.tsx` | 헤더에 상시 표시되는 남은 시간 |

**가장 중요한 것: 시계 어긋남을 다루는 방식을 반드시 그대로 따르십시오.**

`MeResponse`(`packages/shared/src/index.ts:62`)는 `sessionExpiresAt` 과 함께 **`serverNow`(응답을 만든
서버 시각)** 를 내려줍니다. 화면은 `sessionExpiresAt - serverNow` 로 남은 시간을 재고, 그 뒤로는
자기 시계로 흘려보냅니다(`session.ts` 의 `receivedAtLocalMs`). 그 필드의 주석이 이유를 적어 두었습니다.

> 브라우저 시계를 그대로 믿고 빼면, 사내 PC 시계가 몇 분 어긋나 있을 때 연장 창이 엉뚱한 때에
> 뜨거나 아예 뜨지 않는다.

**재시작 예고도 똑같습니다.** `scheduledAt` 만 내려주고 브라우저 시계로 빼면, 시계가 3분 빠른 PC 는
재시작 2분 뒤에야 팝업을 보게 됩니다. **서버 시각을 함께 내려주십시오.**

`tickIntervalMs` 가 남은 시간에 따라 간격을 바꾸는 것(30초 → 1초)도 그대로 쓸 수 있습니다.
`setInterval` 이 아니라 `setTimeout` 을 다시 거는 형태인 이유가 그것입니다.

### 3.3 예고를 화면에 어떻게 닿게 할 것인가 — 결정이 필요하다

**이번 작업에서 설계 판단이 필요한 유일한 지점입니다.** 브레인스토밍에서 다루십시오.

지금 `me` 질의는 `staleTime: 30_000` 이고(`apps/web/src/lib/auth.ts:18`) **주기적으로 다시 받지
않습니다.** 창 포커스나 마운트 때만 갱신됩니다. 즉 사용자가 화면을 켜 둔 채 가만히 있으면
새로 등록된 예고가 닿지 않습니다.

갈래는 둘입니다.

- **`me` 응답에 예고를 얹고 `me` 를 주기적으로 다시 받는다.** 새 엔드포인트가 필요 없고 `serverNow`
  가 이미 있어 시계 문제도 그대로 풀립니다. 대신 `me` 가 무거워지고, 예고가 없을 때도 계속 부릅니다.
- **예고 전용 엔드포인트를 따로 두고 그것만 주기적으로 부른다.** `me` 를 건드리지 않고 응답이
  가볍습니다. 대신 `serverNow` 를 그쪽에도 실어야 하고 폴링 자리가 하나 늘어납니다.

어느 쪽이든 **폴링 주기는 예고 여부에 따라 달라야 합니다.** 5분 전부터 팝업이 떠야 하는데 폴링이
5분 간격이면 놓칠 수 있습니다. 평소에는 느리게, 예고가 잡히면 빠르게 가는 형태를 생각해 두십시오.

### 3.4 "편집 중인 내용이 있으면" 은 이미 알 수 있다 (다만 프로젝트 상세 화면 안에서만)

확정명세 §5-나가 요구하는 "저장하지 않은 변경이 있습니다" 에 쓸 상태가 **이미 있습니다.**

- `NodeDetail.tsx:96` 의 `dirty` 가 제목·설명·시작일·종료일·진행률을 원본과 견주어 판정하고,
  `onDirtyChange` 콜백과 ref 의 `isDirty()` 두 갈래로 밖에 알립니다.
- `ProjectDetailPage.tsx` 가 그것을 받아 **`isDetailDirty`(622행)와 `isCommentDirty`(630행)** 두 상태로
  들고 있습니다. 댓글 입력도 `CommentInputForm`·`NodeCommentsPanel` 이 같은 방식으로 알립니다.

**한계가 하나 있습니다. 이 상태는 프로젝트 상세 화면 안에만 있습니다.** 팝업은 어느 화면에서든
떠야 하므로, 그 값을 팝업이 읽으려면 위로 끌어올려야 합니다. 갈래는 둘입니다.

- 전역 상태에 "편집 중" 플래그를 하나 두고 각 화면이 올린다.
- 팝업을 프로젝트 상세 화면 안에도 하나 더 두어 그 화면에서만 문구를 붙인다.

**전역 상태를 쓴다면 `apps/web/src/lib/store.ts` 의 `createStore`·`useStore` 를 쓰십시오.**
`useSyncExternalStore` 위에 얹은 자체 구현이며 `adminMode`·`theme`·`toast` 가 이미 이 방식입니다.
**AGENTS.md §2.1 은 프런트엔드 기술 스택에 Zustand 를 적어 두었으나 실제로는 설치되어 있지 않습니다**
(`apps/web/package.json` 에 없습니다). 문서 쪽이 낡은 것이므로 새 라이브러리를 들이지 마십시오.

**브레인스토밍에서 확인받으십시오.** 다른 화면(프로젝트 생성·복제·사용자 상세 등)에도 편집 중인
입력이 있으므로, 상세 화면만 다루면 반쪽이 됩니다. 범위를 어디까지로 할지가 결정 사항입니다.

## 4. 마이그레이션 — 이번에는 두 개가 함께 나간다

**직전 마이그레이션은 `20260903010359_user_groups_and_retired_at`(2차·3차)이고 아직 운영에
적용되지 않았습니다.** 5차의 `server_notices` 를 더하면 배포 시 **두 개가 순서대로** 적용됩니다.

- `sp-server.exe` 는 데이터가 든 DB 에서 미적용 마이그레이션을 발견하면 **DB 를 건드리지 않고 종료
  코드 3 으로 멈춥니다**(`apps/api/src/prisma/boot-decision.ts:77`). 관리자가 `sp-migrate.exe` 를 따로
  실행해야 하며, 그 도구가 `VACUUM INTO` 로 `backups/pre-migrate/` 에 스냅샷을 뜬 뒤 적용합니다.
  절차는 배포판 `README.txt` 4장(원본 `apps/api/scripts/README-exe.txt`)에 이미 상세히 있습니다.
- 빌드 쪽은 손댈 것이 없습니다. `apps/api/scripts/build-exe.js` 가 `prisma/migrations` 전체를 복사해
  두 exe 의 pkg 자산에 넣고, 폴더가 비어 있으면 빌드를 중단하는 검사까지 있습니다.
  **새 마이그레이션 폴더를 만들기만 하면 자동으로 실려 나갑니다.**
- 줄바꿈 오염도 막혀 있습니다. `.gitattributes` 가 `apps/api/prisma/migrations/**/*.sql` 을 `eol=lf` 로
  못박고 있습니다.
- **`master` 에 머지하기 전에 fly.io 볼륨 스냅샷을 뜨십시오**(AGENTS.md §7). `master` 에 push 하면
  `deploy.yml` 이 돌고 컨테이너가 뜰 때 `prisma:migrate:deploy` 가 먼저 불립니다.

```bash
fly volumes list -a seedcore-scheduler
fly volumes snapshots create <volume id>
```

## 7. 작업 환경 주의사항

- **`prisma migrate dev` 는 개발 서버를 끄고 돌립니다.** SQLite 는 단일 writer 라 `pnpm dev` 가 DB
  핸들을 쥐고 있으면 락이 걸립니다.
- **`packages/shared` 에 새 export 를 추가하면 vite 사전 번들 캐시를 지워야 합니다.** 안 지우면 그
  심볼이 조용히 `undefined` 가 되어 **에러 없이 화면만 빈 채로** 뜹니다. `pnpm dev` 로 띄우면
  `scripts/dev.mjs` 가 매번 지우므로 안전합니다.
- **API 는 3000 이 뜰 때까지 시간이 걸립니다.** `pnpm dev` 직후 5173 이 응답해도 3000 은 아직
  컴파일 중일 수 있어 `/api` 호출이 502·500 으로 떨어집니다. `curl http://localhost:3000/api/v1/health`
  가 200 을 줄 때까지 기다리십시오.
- **브라우저로 3000 을 직접 열지 마십시오.** exe 빌드가 남긴 `apps/api/public` 의 옛 화면이 뜹니다.
- 코드 수정 후에는 `pnpm -r typecheck` 를 돌립니다.
- 셸에서 `cd` 를 독립적으로 쓰지 않고 절대 경로를 씁니다.
- 커밋 메시지는 파일에 써서 `git commit -F` 로 넘기는 편이 안전합니다.

## 8. 권해 두는 스킬

- **`superpowers:brainstorming`** — **가장 먼저 부르십시오.** §3.3(예고를 화면에 닿게 하는 방식)과
  §3.4(편집 중 상태)를 확인받아야 합니다. 나머지는 확정명세에 이미 정해져 있으므로 무거운 경로가
  필요한지는 판단해 보십시오.
- **`superpowers:writing-plans`** — 설계를 승인받은 뒤에 부릅니다.
- `superpowers:test-driven-development` — 카운트다운 계산처럼 분기가 있는 순수 로직에 씁니다.
  `sessionCountdown.test.ts` 가 본뜰 형태입니다.
- `superpowers:systematic-debugging` — 4차에서 이 스킬로 프레임 단위 측정을 해 깜박임의 원인을
  잡았습니다. 추측으로 고치지 말고 재는 습관이 이 저장소에서 잘 통합니다.
- `sam-troubleshooting` (프로젝트 스킬) — `database is locked`, 옛 빌드 실행, 빈 화면 같은 함정.
- `mirero-tools:easy-korean-doc` — 고객에게 보낼 문서를 고칠 때.
