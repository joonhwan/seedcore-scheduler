### 2.2 채택한 접근 방식

**복제 화면에 이미 있는 참여자 명단 편집기를 공용 컴포넌트로 떼어내고, 그룹 선택을 그 편집기의
"채우기" 입력으로 붙입니다.** 그룹은 명부일 뿐이며 프로젝트 권한과 실시간으로 연결되지 않습니다
(㉯ 회신의 명단 복사 방식).

검토했다가 버린 대안 두 가지를 적어 둡니다. 다음 세션이 같은 고민을 되풀이하지 않도록 하기 위함입니다.

- **그룹을 권한 주체로 승격**(`project_groups` 연결 테이블을 두어 그룹 인원 변경이 프로젝트에 자동
  반영되게 함): ㉯ 회신이 "자동 반영 없음"으로 확정했으므로 요구사항과 정면으로 어긋납니다.
- **서버가 그룹 id를 받아 인원을 펼침**(화면은 그룹 id만 전송): 생성 전에 최종 명단과 "총 7명"을
  확인할 수 없어 확정명세 §2-나와 어긋납니다.

### 2.3 승인받은 설계 — 데이터 모델과 서버 API

**아래 두 절은 사용자에게 제시해 확인을 받았습니다.** 화면 설계와 검증 계획은 아직 제시하지
않았습니다.

**가. 데이터 모델 (Prisma)**

```prisma
model UserGroup {
  id          String   @id
  name        String
  parentId    String?  @map("parent_id")
  description String?
  createdAt   DateTime @default(now()) @map("created_at")
  updatedAt   DateTime @updatedAt @map("updated_at")

  parent   UserGroup?        @relation("GroupTree", fields: [parentId], references: [id])
  children UserGroup[]       @relation("GroupTree")
  members  UserGroupMember[]

  @@unique([parentId, name])
  @@map("user_groups")
}

model UserGroupMember {
  groupId   String   @map("group_id")
  userId    String   @map("user_id")
  addedById String   @map("added_by")
  addedAt   DateTime @default(now()) @map("added_at")

  group   UserGroup @relation(fields: [groupId], references: [id], onDelete: Cascade)
  user    User      @relation("GroupMemberUser", fields: [userId], references: [id])
  addedBy User      @relation("GroupMemberAddedBy", fields: [addedById], references: [id])

  @@id([groupId, userId])
  @@index([userId])
  @@map("user_group_members")
}
```

`User` 모델에는 역참조 두 줄을 더해야 합니다.

```prisma
  groupMemberships   UserGroupMember[] @relation("GroupMemberUser")
  groupMembersAdded  UserGroupMember[] @relation("GroupMemberAddedBy")
```

설계 판단 세 가지를 근거와 함께 남깁니다.

- **`@@unique([parentId, name])` 은 최상위 그룹끼리는 걸리지 않습니다.** SQL 표준상 `NULL` 끼리는
  같다고 보지 않으므로, `parentId` 가 `NULL` 인 최상위 그룹의 이름 중복은 데이터베이스가 막아 주지
  않습니다. **애플리케이션에서 따로 검사해야 합니다.**
- **`onDelete` 정책이 양쪽에서 다릅니다.** 그룹 쪽은 `Cascade`, 사용자 쪽은 기존 관례대로
  `RESTRICT` 입니다. 다만 인원이나 하위 그룹이 남아 있으면 서버가 삭제 자체를 거부하므로 `Cascade`
  는 실제로 발동하지 않는 안전망입니다.
- **계층 깊이는 5단계로 제한하고 순환을 막습니다.** 상위 그룹을 지정할 때 자기 자신이나 자기 자손을
  고르면 그래프가 순환하여 펼침 함수가 무한히 돕니다. 조직도는 회사·본부·센터·팀·파트면 충분하다고
  보아 5로 잡았습니다.

**나. 서버 API**

그룹 (`/api/v1/admin/groups`, ADMIN 전용):

| 메서드 | 경로 | 역할 |
|---|---|---|
| `GET` | `/admin/groups` | 전체 그룹을 계층 정보와 인원수까지 담아 한 번에 반환 |
| `POST` | `/admin/groups` | 그룹 생성 |
| `PATCH` | `/admin/groups/:id` | 이름·설명·상위 그룹 변경 (순환 검사 포함) |
| `DELETE` | `/admin/groups/:id` | 인원·하위 그룹이 없을 때만 삭제 |
| `GET` | `/admin/groups/:id/members` | 소속 인원 목록 |
| `POST` | `/admin/groups/:id/members` | 여러 명을 한꺼번에 추가. 다른 그룹 소속자는 `move` 옵션으로 옮김 |
| `DELETE` | `/admin/groups/:id/members/:userId` | 소속 해제 |

사용자 기준 권한 (`/api/v1/admin/users/:userId/projects`, ADMIN 전용):

| 메서드 | 경로 | 역할 |
|---|---|---|
| `GET` | `…/projects` | 참여 중인 프로젝트와 역할·참여일 |
| `POST` | `…/projects` | 여러 프로젝트에 한 번에 참여시킴 |
| `PATCH` | `…/projects/:projectId` | 역할 변경 |
| `DELETE` | `…/projects/:projectId` | 참여 해제 |

프로젝트 쪽 확장:

- `CreateProjectDto` 에 `memberUserIds` 를 더해 `CloneProjectDto` 와 형태를 맞춥니다. 기본값이 빈
  배열이라 기존 호출은 그대로 동작합니다.
- `POST /projects/:projectId/members/bulk` 를 신설합니다. 개별 추가 API를 여러 번 부르면 중간에
  하나가 실패했을 때 절반만 들어간 상태로 남으므로, 트랜잭션 하나로 처리하고 이미 멤버인 사람은
  건너뛰어 결과를 요약해 돌려줍니다.

**계층 펼침은 `packages/shared` 의 순수 함수로 둡니다.** 그룹 목록과 소속 정보를 받아 "선택한
그룹들의 자손까지 포함한 사용자 id 집합"을 돌려주는 함수이며, **서버의 일괄 추가와 화면의 미리보기가
반드시 같은 함수를 써야** 화면에 "총 7명"이라고 보여 준 숫자와 실제로 들어가는 인원이 어긋나지
않습니다. 분기가 많으므로 테스트를 먼저 쓰십시오.

기존 규칙은 그대로 지킵니다. 새 라우트에는 모두 `@UseGuards(OriginGuard)` 와 Zod 검증을 붙이고,
`AuditAction` 에 `GROUP_CREATE`·`GROUP_UPDATE`·`GROUP_DELETE`·`GROUP_MEMBER_ADD`·`GROUP_MEMBER_REMOVE`
다섯 가지를 더합니다. 일괄 추가는 사람마다 기존 `MEMBER_ADD` 를 남겨 프로젝트 이력에서 추적되게 하고,
마지막 MANAGER 제거 금지 규칙을 사용자 기준 API에도 똑같이 적용합니다.

## 3. 마이그레이션 안전성 — 실측으로 검증 완료

사용자 요청으로 확인했습니다. **다시 검증할 필요가 없습니다.**

`prisma migrate diff --from-schema-datasource` 로 실제 개발 DB와 새 스키마의 차이를 뽑은 뒤, 그 SQL을
데이터가 든 DB 사본에 직접 적용해 확인했습니다. 2차의 테이블 두 개와 3차의 `users.retired_at` 을
한꺼번에 넣은 경우입니다.

- 생성된 SQL은 `ALTER TABLE ADD COLUMN` 하나, `CREATE TABLE` 둘, `CREATE INDEX` 둘로 **모두 다섯
  문장이며 기존 테이블을 재생성하지 않습니다.** SQLite에서 Prisma가 종종 택하는 테이블 재생성
  경로(`RedefineTables`)가 발동하지 않은 이유는 `retired_at` 이 `NULL` 을 허용하고 기본값이 없기
  때문입니다.
- 적용 전후로 users 7, projects 1, project_members 3, schedule_nodes 8, node_comments 2,
  node_history 111, audit_logs 192, sessions 4, autocomplete_terms 34가 **모두 그대로**였습니다.
- `PRAGMA integrity_check` 는 `ok`, `PRAGMA foreign_key_check` 는 위반 0건이었습니다.
- 배포판이 쓰는 문장 분리기(`splitSqlStatements`)에 넣어도 정확히 다섯 문장으로 갈라져 모두
  성공했습니다.

**주의: `retired_at` 에 기본값을 주거나 `NOT NULL` 로 바꾸면 위 결론이 무너집니다.** 그 경우 Prisma가
`users` 테이블을 통째로 재생성하는 경로를 택하므로, 스키마를 그렇게 고칠 일이 생기면 검증을 다시
하십시오.

## 4. 배포 절차 — v1.6 이후 첫 스키마 변경

**이 항목이 이번 세션에서 가장 중요한 발견입니다.**

`sp-server.exe` 는 데이터가 든 DB에서 미적용 마이그레이션을 발견하면 **DB를 건드리지 않고 종료 코드
3으로 멈춥니다**(`apps/api/src/prisma/boot-decision.ts:77`). 자동으로 적용하는 경우는 DB가 완전히
비어 있는 최초 설치일 때뿐입니다. 관리자가 `sp-migrate.exe` 를 따로 실행해야 하며, 그 도구가
`VACUUM INTO` 로 `backups/pre-migrate/` 에 스냅샷을 뜬 뒤 적용합니다.

- 배포판 `README.txt` 4장(원본은 `apps/api/scripts/README-exe.txt`)에는 이 절차가 다섯 단계로 이미
  상세히 적혀 있습니다. **손댈 필요가 없습니다.**
- 반면 고객에게 전달한 확정명세 §7에는 "운영 서버는 재시작 시 마이그레이션이 적용되며"라고 잘못
  적혀 있었습니다. **이번 세션에서 절차 표로 고쳐 커밋했습니다.**
- **마지막 스키마 변경은 2026-07-14 커밋 `b96c0a2` 이고 그 뒤로 237개 커밋 동안 스키마가
  그대로였습니다.** 즉 `sp-migrate.exe` 경로는 코드와 테스트로는 갖춰져 있으나 고객 현장에서 실제로
  돌아본 적이 없을 가능성이 높습니다. **배포 전에 실제 exe를 빌드해 고객 DB 사본으로 업그레이드를
  예행 연습하는 단계를 구현 계획의 마지막에 넣기로 했습니다.**

빌드 쪽은 손댈 것이 없습니다. `apps/api/scripts/build-exe.js` 가 `prisma/migrations` 전체를 복사해
`sp-server.exe` 와 `sp-migrate.exe` 양쪽 pkg 자산에 넣고, 폴더가 비어 있으면 빌드를 중단하는
검사(`assertMigrationsEmbedded`)까지 있습니다. **새 마이그레이션 폴더를 만들기만 하면 자동으로
실려 나갑니다.**

줄바꿈 오염도 이미 막혀 있습니다. `.gitattributes` 가 `apps/api/prisma/migrations/**/*.sql` 을
`eol=lf` 로 못박고 있어 새 파일도 그 규칙에 걸리며, checksum 고정 테스트
(`migration-runner.test.ts`)는 기존 여섯 개만 대조하도록 짜여 있어 새 마이그레이션을 막지 않습니다.

## 5. 코드 조사 결과 — 다시 찾지 않아도 되는 사실들

이번 세션이 코드를 뒤져 알아낸 것입니다. **문서 어디에도 없으므로 여기가 유일한 기록입니다.**

### 5.1 프로젝트 생성과 복제의 비대칭

- **`CreateProjectDto` 는 `managerUserIds` 만 받습니다**(`packages/shared/src/index.ts:189`). 즉
  **생성 시점에 MEMBER를 넣는 방법이 현재 없습니다.** 확정명세 §2-나가 요구하는 "참여자마다 역할
  지정"을 담으려면 이 DTO를 확장해야 합니다.
- **반면 `CloneProjectDto` 는 `managerUserIds` 와 `memberUserIds` 를 이미 함께 받습니다**
  (같은 파일 264행 부근). 따라서 새 형태를 발명하지 말고 이 형태에 맞추십시오.
- **`ProjectClonePage.tsx` 에 참여자 명단 편집기가 이미 있습니다.** `MemberDraft` 인터페이스
  (22행)로 사람마다 MANAGER·MEMBER·제외를 고르고 인원수를 세는 UI이며, 확정명세가 요구하는 "최종
  참여자 명단 확인" 화면이 사실상 여기에 완성되어 있습니다. **채택한 접근 방식의 근거가 바로
  이것입니다.**
- `ProjectNewPage.tsx` 는 MANAGER 체크박스 목록만 있는 단순한 화면입니다. 요청 3번의 "전체 선택
  버튼"이 붙을 자리가 여기입니다.

### 5.2 멤버 API의 축

- `apps/api/src/members/` 는 `@Controller('projects/:projectId/members')` 하나뿐입니다. **사용자를
  기준으로 조회하는 축이 아예 없습니다.**
- `project_members` 테이블에는 `@@index([userId])` 가 이미 있어 조회 성능은 문제없습니다.
- `members.service.ts` 에 지켜야 할 규칙이 모여 있습니다. `LAST_MANAGER` 검사(마지막 MANAGER 제거
  거부), `CANNOT_CHANGE_SELF_ROLE`(관리자 모드가 아니면 자기 역할 변경 금지), 관리자 모드일 때
  `ADMIN_OVERRIDE_EDIT` 를 함께 남기는 패턴입니다. **새 API도 같은 패턴을 따르십시오.**

### 5.3 화면 구조

- `AdminUsersPage.tsx` 는 목록 한 벌에 행마다 버튼이 붙은 단순한 구조이며, 권한 패널을 얹을 자리가

## 7. 작업 환경 주의사항

1단계 이관 문서 §5에 자세히 있으므로 여기서는 이번 작업에 특히 걸리는 것만 적습니다.

- **`prisma migrate dev` 는 개발 서버를 끄고 돌립니다.** SQLite는 단일 writer라 `pnpm dev` 가 DB
  핸들을 쥐고 있으면 락이 걸립니다.
- **`packages/shared` 에 새 export를 추가하면 vite 사전 번들 캐시를 지워야 합니다.** 이번 작업은
  계층 펼침 함수와 새 DTO를 여럿 추가하므로 이 함정에 걸리기 쉽습니다. `pnpm dev` 로 띄우면
  `scripts/dev.mjs` 가 매번 지워 주므로 안전합니다.
- 코드 수정 후에는 `pnpm -r typecheck` 를 돌립니다.
- 셸에서 `cd` 를 독립적으로 쓰지 않고 절대 경로를 씁니다.
- 커밋 메시지는 파일에 써서 `git commit -F` 로 넘기는 편이 안전합니다. PowerShell 문법(`@'...'@`)을
  Bash 도구에 쓰면 제목에 `@` 가 섞입니다.

## 8. 권해 두는 스킬

- **`superpowers:brainstorming`** — **가장 먼저 부르십시오.** 이 세션이 그 스킬의 아키텍처 경로
  중간에 멈춘 상태입니다. 남은 단계는 "화면 설계 제시 → 승인 → 설계 문서 작성 → 자체 검토 → 사용자
  검토"입니다.
- **`superpowers:writing-plans`** — 설계 문서를 사용자가 승인한 뒤에 부릅니다. 브레인스토밍 다음에
  부를 스킬은 이것뿐이며, 다른 구현 스킬을 먼저 부르면 안 됩니다.
- `superpowers:test-driven-development` — 계층 펼침 함수와 순환 검사처럼 분기가 많은 순수 로직에
  씁니다.
- `sam-troubleshooting` (프로젝트 스킬) — `database is locked`, 옛 빌드 실행, 빈 화면 같은 이 저장소
  고유의 함정을 다룹니다.
- `mirero-tools:easy-korean-doc` — 고객에게 보낼 문서를 고칠 때 씁니다.
- `superpowers:verification-before-completion` — "됐다"고 보고하기 전에 실제로 돌려 본 증거를
  남기는 습관용입니다.
